智能体评测平台架构设计

一个要执行别人代码的评测系统。全自研，容器化执行，四类智能体形态统一接入， 轨迹靠 LLM 网关兜底而不依赖被测方自觉埋点。

方案 全自研 · 容器化执行 后端 Python · FastAPI · MySQL · Redis 前端 Vue3 · Element Plus 判官 DeepSeek flash / pro 首期粗估 ~15 人月 ±30%

0与 PRD 的差异说明

先说清楚变了什么，否则这份文档会和 PRD 打架。两个变更动了架构根基。

变更一：不部署 Langfuse，只参考其实现

PRD 的方案 B 是「自研评测中枢 + Langfuse 作证据与 Judge 底座」。现在明确：Langfuse 只作设计参考，不进部署清单。 三件 PRD 里判定「自研性价比最低」的东西，因此必须自研。

PRD 里靠 Langfuse现在影响
OTel 轨迹接收与 ClickHouse 存储自研 OTLP 端点 + 分层存储见 §9
转录本查看器自研（前端最大的一块）见 §4、§9.4
人工标注队列自研标注工作台见 §3
LLM Judge 执行器影响小PRD 首期本就选了「中枢直调 DeepSeek」

省掉了

  • 三套库并存（PostgreSQL + ClickHouse 不再需要）
  • 上游升级风险与 fork 漂移
  • MIT / EE 许可证边界约束
  • 中枢 ↔ Langfuse 的同步与一致性处理
  • 双 UI 分工与深链接规则
  • 部署组件 9 个 → 5 个

新增了

  • OTLP 摄入端点与轨迹分层存储
  • 转录本查看器（span 树、时间轴、diff）
  • 人工标注工作台
  • LLM 网关（原部分依赖 Langfuse）
  • 容器化执行引擎（原二期）
  • 智能体制品管理（原不在范围）

Langfuse 从「底座」降为「设计参考」。 这些实现思路值得抄，代码不引入：业务实体与轨迹分库存储、OTel GenAI 语义约定的落地方式、评分器分 LLM 与 CODE 两类、数据集条目用 validFrom/validTo 做版本、用 sourceTraceId 把生产轨迹直接转成评测任务。

变更二：智能体从「外部调用」变成「上传托管」

PRD 的接入层假设被测智能体在平台外部运行，平台只是调用方。现在平台要执行别人的代码——这是整个架构里最难、安全风险最高的部分，也是选容器化执行的直接原因。

这条改变了首要风险

PRD 的风险表里首要风险是「许可证边界」与「上游升级」。现在这两条消失了，取而代之的是「平台执行任意代码与 shell」。尤其是 AI 编程工具型智能体（opencode / claude code / codex），它们的本质就是「在你的机器上执行命令」。安全设计见 §11，不粉饰残余风险。

工作量重估

PRD 原估首期 9.6 人月，前提是「外部智能体 + Langfuse 底座」。两项变更叠加后重估，依据逐条列出，不含糊：

变化项人月增减说明
去掉 Langfuse 集成与同步−0.5省掉双向同步、幂等重试、冲突处理
自研 OTLP 接收与轨迹存储+1.0protobuf/json 双格式解析 + 分层落库
自研转录本查看器+1.5span 树、时间轴、筛选、搜索、diff 视图

PRD 已按本文档同步修订，两份文档在组件清单、部署拓扑、工作量、风险四处口径一致。

1架构目标与约束

1.1 架构要达成的四件事

直接对应 PRD 第 2.2 节的目标，但落到架构语言：

目标架构上怎么保证
判据绕不过去rubric 硬约束落到 MySQL 的 NOT NULL 与 CHECK；打分公式在服务端唯一实现，无旁路写入口
轨迹完整可审计LLM 网关强制代理——不依赖被测方埋点；三通道证据各有独立采集链路
执行环境可信且可复现每试次一个容器，跑完销毁；夹具与工作区快照版本绑定
门禁能真的阻断门禁判定是同步 API + 稳定 exit code，CI 直接消费

1.2 硬约束

约束内容来源
技术栈后端 Python + FastAPI + MySQL + Redis；前端 Vue3 全家桶 + Element Plus部门指定
大模型DeepSeek 双档：deepseek-v4-flash / deepseek-v4-pro，共用一把 key部门指定
不引入Langfuse 不部署；ClickHouse 不引入（理由见 §6.3）本轮确认
部署内网，中间件无限制；容器编排能力待确认（§10 给 K8s 与纯 Docker 两种拓扑）本轮确认
首期范围测试支撑智能体优先；产品智能体二期PRD §13
密钥公开仓库，任何产物只出现环境变量名PRD §5.5

1.3 四类智能体形态

这是架构必须同时承接的四种东西，隔离难度差一个量级。第 ③ 类是架构的压力测试点。

形态怎么跑轨迹从哪来隔离难度
① 配置式
提示词 + 模型 + 工具		 平台内置运行时按配置编排 平台自己产生，最完整 低 无任意代码执行
② Python 代码包
zip / wheel / Git		 容器内装依赖，按契约调入口函数 LLM 网关兜底 + 可选 SDK 埋点 中 可执行任意 Python
③ AI 编程工具 CLI
opencode / claude code / codex		 容器内给工作区，它读写文件、跑 shell、执行测试 LLM 网关为主 + CLI 会话日志适配器 + shell 审计 高 可执行任意 shell
④ 远程服务
只注册地址		 只发 HTTP 请求 靠对方埋点，平台不可控 不适用（不在平台内执行）
形态 ④ 的诚实说明

远程服务模式下，平台无法保证「每试次全新环境」，也拿不到完整轨迹。它是兼容性选项，不是推荐路径。用它跑出来的鲁棒性与一致性指标要在报告里标注「环境不可控」。

2整体架构

七层结构沿用 06 分册，但每一层落到具体组件。看这张图先看颜色：蓝色是自研服务，橙色是存储，红色虚线框是不可信执行区——那里跑的是别人的代码。

自研服务 存储 外部系统 不可信执行区 —— 数据流　- - - 控制流

2.1 三条贯穿全架构的设计主线

主线一 · 不可信执行区只有一个出口
做法
容器默认拒绝出网，只放行 LLM 网关与平台回调两个地址。
为什么
被测智能体不能直接触达外网、不能访问其他试次的数据、不能连数据库。把出口收敛到一个点，采集与管控才有着力点。
顺带收益
所有模型调用必经网关 → 轨迹完整性不依赖被测方自觉；成本能算到每个试次；二期故障注入有现成拦截点。
主线二 · 业务语义只在服务端实现一次
做法
打分公式、安全门控、权重校验只在评分层实现，无旁路写入口；前端只做提示，不做判定。
为什么
平台存在的意义是把「靠自觉」变成「绕不过去」（PRD §2.2）。判定逻辑一旦有第二个实现，两边就会漂移。
否决了什么
否决了「前端算分、后端存分」的省事写法。
主线三 · 热数据进 MySQL，大载荷进对象存储
做法
轨迹的结构化索引（span 树、耗时、token、成本）进 MySQL；prompt/completion 全文、shell 输出、文件 diff 进对象存储，MySQL 只存 key。
为什么
技术栈限定 MySQL，而轨迹是高写入、含大文本的数据。不分层，MySQL 会被大 BLOB 拖垮。
否决了什么
否决了引入 ClickHouse（理由见 §6.3），也否决了「全塞 MySQL」。

3业务架构

七个能力域。依赖方向是单向的：左边是「准备什么」，中间是「跑与判」，右边是「看与治」。任何一个域反向依赖右边的域，都是设计错误。

3.1 智能体管理域（新增，本轮重点）

PRD 里没有这个域，因为原假设是智能体在平台外部跑。现在它成了入口。

能力说明优先级
制品上传与存储zip / wheel / Git URL 三种来源；落对象存储，记 SHA256P0
版本管理同一智能体多版本并存，可指定版本参与评测，支持多版本 A/B 并排跑P0
规格契约声明形态、入口约定、输入输出 schema、环境变量、资源需求、超时P0
静态检查依赖漏洞扫描、体积上限、禁用 API 检测（如直接 socket 外连）P1
冒烟自检上传后自动跑一个 hello-world 任务；不通过不允许进评测P0
生命周期状态机草稿 → 检查中 → 已验证 → 已发布 → 已下线P0
运行日志留存stdout / stderr / CLI 会话日志，按试次归档P1
冒烟自检不是可选项

没有它，一个装不上依赖的智能体会在正式评测里产生几十条 infra_error，浪费算力还污染统计。上传即验证，是把失败成本前移。

4应用架构

模块化单体，不是微服务。 三人团队、首期 15 人月，拆微服务会把大部分预算花在treating分布式事务和服务治理上。做法是：单进程部署，但包边界严格，为将来拆分留缝。

决策 · 模块化单体 vs 微服务
选择
模块化单体（eval-hub-api）+ 独立的异步执行进程（eval-hub-worker）+ 独立的 LLM 网关（eval-hub-gateway）
为什么拆出 worker
试次执行是长任务（分钟级到小时级），跟 Web 请求生命周期不匹配，必须异步；且要按并发独立扩容。
为什么拆出网关
它是唯一持有真实密钥的组件，且被不可信容器直接访问。安全上必须独立进程、独立网络策略，不能和主 API 同进程。
为什么其余不拆
评分、门禁、报告之间共享大量领域模型，拆开会产生分布式事务。包边界清晰即可，真到瓶颈再拆。

4.1 包边界规则

  • 接口层薄。 api/v1/* 只做协议转换、鉴权、Pydantic 校验，业务逻辑一行不写。
  • 模块间不直接 import 内部实现，只调对方的 service.py 公开函数，或通过事件总线解耦。
  • 只有 scoring 能写评分结果，其他模块只读。这是「业务语义只实现一次」的落地。
  • 仓储抽象隔离 ORM，领域逻辑不依赖 SQLAlchemy，便于单测。

5数据架构

三处存储，各有明确分工。判断一份数据放哪，只看两个问题：要不要按它查询与聚合？它有多大？

5.1 为什么轨迹要分层存

一次 CLI 型智能体的试次，可能产生上百个 span，其中每个 LLM 调用的 prompt 全文就有几十 KB，shell 输出与文件 diff 更大。直接塞 MySQL 会有三个后果：表膨胀到 TB 级、SELECT * 慢查询、备份恢复时间失控。

数据去处判断依据
span 的 id / parent / name / kind / 起止 / 耗时 / token / 成本MySQL要按它筛选、排序、聚合
span 属性中的短标量（模型名、工具名、状态码）MySQL（JSON 列）要按它筛选，但结构不固定
prompt / completion 全文对象存储只在打开某条 span 时整体读取
shell 输出、文件 diff、产物对象存储同上，且体积大

查询路径：转录本查看器先从 MySQL 取整棵 span 树（一次查询，索引 (trace_id, start_time)），渲染骨架；用户点开某条 span 时，才按 key 去对象存储拉全文。首屏不拉大文本。

5.2 数据生命周期

阶段时长处理
热0–90 天全在 MySQL + 对象存储，查询无限制
温90 天–1 年span 明细从 MySQL 归档为对象存储的列式文件，只保留 trace 汇总行
冷> 1 年对象存储转低频存储层；run / trial / rubric_result 永久保留（基线可追溯性要求）
评分结果不归档

rubric_result 含 evidence_ref 与 evidence_excerpt，是审计链的一环。摘录（excerpt）必须留在 MySQL，这样即使原始轨迹归档了，「当时凭什么这么判」仍然可查。这是 PRD §8.2 的设计要点②在数据生命周期上的延伸。

5.3 容量估算（粗估，需按实际压测修正）

假设值
首期被测对象3 类支撑智能体 × 各 2–3 个版本
评测集规模每类 20–30 任务
运行频次冒烟每次提交、回归每次合入、能力集每日
试次量约 6–8 万试次 / 年
MySQL 首年< 30 GB（含轨迹索引）

6.2 需要额外引入的组件，逐个给理由

技术栈只指定了 FastAPI + MySQL + Redis + Vue3。下面是必须补的，每个都说清为什么非要不可。

组件为什么非引不可能否省掉
对象存储
MinIO / S3 兼容		 轨迹大载荷、智能体制品、工作区快照、试次产物都是大文件，MySQL 存不合适（见 5.1） 不能省。 若部门已有 S3 兼容存储，直接复用，少运维一个组件
Celery 试次执行分钟级到小时级，超出 HTTP 请求生命周期；且要按并发独立扩容 可用 FastAPI BackgroundTasks 替代，但没有重试、限流、可观测，不建议
容器运行时
K8s 或 Docker		 要执行不可信代码，进程级隔离不够（见 §11） 不能省。 这是架构方案的前提
镜像仓库
Harbor 或已有		 存放平台维护的标准基础镜像 可用已有仓库；镜像只有 2–3 个，量很小
Prometheus + Grafana 运行成功率、infra_error 率、判官成本、队列积压要可观测 可推后，但 P1；若部门已有监控体系直接对接

6.3 被否决的选型

否决 · 部署 Langfuse 作证据底座
否决理由
用户明确只参考实现、不部署。连带后果是三套库变一套、集成与同步逻辑全省，但轨迹存储、转录本查看器、标注台要自研。
保留了什么
它的设计思路：业务实体与轨迹分库、OTel 语义约定落地方式、评分器分 LLM/CODE 两类、数据集条目版本化、生产轨迹转任务。见 §16.2。
否决 · 引入 ClickHouse 存轨迹
否决理由
首期量级撑不起它。按 5.3 估算，首年轨迹索引 < 30 GB，MySQL 加合适索引完全够用。为这个量引一个列存数据库，运维成本远大于收益。
什么时候该重新考虑
二期接入产品智能体后，若 span 表超过 5000 万行或聚合查询超过 3 秒，再评估。架构上留了缝：轨迹读写走 evidence 模块的仓储抽象，换存储不影响上层。
否决 · 引入 OpenTelemetry Collector
否决理由
首期只有一个消费端（本平台），Collector 的价值（多后端扇出、采样、批处理）用不上。FastAPI 直接实现 OTLP/HTTP 端点，少一个组件。
代价
要自己处理 protobuf 解析与背压。用 opentelemetry-proto 官方包，工作量约 3 人日。
什么时候该重新考虑
轨迹要同时送多个后端时。
否决 · 微服务拆分
否决理由
三人团队、首期 15 人月。拆微服务会把预算花在服务治理与分布式事务上，而不是业务能力。
替代
模块化单体 + 严格包边界，见 §4。网关与 worker 因安全与生命周期原因单独成进程，这是必要拆分，不是微服务化。

7智能体接入与执行架构

7.1 制品生命周期

上传不等于可用。中间必须过两道闸：静态检查拦掉明显不该进来的，冒烟自检拦掉跑不起来的。

7.2 智能体规格契约

上传时必须声明的元信息。契约是平台与智能体之间唯一的约定，不靠口头沟通。

字段说明适用形态
formconfig / python_pkg / cli_tool / remote全部
entrypointPython：module:function；CLI：命令行模板② ③
input_schema / output_schemaJSON Schema，平台据此校验并生成表单全部
runtime基础镜像标识：py311 / cli-tools② ③
dependenciesrequirements.txt 或 pyproject.toml②
env_declares需要的环境变量名（只声明名字，值由平台注入）② ③
resourcesCPU / 内存 / 磁盘上限，超出则拒绝调度② ③
timeout_sec单试次硬超时全部
workspace_required是否需要工作区（代码仓库快照）③
env_declares 只声明名字，不接受值

智能体不能在契约里塞自己的 API key。所有密钥由平台在启动容器时注入，且注入的是试次临时凭证而非真实密钥（见 §8）。若某智能体确实需要访问内部专有服务，走白名单审批，并在报告里标注「轨迹完整性降级」。

7.3 四形态的执行路径

7.4 容器执行的六条硬规则

规则怎么实现为什么
每试次全新容器Job / docker run --rm，跑完销毁，不复用杜绝跨试次状态污染（06 §5.1）
默认拒绝出网NetworkPolicy 或自定义 bridge + iptables，只放行网关与回调两个地址收敛出口，采集与管控才有着力点
非 root 运行runAsNonRoot + 固定 UID，禁用 privileged 与所有 Linux capabilities降低逃逸后的破坏面
根文件系统只读readOnlyRootFilesystem，只有工作区与 /tmp 可写且限额防止篡改运行时
资源硬限制CPU / 内存 limits + 磁盘配额 + timeout_sec 硬杀单个智能体不能拖垮整个执行池
金标准延迟投放启动时挂载的载荷不含金标准；评分在容器销毁后于平台侧进行时间防火墙（03 §7.2）

7.5 冷启动与预热池

冒烟门禁的预算是 ≤ 5 分钟。若每次起容器都要拉镜像、装依赖，光冷启动就能吃掉一大半。

  • 基础镜像只维护两个：py311-runtime（形态 ②）与 cli-tools（形态 ③，预装 opencode / claude code / codex）。制品挂载进去，不为每个智能体版本重新构建镜像。
  • 依赖层缓存：同一智能体版本的 requirements hash 命中时复用已构建的依赖层。
  • 预热池：常驻 N 个空闲容器（可配，默认 4），调度时直接注入制品与工作区，省掉容器创建时间。池子按门禁级别分配优先级——冒烟优先拿预热容器。
  • 镜像预拉：执行节点上常驻基础镜像，不走每次拉取。
CLI 工具版本要锁死并纳入版本三元组

形态 ③ 的评测结果同时取决于模型和 CLI 工具本身的版本。cli-tools 镜像里各工具的版本必须锁定，且写进运行记录的 agent_version。否则某天镜像重建、工具升级，分数变了却查不出原因——这正是 WildClawBench「同一模型换 harness 分数差 6 个百分点以上」揭示的问题。

8LLM 网关架构

这是整个架构最关键的一环。 它同时解决四个问题：轨迹完整性、成本归集、密钥安全、故障注入点。

核心思路

被测智能体不会主动埋点——claude code、codex 这些工具更不会为你的平台改代码。但它们都要调模型。 把模型调用收敛成唯一出口，就能在不修改智能体一行代码的前提下拿到完整的 LLM 调用轨迹。

8.1 试次临时凭证的设计

这是网关能把调用归属到试次的关键。

属性设计理由
形式JWT，载荷含 trial_id / run_id / agent_version_id / jti无状态校验，网关不必每次查库
有效期= 该试次的 timeout_sec + 60 秒缓冲试次结束凭证即失效，泄露了也用不了多久
吊销Redis 存 jti 白名单，试次结束立即删除硬超时或人工中止时能立刻断掉
作用域只能调网关，只能用该智能体契约里声明的模型档位防止低优先级任务偷用强档
格式伪装对外看起来就是一个 sk- 前缀的普通 keyCLI 工具会校验 key 格式，不伪装会被拒绝
凭证泄露的处置

凭证会出现在容器环境变量里，被测智能体理论上能读到并外传。缓解是纵深防御：容器不能出网（除网关外）→ 传不出去；凭证短时效 → 传出去也快过期；作用域受限 → 只能调网关的模型接口，做不了别的。残余风险仍然存在，接受它并靠审计发现异常调用量。

8.2 网关必须做到的三件事

  • 协议兼容要真。 支持 OpenAI 的 /v1/chat/completions（含流式 SSE）与 Anthropic 的 /v1/messages——CLI 工具用哪套协议不由我们决定。流式响应要边转发边累积记录，不能等全部收完再转发（会破坏交互体验并可能触发工具超时）。
  • 失败要透传语义。 上游 429 / 500 要原样传回，不能吞掉转成自己的错误码，否则智能体的重试逻辑会失效，测出来的鲁棒性是假的。
  • 网关自身不能成为瓶颈。 它在所有试次的关键路径上。用 httpx.AsyncClient 连接池 + 无状态设计，可水平扩多副本。

9.1 OTLP 摄入端点

项设计

9.2 CLI 会话日志适配器

形态 ③ 的特殊处理。opencode / claude code / codex 各自有自己的会话记录格式（JSON Lines 或 SQLite），格式不统一且会随版本变。

  • 适配器按工具分别实现，放在 evidence/cli_adapters/ 下，每个工具一个模块，解析结果统一转成 OTel span。
  • 适配器是尽力而为，不是依赖项。 某个工具升级后格式变了、解析失败，只影响轨迹的丰富度，不影响评分——因为 LLM 调用轨迹来自网关，产物来自工作区 diff，这两条都不依赖会话日志。
  • 解析失败要显式记录并在报告标注「该试次 CLI 会话日志未解析」，不静默吞掉。

9.3 shell 审计

形态 ③ 会执行任意 shell。要知道它做了什么，有三种做法，按可行性排序：

做法覆盖度代价取舍
包装 shell：容器内把 /bin/sh 替换为记录后转发的包装脚本中——能记 CLI 工具通过 shell 执行的命令低首期采用
容器内 auditd高——系统调用级中，需要额外 capability，与「禁用所有 capabilities」冲突不采用
宿主 eBPF 探针最高高，需内核支持与专门运维二期评估
包装 shell 能被绕过，要说清楚

智能体若直接用 subprocess 调二进制而不经 shell，包装脚本就记不到。它是取证辅助，不是安全边界。 真正的安全边界是容器隔离与网络策略（§11）。审计的目的是「事后能查」，不是「事前能防」。

9.4 转录本查看器（自研）

前端最大的一块，也是「不部署 Langfuse」后新增的主要工作量。功能清单：

必须有（P0）

  • span 树形展开 / 折叠，按耗时着色
  • 时间轴甘特视图，看清并发与阻塞
  • 按 span 类型筛选（LLM / 工具 / shell / 文件）
  • LLM 调用的 prompt / completion 左右对照

11安全架构

这是本架构的首要风险，不粉饰

平台要执行用户上传的任意代码，其中形态 ③（AI 编程工具 CLI）还会执行任意 shell 命令。这在安全上等价于「对内提供了一个可编程的远程执行服务」。所有隔离手段都是降低风险，没有一种能把风险降到零。下面写清楚每一层挡什么、挡不住什么。

11.1 威胁与缓解

威胁缓解手段残余风险
智能体读取其他试次的数据每试次独立容器与工作区；数据库凭证不进容器；对象存储不对容器开放低
智能体外连互联网（数据外泄 / 拉恶意载荷）出网默认 DROP，白名单仅两个地址低（依赖网络策略配置正确）
智能体盗用真实模型密钥真实密钥只在网关；容器只拿短时效受限凭证低
智能体耗尽资源影响其他试次CPU / 内存 / 磁盘硬限 + 硬超时 + 独立节点池中（磁盘 IO 争抢难完全隔离）
容器逃逸获取节点权限非 root、无 capabilities、只读根 FS、独立节点池、及时补丁中——0day 无法防住
worker 的 docker.sock 被利用（仅拓扑乙）worker 与执行节点同机隔离部署；socket 代理限制可调用的 API高——这是拓扑乙的主要短板
恶意制品上传静态检查 + 上传者实名 + 操作审计中（内部威胁模型下接受）
轨迹数据泄露敏感信息入库前脱敏规则；对象存储访问走签名 URL 且短时效中（脱敏规则覆盖不全）

11.2 密钥流转

密钥存放谁能读
DEEPSEEK_API_KEY密钥管理服务 / K8s Secret只有 gateway 进程
MySQL / Redis / 对象存储凭证同上api 与 worker，不进容器
试次临时凭证运行时签发，Redis 存吊销白名单容器（这是它唯一拿到的凭证）
JWT 签名密钥同上api 与 gateway
密钥纪律（沿用 PRD §5.5）

代码与文档中只出现环境变量名：DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL / DEEPSEEK_MODEL_FAST / DEEPSEEK_MODEL_PRO。CI 加 secret 扫描，命中即阻断。密钥一旦出现在聊天、工单、文档中，立即轮换。

11.3 权限模型

单一系统，权限全在中枢侧实现（PRD 原设计里这部分因 Langfuse oss 无项目级 RBAC 而放在中枢，结论不变，理由变了）。

13非功能设计

13.1 性能：时长预算怎么保证

三级门禁的时长是硬约束不是期望值（07 §2.2）。架构上分解到每个环节：

环节冒烟预算内的目标保证手段
容器冷启动< 3 秒预热池 + 镜像节点常驻 + 依赖层缓存
工作区解包< 5 秒zstd 压缩；大仓库用增量快照
智能体执行受 timeout_sec 约束硬超时杀进程
评分< 30 秒安全项前置短路；判官并发调用；结果缓存
聚合与门禁< 2 秒纯计算，无外部调用
整体≤ 5 分钟任务数 × k 与并发度自动匹配预算；超时中止返回 exit 3

13.2 并发与配额

项设计
全局并发试次默认 20，受 worker 副本数、执行节点资源、LLM 配额三重限制
LLM 限流Redis 令牌桶，按模型分桶——flash 与 pro 共用一把 key，不分桶强档会拖住快档批量判定
强档占比上限可配置，建议 ≤ 20%；超限告警，防止有人把所有 rubric 项改成 pro
单次运行成本上限可配置；预估超阈值需二次确认，实际超限中止并告警
门禁优先级冒烟 > 回归 > 能力集；预热池与配额优先给冒烟

13.3 判官成本控制

总调用次数 = 任务数 × k × j × LLM 类 rubric 项数，是乘出来的。25 任务、k=3、j=3、每任务 5 个 LLM 项 = 1125 次调用。架构上四个抓手：

  • 安全门控前置短路——安全项是确定性检查，不通过直接不调判官
  • 结果缓存——key = 产物 hash + 模板 hash + 模型名。模型名必须在 key 里，否则换档后命中旧结果
  • 按档位分别预估与统计——报告分列 flash / pro 的调用量与成本，让「谁把项改成了 pro」可见
  • Judge 项占比控制在 25–40%（03 分册要求），其余用确定性检查

13.4 可观测

指标为什么要盯
infra_error 率超 2% 说明环境有问题，此时的质量结论不可信
容器冷启动 P95直接决定冒烟能否守住 5 分钟
判官调用量与成本（分档）预算控制；异常暴涨通常是有人误配了 pro
队列积压深度积压说明并发配置与实际负载不匹配
网关错误率与上游 429模型配额是否吃紧
轨迹落库延迟OTLP 异步落库，延迟过高会导致报告里轨迹缺失

13.5 容灾与降级

故障降级策略
评测平台整体不可用CI 侧配超时，降级放行并告警——不能因为评测挂了卡住所有合入
DeepSeek 不可用判官项标记为「未判定」，只跑确定性项 + 安全门控，报告明确标注判官项缺失，门禁按确定性项结论走
对象存储不可用轨迹大载荷暂存本地磁盘队列，恢复后补传；结构化索引不受影响
执行节点不足试次排队而非失败；超时后按 infra_error 处理，不计入质量分
Redis 不可用队列不可用 → 新运行拒绝创建；已在跑的试次继续；这是可接受的短时停摆

一条原则：评测平台不是生产系统，可接受计划内停机；但它绝不能成为研发流程的单点阻塞。

三类评分器走统一接口。二期加多模态评判（看渲染结果）时，作为新的确定性检查器注册即可。

首期不做但要留位的：Mock 服务

支撑智能体不需要 Mock，但产品智能体（尤其工作流编排型）离不开。架构上，Mock 服务的位置与 LLM 网关对称——都是「容器唯一能访问的外部服务」。二期加它时，出网白名单从两个地址变成三个，其余不变。

15风险与取舍

风险影响对策
执行任意代码与 shell
首要风险		 容器逃逸可导致执行节点失陷 三层信任边界（§11）；执行节点独立池；非 root + 无 capabilities + 只读根 FS；接受 0day 残余风险，靠节点隔离限制爆炸半径
拓扑乙的 docker.sock 挂载 等价于宿主 root，是明确的提权路径 若最终无 K8s：worker 与执行节点独立机器；用 socket 代理限制可调用的 Docker API；这是拓扑乙的主要短板，选型时要知情
CLI 工具版本漂移 镜像重建导致工具升级，分数变了查不出原因 版本锁死并写入 agent_version；镜像升级必须先过预发；升级视为「换测量仪器」，需重跑基线
自研轨迹存储的容量失控 MySQL span 表膨胀导致慢查询 分层存储 + 90 天归档；监控行数与查询 P95；超 5000 万行触发列存评估（架构已留仓储抽象）
转录本查看器工作量被低估 首期延期 P0 功能（树 + 时间轴 + 对照 + 懒加载）先上；diff 视图、并排 diff、全文搜索排到 P1
判官成本失控 预算超支 分档预估 + 配额 + 前置短路 + 缓存；强档占比上限
单一模型供应商依赖 DeepSeek 不可用则判官全线停摆 ⚠️ flash + pro 两档不构成冗余——同供应商、同端点、同一把 key。网关预留第二供应商配置位；故障时降级为「只跑确定性项」
四形态并行支持导致复杂度膨胀 执行层难维护 四形态共用同一调度骨架，差异收敛在「运行时适配器」一层；新增形态只加适配器
评测集质量不够 平台建好了但结论不可信 平台不解决这个，02 分册解决。架构上强制：参考解满分校验、坏任务扫描、rubric 硬约束

15.1 明确接受的三个取舍

  1. 接受容器逃逸的残余风险。 替代方案（虚机级隔离、gVisor）成本远高于收益，且这是部门内网工具、上传者实名、有操作审计——威胁模型不是公网 SaaS。
  2. 接受 shell 审计可被绕过。 它是取证辅助不是安全边界。真正的边界是容器隔离与网络策略。
  3. 接受形态 ④（远程服务）的轨迹不完整。 它是兼容性选项，报告里标注「环境不可控」，不假装它和容器内执行等价。

16.3 工作量估算依据

  • 单位为人月，按一名熟练工程师全职一个月计
  • 后端按「数据模型 + API + 业务逻辑 + 单测」计入，不含需求澄清与评审
  • 前端按页面数 × 复杂度系数：列表页 0.15、编辑器 0.4、报告页 0.5、转录本查看器 1.5、标注台 0.5
  • 不确定度 ±30%，主要来自：容器编排环境未定、CLI 工具适配的未知问题、部门系统对接的配合成本
  • 未计入：容器平台的运维准备（假定运维承担）、部门账号体系对接的对方工作量
