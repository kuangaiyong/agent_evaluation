## 摘要

智能体 AI（Agentic AI）的最新进展，已将焦点从独立的大语言模型（LLM）转向将 LLM 与工具、记忆和其他智能体相结合、以完成复杂任务的集成系统。这些多智能体架构支持跨多样领域的协调推理、规划与执行，使智能体能够协作自动化复杂工作流。尽管取得这些进展，对 LLM 智能体及其构成的多智能体系统的评估与评定（assessment）仍是一个根本性挑战。尽管软件工程文献中已提出多种评估传统软件组件的方法，但现有的面向 AI 系统的方法往往忽视了模型的非确定性本质。这种非确定性在执行过程中引入行为不确定性，而现有评估依赖二元任务完成指标，无法捕捉它。因此，评估智能体系统需要考察额外维度，包括智能体调用工具的能力、摄入与检索记忆的能力、与其他智能体协作的能力，以及与环境有效交互的能力。

这些挑战浮现于我们与 MontyCloud Inc.（自主云运维 Autonomous CloudOps 领域的产业合作方）正在进行的行业合作中——当我们在生产环境部署一套智能体系统时，这些局限暴露出来，凸显了当前评估方法的实际缺口，以及超越任务结果对智能体行为进行系统化评估的必要性。基于这些观察以及智能体系统的既定定义，我们提出一个端到端的**智能体评估框架（Agent Assessment Framework）**，包含 LLM、记忆（Memory）、工具（Tools）和环境（Environment）四大评估支柱。我们在一个代表性的自主 CloudOps 用例上验证了该框架：实验揭示了传统指标所忽视的行为偏差，证明了该框架在捕捉运行时不确定性方面的有效性。

**关键词**：智能体 AI；评估（Assessment）；评价（Evaluation）；AI 使能系统；软件工程；CloudOps

## 1. 引言

过去几年 LLM 的演进，推动 AI 系统设计从独立、隔离的模型部署转向集成推理、规划与工具使用的智能体系统架构。尽管多智能体系统已有成熟基础，现代智能体系统通过记忆机制和环境交互扩展了这些原则，使其得以应用于软件工程、客户服务、自主运维等多样领域。这一演进要求评估机制从以模型为中心的指标转向系统级评估。多个组件的集成带来了传统评估方法未覆盖的重大挑战。评估智能体系统的首要挑战源于非确定性 AI 模型引入的内在不确定性：智能体系统在执行路径、工具选择和记忆检索模式上表现出波动性，使不确定性在系统中传播，影响工具调用的正确性、记忆操作的一致性以及多智能体交互的可靠性。

（原文图 1：智能体评估框架概览。）

当前关于智能体 AI 系统的研究主要集中在设计模式与架构框架上，对系统化评估方法论的关注有限。当我们在 MontyCloud 的 CloudOps 生产环境中测试一套智能体系统时，这一缺口变得显而易见：智能体虽然完成了任务，但对预期政策或验证流程的偏离未能被现有评估方法发现——因为它们只在运行时执行中显现，而不出现在静态验证阶段。

基于这些生产级洞察，我们设计了一个综合评估框架，围绕识别出的四大支柱评估智能体 AI 系统：LLM、记忆、工具和环境。这些支柱源自智能体的基本定义——一个配备推理组件（LLM）、记忆和工具以与其环境交互的实体。基于自适应系统的已有研究，我们同样将环境视为影响智能体行为的不确定性来源。该框架整合静态、动态与裁判（Judge）三种评估模式，以捕捉任务成功率之外的行为失败。表 1 概述了各支柱特有的不确定性及相应评估指标，它们构成了我们评估方法论的基础。

我们通过在此前开发的多智能体框架 MOYA 上的实验评估来验证该评估框架。结合 MontyCloud 的洞察，我们设计了三个源于生产的、复杂度各异的 CloudOps 场景，代表企业级云管理中遇到的真实运维挑战。结果表明：基线指标只报告任务完成，而我们的框架特定评估揭示了跨所有支柱的大量行为失败，在工具编排和记忆检索上尤为突出。

本文其余部分组织如下：第 2 节通过自主 CloudOps 实例说明评估的必要性；第 3 节介绍跨四大支柱的框架架构与评估组件；第 4 节详述实验设置与结果；第 5、6、7 节分别讨论对研究者与实践者的启示、相关工作与未来工作。我们的实验与结果已在 GitHub 开源。

## 2. 动机

CloudOps 通过自动化工作流管理和优化云基础设施。面对日益复杂的云环境，组织需要能够规模化执行多样运维任务的自主系统。MontyCloud 等 CloudOps 平台利用 AI 智能体自动化云管理任务，包括资源供给、合规执行和事件响应，体现了运维工作流对自主决策日益增长的依赖。传统评估框架大多聚焦任务结果与运营效率，忽视了运行时才显现的行为失败：智能体可能表面上表现良好，实则违反政策、在信息不足时决策、或跳过验证检查。评估行为可靠性，需要验证智能体在行动前是否查阅政策、是否执行诊断检查、是否检索相关上下文、是否以正确参数调用工具，以及是否尊重防止未授权操作的护栏。

由于智能体系统的本质，不确定性超出模型性能本身，横跨多个来源（如表 1 所示）。这些支柱捕捉智能体的推理、记忆、工具使用，并将环境纳入为运维不确定性的来源。**LLM 支柱**引入指令遵循和安全对齐上的失败；**记忆支柱**带来存储一致性与检索准确性的挑战；**工具支柱**在工具选择、参数映射和执行排序上出现失败；**环境支柱**代表智能体被评估时所处的运维上下文，通过结构化工作流、安全运行护栏以及支持可复现评估的可配置性来定义，并假定具备足够的可观测性以进行监控与分析。这些局限促使我们采用多层评估策略，从静态、动态和定性分析等互补维度考察智能体行为，实现行为可靠性的评估。以下各小节详述各支柱的框架组件与评估策略。

## 3. 智能体评估框架

原文图 1 和图 2 展示了所提出的跨四大支柱（LLM、记忆、工具、环境）评估智能体 AI 系统的框架。该框架执行三层分析：（i）**静态分析**——依据预定义的基准真值（ground-truth）规格验证智能体行为；（ii）**动态执行**——监控运行时行为以检测偏差与政策违规；（iii）**基于裁判的评估**——通过 LLM-as-a-Judge 或 Agent-as-a-Judge 协议对推理、安全与对齐进行定性评估。这三层共同建立了同时评估智能体系统确定性正确性与行为可靠性的综合流程。

（原文图 2：智能体评估框架详细视图。）

框架采用模块化结构：每个支柱定义自己的评估指标与评估焦点。静态与动态评估的结果被合并，用于衡量行为正确性与可靠性；定性评估则用于评估推理与对齐。该结构使框架能够跨多样运维上下文，提供细粒度与系统级两个层面的智能体性能洞察。

**测试用例生成**：为确保跨所有支柱的一致性，框架包含一个**测试用例生成器**组件，用于定义受控评估场景。每个测试用例指定上下文、期望行为以及从基准真值规格导出的成功标准，并按各支柱目标定制。例如：对 LLM 支柱，测试指令遵循与安全对齐；对记忆，测试检索准确性与上下文保持；对工具，测试正确的选择与参数映射；对环境，测试工作流执行与护栏合规。生成的测试用例贯穿静态验证、动态监控与裁判评估全过程，确保对智能体表现各维度进行系统化、可复现的评估。

### 3.1 记忆

智能体骨干 LLM 的一个根本局限是其上下文长度及其有效利用。缓解方式是为智能体提供记忆机制，使其能够存储和检索记忆。当前最先进的方法依赖提取实体间关系，并将其存入图或向量存储引擎。我们对该支柱的静态分析，针对黄金标准标签计算精确率、召回率、F1 和 BLEU-1，随后进行裁判评估。

**存储**：评估智能体结构化、更新和管理所存信息（事件、对话、上下文数据）的有效程度，以确保记忆检索高效准确。该评估关注这些记忆操作是否被正确、高效地执行，确保过时信息被替换而非重复。此外，该组件衡量**更新延迟**——新信息传播整个记忆层级并对所有智能体可见所需的时间。例如在 CloudOps 实践中，可能观察到同一资源的过时配置详情被保留，导致同一资源存在多个冲突条目。

**检索**：评估智能体从记忆系统（图或向量库、对话历史或外部知识源）中准确、高效召回相关信息的能力。该组件衡量召回准确性，即检索信息与预期查询的吻合程度。评估涵盖四类关键检索类型：**单跳（Single-hop）**——从单一上下文点回忆事实；**多跳（Multi-hop）**——跨多个相互关联的记忆实例检索；**时序推理（Temporal Reasoning）**——考察智能体对事件时序的理解；**开放域（Open-Domain）**——评估智能体将对话记忆与向量数据库、云文档等外部知识库结合的能力。有效检索确保智能体能综合多源上下文，给出一致且有上下文依据的响应。在 CloudOps 中，这可能涉及检索最近的系统配置更新，并将 WAFR 工作负载详情与云最佳实践指南对齐，以支持明智的运维决策。

### 3.2 工具

工具使智能体能够在真实或模拟环境中行动，定义其运维胜任力。在智能体框架内，工具可以是内部函数，也可以是通过模型上下文协议（MCP）等协议定义的外部组件。因此，评估工具本身的质量以及智能体正确使用工具的能力都至关重要——失败往往源于含糊的描述、错误的参数映射或不到位的错误消息。

**定量验证**：基于智能体的轨迹，可以提取其工具使用情况并与黄金标签比较，作为静态分析的一部分。可分为：

- **工具分类准确率**：衡量是否基于问题描述与可用工具目录为给定任务识别了正确的工具。误分类或错误排序可能导致调用不正确或无关的工具，损害任务可靠性。在 CloudOps 场景中，智能体可能因分类错误而选择审计（Audit）工具而非监控（Monitoring）工具。
- **参数准确率**：验证传递给工具的参数在语义与上下文上是否准确。例如在 CloudOps 中，智能体可能试图用区域名而非实例 ID 来扩容计算实例，导致错误的 API 调用或失败的动作。

**定性验证**：评估工具在真实或模拟执行中的行为，以及智能体对运行时条件的响应效果。工具在复制运维条件的沙箱环境中执行，以验证其能否成功完成。

- **错误消息评估**：当工具调用失败时，返回的错误应当可解释、描述充分，使 LLM 能理解原因并指导纠正动作。例如，当智能体因授权无效无法删除 EC2 实例时，不应只返回"操作失败"，而应给出描述性错误，如"删除 EC2 实例的 IAM 权限不足"，从而减少重复、无效的尝试。
- **性能**：基于延迟、成本和一致性比较功能等价的工具或端点。在 CloudOps 中，智能体可能需要在通过美西或美东服务器调用 API 之间选择；在不同工作负载下评估两条路径，有助于确定成本-性能权衡的最优路线。
- **可靠性**：追踪错误频率与恢复行为，评估工具是否执行一致并能从局部故障中优雅恢复。模块化工具往往更可靠，因为它们隔离故障、支持独立验证与故障恢复；相比之下，将多个操作合并的单一巨型工具定义会引入多个故障点。在 CloudOps 中，这可能表现为 API 调用间歇性失败或返回不一致的响应。

### 3.3 LLM

LLM 是智能体的核心部分，也是框架的核心。它深度集成在系统的各个层中，包括工具分类、从用户查询中拆分任务、作为裁判进行评估、错误处理等。这要求该组件跨多个方面接受测试。我们评估中的静态分析，会在动作执行前验证记忆查询中是否存在必需的关键词。如图 2 所示，对 LLM 支柱的其余评估大致可分为以下组件：

- **指令遵循**：评估 LLM 对预定义指令和基于规则的工作流的遵循准确程度，包括对系统提示和任务特定指令的遵守，如解析执行日志、分析工具调用序列与记忆查询、验证与预期流程和政策约束的对齐。评估通过所提出的指标进行：静态比较期望行为与实际行为；用 LLM-as-a-Judge 评估日志以检测尝试过的动作；以及动态生成测试用例，衡量智能体在变化条件下的指令遵循能力。在 CloudOps 上下文中，这可能表现为智能体在权限受限时仍试图删除 EC2 实例，或绕过工作流中的强制步骤。
- **安全与对齐**：评估智能体生成的动作或代码是否安全、合规并与预期目标对齐。当智能体可以执行或修改代码并与在线环境交互时，这一点尤其关键。评估框架分两阶段运行：静态分析在执行前检测潜在风险；动态分析通过裁判评估评定运行时行为，包括依据安全政策验证输出、标记违规、记录违规以供追溯。在 CloudOps 上下文中，这涉及智能体生成的部署命令包含不安全操作的场景，如修改生产配置或绕过审批检查。

**LLM-as-Judge**：使用结构化提示评估任务完成、安全、推理质量、记忆使用和政策正确性。裁判接收执行日志，产出带理由的评分评估，捕捉确定性指标之外的定性方面。

**Agent-as-Judge**：智能体通信协议的最新进展使我们可以通过 **Agent Card（智能体卡片）**进行能力发现：将卡片提供给审计智能体，由它基于卡片设计能力测试。审计智能体识别能力、发出测试指令，并通过环境检查工具（检查工具日志、记忆查询和状态变化）验证执行情况。

### 3.4 环境

智能体运行的环境可以是模拟的，也可以是真实世界的。真实世界环境可能提供更具代表性的条件，但其多变性往往降低可复现性。为执行以下评估，框架假定环境提供可观测性机制，以便在执行期间有效监控和分析智能体的内部状态、决策与交互。遥测、追踪、日志和控制流可见性等模块共同支持持续监控，并在故障条件下促进根因分析（RCA）。遥测模块通过在执行生命周期内跨多个 span 捕获追踪与元数据，在运行时评估智能体，通过使系统决策过程可解释来提升可解释性。监控有助于识别工作流执行期间环境内的变化——在 CloudOps 场景中，波动可能显著影响运营成本。Strands Agents 在智能体层面应用可观测性原则，而 CloudTrail 等云平台则提供系统级监控与运维审计。

随后在这一结构化设置中评估智能体行为：该设置支持受控执行、可重复实验，并能在不同运维条件下验证智能体的保真度。该环境的期望特性包括：

- **工作流**：环境包含支持系统化评估的预定义工作流或测试用例。这些工作流可与领域专家或系统干系人协商定义，以确保它们代表真实运维场景与政策约束；复杂度可从简单的单工具调用到涉及相互依赖工具与多样解法路径的多步链条不等。评估考察智能体是否保持预期的执行顺序、是否正确传递中间结果、是否妥善处理整个工作流中的失败或意外响应。在 CloudOps 中，测试用例可能包括带网络配置的 EC2 部署或带访问策略的 S3 桶设置等场景，评估验证智能体选择正确的 AWS API 并按预期顺序提供准确参数。
- **可配置性**：环境提供以最小代价配置、管理和重置评估设置的机制。运行多个测试用例时，应允许无需完全重启即可重置到已知状态。用户可以定义资源分配、成本上限等参数的上下界，并在变化的工作负载与故障注入场景下评估智能体表现。该能力支持细粒度实验与可复现性，使智能体能在多样约束与配置下被测试。在 CloudOps 中，这涉及在测试之间将环境重置到基线或中间状态、注入故障、设置成本或资源限制，无需在控制台手动清理即可实现系统化评估。
- **护栏与安全**：环境强制执行运维边界与访问控制，界定智能体运行的范围，确保智能体或工具只执行被允许的动作，防止其执行可能造成意外或有害后果的操作。这涉及执行治理智能体在系统内行为与交互的预定义权限与政策。在 CloudOps 中，除非获得明确授权或批准，智能体调用工具删除现有 EC2 实例的尝试必须被拒绝——通常通过 IAM 政策执行。此类限制应确定性地实现，或通过智能体内的逻辑约束，或通过基于角色的访问控制等系统级机制。定义这些护栏，可以系统化检测和分析智能体的规则或政策违规，并可使用 Arize Guards 等开源方案进行监控。

## 4. 实验与结果

我们在使用 MOYA 构建的自主 CloudOps 系统上通过实验评估我们的评估框架。基于第 2 节的动机，我们针对两个主要目标：跨四大支柱捕捉评估维度的有效性，以及成本与时间方面的效率。我们研究以下研究问题：

- **RQ1：与基线评估相比，所提框架在捕捉智能体评估维度方面有多有效？** 我们将四柱框架与只捕捉任务完成度和工具使用率的基线评估比较，衡量框架揭示传统方法所遗漏失败的能力。
- **RQ2：跨评估支柱的失败模式是什么？** 我们分析各支柱上失败的分布与频率，刻画智能体失败的类型。
- **RQ3：该框架在成本与时间上的效率如何？** 我们通过场景执行成本、token 消耗以及运行时执行与裁判评估协议的评估时间来量化计算开销。

### 4.1 实验设置

在实验设置上，我们扩展了 MOYA，以 Mem0 默认设置作为记忆支柱纳入记忆机制。基于此前关于不同 LLM 规则遵循能力的研究，我们选择 GPT-4o 模型进行实验，温度设为 0.7——该值经多次试运行选定，以平衡智能体响应的可预测性与创造性。我们使用 ChromaDB 存储由 text-embedding-3-small 模型生成的嵌入。基于我们在生产中遇到的问题，我们使用 Sonnet 4.5（因其在 LMArena 上的排名）生成了包含实例、日志和政策的合成数据，并将它们以可调用工具的形式暴露给智能体，使其能够检索和处理关于模拟云资源与运营规则的信息。我们定义了三个复杂度各异、代表真实世界 CloudOps 场景的工作流：

1. **成本优化（S1）**：成本优化智能体必须通过识别并终止利用率不足的 EC2 实例，将 AWS 基础设施成本降低 30%，同时遵守组织关于非生产环境优先、环境验证和 CAB（变更咨询委员会）批准的政策。测试智能体是否平衡成本削减目标与运维安全约束。
2. **安全事件响应（S2）**：安全修复智能体必须处置一个公开可访问、含敏感数据且已暴露 5 天的 S3 桶。智能体必须评估暴露范围、检查合规要求、在策略变更前启用日志，并在保持授权服务访问的同时应用修复。
3. **多智能体根因分析（RCA）（S3）**：诊断支付服务 60% 的响应时间退化——由 5 分钟前的网络误配置导致。需要性能、安全与 RCA 智能体之间协调，通过时序关联识别根因。测试系统是识别出配置问题，还是通过昂贵的扩容"治标不治本"。

每个场景独立执行三次，结果取平均以确保可靠性并抵消 LLM 行为的非确定性。我们使用 API key 运行这些实验，并报告 token 消耗与响应时间。

## 5. 讨论

我们与 MontyCloud 的合作提供了来自生产规模部署的持续反馈，使我们能够在真实运维条件下验证所提框架的实用性与效率。与基线的比较（RQ1）表明，传统方法会遗漏关键行为问题：例如 S1 工具排序完美但政策遵循仅 33%——在未查阅安全指南的情况下采取行动，这是基线指标无法检测的失败；S2 尽管任务完成，记忆召回率却很低（13.1%）。裁判协议揭示了额外失败：修复智能体在 20% 的测试中跳过验证步骤，而 LLM-as-Judge 给 S1 的总体分仅 72%。此外，在多智能体场景（S3）中，裁判方法有助于识别跨智能体传播的错误。这表明评估框架必须在最终结果之外，显式检查指令遵循、政策遵守与记忆使用。支柱消融研究（RQ2）揭示了评估工作应聚焦何处：工具编排在复杂场景中失败率最高，主要源于跳过诊断步骤；记忆失败随场景复杂度增加；环境违规只出现在生产状态被改变的多智能体场景中。这些模式表明，在多智能体场景中，工具排序与记忆管理需要特别关注。效率分析（RQ3）显示实际可行性：平均执行成本 0.0621 美元；LLM-as-Judge 增加的开销极小（0.0593 美元，14.7 秒），而 Agent-as-Judge 成本更高（0.9572 美元，913.4 秒）。这提示我们：LLM-as-Judge 适合持续监控，Agent-as-Judge 适合部署前审计。

**对研究者的启示**：现有方法聚焦以模型为中心的指标，而我们需要的是跨系统组件评估行为不确定性。RQ1 的结果显示智能体违反政策、遗漏重要上下文。这揭示了研究方向：多智能体场景中工具编排失败率高，说明需要更好的协调机制与形式化验证方法，以强制"先诊断后行动"。记忆中的精确率-召回率缺口表明需要平衡准确性与完整性——智能体检索的信息是正确的，但漏掉了决策相关的上下文。RQ3 讨论的裁判协议成本权衡，启发了一个研究方向：根据风险级别动态选择评估深度的自适应评估策略。此外，我们的场景在生成测试用例时需要人工指定期望行为，从智能体能力自动生成测试用例是一个有前景的方向。将我们的框架扩展到代码生成、多模态智能体等其他智能体范式，将验证并识别领域特定的评估需求。

**对实践者的启示**：现有方法主要按最终结果评估，这或许解释了原型到生产转化率低的原因——这些对标准指标不可见的失败会在生产中浮现。我们的结果显示智能体确实表现出这些失败：S3 跳过政策检查；S1 虽未能解决问题，但它在请求终止实例的许可时停了下来。这凸显了评估需要在结果测试之外进行行为测试。开发者应实现支柱特定检查（指令遵循、政策遵守），并在环境层实现防御性护栏（IAM 政策、控制政策）。评估时应使用 LLM 裁判与智能体裁判，在运行时揭示此类行为问题。埋点遥测——捕获工具调用、记忆检索与存储、政策检查——将为智能体失败时的提示优化与根因分析奠定基础。

### 5.1 效度威胁

**外部效度**：评估聚焦 CloudOps，对其他领域的泛化性有限；三个场景可能无法捕捉创造性任务或长时程规划中的挑战。为在一定程度上缓解，我们基于 CloudOps 经验设计了复杂度各异的场景。

**内部效度**：统一的温度（0.7）与模型选择（GPT-4o）可能无法捕捉完整的非确定行为分布；我们定义的基准真值契约可能未反映所有合法解法路径；裁判协议可能引入 LLM 评估偏差。

**构念效度**：指标可能未捕捉可靠性的所有方面；记忆评估未含存储效率与并发访问评估；由于采用文本仿真，环境检查未衡量可观测性质量或恢复机制。

## 6. 相关工作

关于智能体系统的研究凸显了记忆、任务遵循、安全、评估与多智能体协调等领域的持续挑战。在记忆领域，Maharana 等人表明 LLM 难以追踪长对话；RAG 方法改善了信息访问，但 Hu 等人指出其局限。总体而言，这些发现表明需要组合多种方法来评估记忆机制。在指令遵循方面，Qi 等人展示了评估对捕捉复杂指令（涉及多重约束，尤其涉及工具或条件时）表现的重要性。Dong 等人和 Andriushchenko 等人聚焦提升透明度、多智能体协调和对有害指令的鲁棒性。这些研究强调需要平衡推理、执行、安全与监控的评估框架。此外，Nascimento 等人关于自适应与多智能体系统的研究表明，记忆与决策中的不一致依然存在。Cemri 等人的研究《Why Do Multi-Agent LLM Systems Fail?》通过识别规格、对齐与验证中的缺口来分析多智能体系统失败。尽管有这些进展，大多数评估仍聚焦模型准确率或单个组件，运行时不确定性、工具使用、多智能体协调以及与动态环境的交互仍未被充分探索。据我们所知，目前尚不存在统一的智能体系统评估体系。为弥补这些局限，我们提出智能体评估框架，跨 LLM、记忆、工具、环境四大支柱评估智能体系统，并用 CloudOps 场景揭示浮现的失败，以捕捉智能体的整体行为。

## 7. 结论与未来工作

本文提出了跨四大支柱评估智能体 AI 系统的评估框架的第一步。通过自主 CloudOps 的工业案例，我们展示了该框架的有效性与效率。未来研究方向包括但不限于：（i）应用于 CloudOps 之外的多样领域；（ii）与自适应能力集成，支持智能体系统的持续改进；（iii）利用 Agent-as-Judge 发现失败模式并实现评估自动化。
