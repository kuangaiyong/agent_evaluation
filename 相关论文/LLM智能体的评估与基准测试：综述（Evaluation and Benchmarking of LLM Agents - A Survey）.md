## 摘要

基于 LLM 的智能体的兴起为 AI 应用开辟了新前沿，但如何评估这些智能体仍是一个复杂且欠发达的领域。本综述深入概览了 LLM 智能体评估这一新兴领域，提出了一个二维分类体系，沿两条轴线组织现有工作：（1）**评估目标**——评估什么，如智能体行为、能力、可靠性和安全性；（2）**评估过程**——如何评估，包括交互模式、数据集与基准、指标计算方法和工具。除分类体系外，我们还强调了当前研究中常被忽视的企业级特有挑战，如基于角色的数据访问、可靠性保障需求、动态长时程交互以及合规问题，并指出了未来研究方向，包括整体化、更真实、可扩展的评估。本工作旨在为碎片化的智能体评估领域带来清晰性，提供系统化评估框架，使研究者和实践者能够面向真实世界部署评估 LLM 智能体。

**关键词**：LLM 智能体；智能体评估；评估分类体系；智能体行为；基准测试；安全；企业级 AI

## 1. 引言

基于 LLM 的智能体是利用 LLM 进行推理、规划和行动的自主或半自主系统，代表了人工智能快速增长的前沿。从客服机器人、编码副驾到数字助手，LLM 智能体正在重新定义我们构建智能系统的方式。

随着这些智能体从研究原型走向真实世界应用，"如何严格评估它们"成为一个紧迫而复杂的问题。评估 LLM 智能体比单独评估 LLM 更复杂：LLM 主要按文本生成或问答能力评估，而 LLM 智能体在动态、交互式的环境中运行——它们推理和制定计划、执行工具、利用记忆，甚至与人类或其他智能体协作。这种复杂行为及对真实世界效果的依赖，使得标准的 LLM 评估方法不再够用。打个比方：LLM 评估像检验一台发动机的性能，而智能体评估则是综合检验一辆整车在各种驾驶条件下的表现。

LLM 智能体评估也不同于传统软件评估。软件测试关注确定性的静态行为，而 LLM 智能体本质上是概率性的、行为动态变化，因此需要新的性能评估方法。LLM 智能体评估处于自然语言处理（NLP）、人机交互（HCI）和软件工程的交叉点，需要额外的视角。

尽管该领域关注度日益增加，现有综述要么只关注 LLM 评估，要么只覆盖特定智能体能力，缺乏整体视角。此外，企业应用对智能体提出了额外要求——对数据和系统的安全访问、面向审计与合规的高度可靠性、更复杂的交互模式——这些在现有文献中很少被讨论。本综述旨在成为智能体评估领域从业者和研究者的有益参考。我们的贡献有二：

- 提出一个 LLM 智能体评估分类体系，按**评估目标**（评估什么：行为、能力、可靠性、安全）和**评估过程**（如何评估：交互模式、数据集与基准、指标计算方法、评估工具、评估环境）组织已有工作。
- 强调企业级特有挑战，包括基于角色的访问控制、可靠性保障、长时交互和合规要求。

本文其余部分组织如下：第 2 节描述本综述用于分析智能体评估格局的分类体系；第 3 节深入第一维度"评估目标"，聚焦被评估的智能体方面；第 4 节描述第二维度"评估过程"，聚焦评估方法；第 5 节讨论企业环境中评估 LLM 智能体的挑战；第 6 节概述开放问题和未来研究方向。

## 2. LLM 智能体评估分类体系

我们提出一个二维分类体系，沿**评估目标**（评估什么）与**评估过程**（如何评估）两条轴组织 LLM 智能体评估的不同方面。该体系在原文图 1 中以层次树形式可视化。

**评估目标**维度关注评估的标的。第一类**智能体行为（Agent Behavior）**聚焦面向结果的方面，如任务完成和输出质量，捕捉智能体满足终端用户期望的程度。其次，**智能体能力（Agent Capabilities）**强调面向过程的胜任力，包括工具使用、规划与推理、记忆与上下文保持、多智能体协作——这些能力帮助洞察智能体如何达成目标、满足设计规格的程度。**可靠性（Reliability）**评估智能体对相同输入是否行为一致，以及在输入变化或系统出错时是否稳健。最后，**安全与对齐（Safety and Alignment）**评估智能体的可信性与安全性，包括公平性、合规性，以及对有害或不道德行为的防范。

**评估过程**维度描述如何评估智能体。**交互模式**区分静态评估（智能体对固定输入作出响应）与交互式评估（智能体与用户互动）。**评估数据**讨论合成数据集与真实世界数据集，以及面向软件工程、医疗、金融等特定领域的基准。**指标计算方法**涵盖定量度量（如任务成功率、事实准确性）与基于人类或 LLM 判断的定性评估。**评估工具**指支撑性基础设施，如插桩框架（LangSmith、Arize AI 等）和公开排行榜（如 Holistic Evaluation of Agents），它们使可扩展、可复现的评估成为可能。最后，**评估环境**界定评估所处的环境，从受控仿真到网页浏览器或 API 等开放世界环境。

该分类体系既是概念框架，也是实用指南，能在广泛的目标、方法和部署条件下系统化比较和分析 LLM 智能体。以下各节逐一详细考察每个维度，突出关键评估实践与代表性研究。需指出，智能体在具体形态上差异很大——工具集成深度、自主性水平、多轮交互、多语言、多模态都日益重要；尽管本分类体系跨这些变化保持适用，但针对性的指标与评估策略常常是必需的，我们将在相关章节讨论这些具体适配。

## 3. 评估目标

### 3.1 智能体行为

智能体行为指用户感知到的智能体整体表现，将智能体视为黑盒。它代表评估中最高层的视角，最直接地反映用户体验。该类别涵盖任务完成、输出质量、延迟与成本等方面。

**3.1.1 任务完成**

任务完成是智能体评估的基本目标，评估智能体是否成功达成给定任务的预定义目标，涉及判断是否达到某个期望状态、或是否满足为任务成功定义的特定标准。尽管有人指出它在失败分析上提供的细粒度洞察有限（尤其当多数模型成功率都很低时），任务完成仍然是衡量智能体整体表现最主要、最必要的指标。

任务完成通常用**成功率（Success Rate, SR）**量化，也称**任务成功率**或**总体成功率**。其他相关指标包括**任务目标完成度（TGC）**和**通过率（Pass Rate）**。一些评估使用二元指示，例如对目标达成返回 0 或 1 的奖励函数。**pass@k** 与 **pass^k** 等指标则将其扩展到多试次情形。

这一关键目标被广泛应用于各类 LLM 智能体评估领域和基准：编码与软件工程任务，如修复 GitHub issue（SWE-bench）、科学数据分析编程（ScienceAgentBench）、复现研究（CORE-Bench、PaperBench）、应用内交互式编码（AppWorld）；也广泛用于与 Web 环境交互的智能体，包括通用网页导航（BrowserGym、WebArena、WebCanvas）、多模态网页任务（VisualWebArena、MMInA）以及耗时的真实网页任务（ASSISTANTBENCH）。

**3.1.2 输出质量**

输出质量指 LLM 智能体响应的特性，是一个涵盖准确性、相关性、清晰性、连贯性以及对智能体规格或任务要求遵循程度的总称。智能体可能完成了任务，但如果交互缺乏上述品质，用户体验仍然欠佳。输出质量在评估对话智能体时尤其重要，因为用户目标往往跨多轮达成。该类别的许多指标与 LLM 评估所用指标重叠，例如：流畅度指标衡量输出符合自然语言规范的程度；逻辑连贯性指标关注论证的严谨性。由于 LLM 智能体可能使用工具检索依据信息并给出上下文感知的文本回答，检索增强生成（RAG）系统的标准指标同样适用，如**响应相关性**或**事实正确性**。

**3.1.3 延迟与成本**

延迟是智能体行为的关键方面，尤其在用户与智能体同步交互的场景中。漫长的等待会显著损害用户体验并侵蚀对系统的信任。常用指标是**首 token 时间（TTFT）**，衡量流式模式下用户看到 LLM 响应第一个 token 之前的延迟。对于异步运行的用例，**端到端请求延迟**——收到完整响应的时间——通常更为相关。

成本虽不能被终端用户直接观察到，却在决定智能体能否规模化部署上起关键作用。我们将成本作为智能体货币效率的度量，通常基于输入与输出 token 数量估算——在大多数 LLM 部署中，token 数与按用量计费直接相关。

### 3.2 智能体能力

除外部行为外，评估还经常针对支撑 LLM 智能体表现的特定能力。该类别的关键方面包括工具使用、规划与推理、记忆与上下文保持、多智能体协作。评估这些能力有助于在更细粒度上确定智能体的强项与弱点。

**3.2.1 工具使用**

工具使用是 LLM 智能体的核心能力，使其能够检索依据信息、执行动作并与外部环境交互。本综述中，"工具使用"指单个工具的调用，与函数调用（function calling）同义；为复杂任务确定工具序列的更复杂情形将在 3.2.2 节讨论。最新进展使 ChatGPT-3.5 及之后的 LLM 原生支持函数调用：这些模型能自主决定是否调用函数、从候选集中选择合适的函数、并生成所需参数。因此，LLM 智能体可以直接构建在底层模型的函数能力之上，许多原本为 LLM 开发的评估技术也得以沿用。

工具使用评估需要回答几个关键问题：第一，智能体能否正确判断给定任务是否需要调用工具？若需要，能否从候选集中选出合适的工具？选定工具后，能否识别工具所需的正确参数，并为每个参数生成恰当的值以确保正确执行？当候选工具集很大时，智能体可能还需要基于任务的自然语言描述从工具库中检索正确的工具。

已提出的评估指标包括：**调用准确率（Invocation Accuracy）**——评估智能体对"是否该调用工具"的决策是否正确；**工具选择准确率**——衡量是否从选项列表中选中了正确的工具；**检索准确率**——关注系统能否从更大的工具集中检索到正确工具，常用 rank-k 准确率衡量。基于排序的评估中，**平均倒数排名（MRR）**量化正确工具在排序列表中的位置，**归一化折损累计增益（NDCG）**反映系统对所有相关工具的整体排序质量。

参数相关评估涉及两方面：**参数名 F1 分数**衡量智能体正确识别函数所需参数名并正确赋值的能力。一些评估依赖抽象语法树（AST）正确性来检查工具调用语法是否有效，但这种方法可能漏掉语义错误，如不正确或幻觉产生的参数值——对枚举类型受限的参数尤其如此。为弥补该局限，Gorilla 论文等近期工作提出基于执行的评估：实际运行工具调用并评估其结果，从而对工具使用能力提供更全面、更有依据的评估。

**3.2.2 规划与推理**

规划与推理是 LLM 智能体的 essential 能力，尤其在需要多步骤或不确定下决策的复杂任务中。规划涉及以恰当顺序选择正确的工具集；推理则使智能体能够预先或在任务执行中动态地作出上下文感知的决策。T-eval 将规划评估形式化为"预测工具集与参考工具集的比较"。由于工具顺序与依赖同样重要，一些基准采用图表示，并引入**节点 F1**（工具选择）与**边 F1** 或**归一化编辑距离**（工具调用序列与结构准确性）等指标。

在动态环境中，智能体常需交替进行规划与执行，随上下文演变调整动作——ReAct 范式即是典型，智能体在推理步骤与工具使用之间交替。评估这种自适应推理，仅比较静态计划是不够的，需要能反映实时决策的指标。T-Eval 框架为此引入推理指标，评估智能体每一步预测的下一工具调用与期望调用的吻合程度，捕捉其在工具输出事先未知时的决策能力。类似地，AgentBoard 提出**进度率（Progress Rate）**指标，将智能体的实际轨迹与期望轨迹比较，细粒度衡量智能体朝目标推进的有效程度。

当智能体被指示以"生成完整多步程序"的方式规划时，代码生成的评估方法同样相关。ScienceAgentBench 等基准用程序相似度指标比较生成的计划与标注的参考。此外，**步骤成功率（Step Success Rate）**被提出用于衡量生成计划中成功执行的步骤比例，从执行角度整体反映规划质量。

**3.2.3 记忆与上下文保持**

长时运行智能体的一项关键能力，是在大量交互中保持信息，并将先前的上下文应用于当前请求。Guan 等人按**记忆跨度**（信息存储多久）与**记忆形式**（信息如何表示）对多轮对话中的记忆评估进行分类。例如，LongEval 和 SocialBench 是测试智能体在长对话（40+ 轮）中上下文保持能力的基准：智能体读到跨越数十轮的对话，之后被问到需要回忆对话早期细节的问题。Maharana 等人展示了跨数百轮（600+ 轮）对话的评估；Li 等人引入记忆增强评估技术，追踪智能体在长时程任务中保持一致性的能力。这些评估常以合成或记录的对话为数据集，指标包括**事实回忆准确率**或**一致性分数**（轮与轮之间无矛盾）。记忆评估还可考虑工具使用智能体的工作记忆（即智能体是否追踪中间结果）与遗忘策略（即是否恰当地遗忘无关细节以避免混乱）。

**3.2.4 多智能体协作**

评估基于 LLM 的多智能体协作，需要不同于传统强化学习驱动的协调方法。传统智能体依赖预定义奖励结构，而 LLM 智能体通过自然语言、策略推理和去中心化问题求解进行协调。这些能力在金融决策、结构化数据分析等真实应用中至关重要——自主智能体必须高效地交换信息、协商并同步决策过程。Autonomous Agents for Collaborative Tasks 评估**协作效率（Collaborative Efficiency）**，衡量多个智能体动态分担责任与分配任务的能力。

### 3.3 可靠性

可靠性是至关重要的评估目标，尤其当 LLM 智能体被考虑用于企业和安全攸关应用时。它涵盖一致性、对变化的鲁棒性以及输出的可信性。任务性能（可能衡量的是最好情形下的能力）不同，可靠性评估探测的是最坏情形与平均情形。

**3.3.1 一致性**

一致性指同一任务重复多次时输出的稳定性。由于 LLM 本质上是非确定性的，基于 LLM 的智能体行为也存在波动性。要在企业或其他高风险应用中被信任，智能体必须在同一任务的重复运行中表现出一致的性能。这方面的常用指标是 pass@k——衡量智能体在 k 次尝试中至少成功一次的概率。但更严格的一致性度量是智能体在全部 k 次尝试中都成功，即 τ-benchmark 中形式化的 **pass^k** 指标，它更好地捕捉了关键任务部署的一致性要求。

**3.3.2 鲁棒性**

鲁棒性指智能体面对输入变化或环境改变时输出的稳定性。要保持有效和可信，LLM 智能体必须在一系列挑战性条件下持续提供高性能。鲁棒性评估常用扰动输入对智能体做压力测试——如改写指令、无关或误导性上下文、错别字和方言等语言变体——评估其是否仍能成功完成任务。例如，对标准提示施加系统性变换，衡量任务成功率或输出质量的下降幅度。HELM 基准明确纳入了此类测试，追踪模型性能在输入变化下的退化情况。

鲁棒性还涵盖自适应韧性——智能体从环境动态变化中恢复的能力。例如 WebLinX 考察网页结构在执行过程中发生变化时智能体的行为：有效的智能体必须调整策略，而不是停滞或失败。

对使用工具的智能体而言，鲁棒性进一步体现在错误处理能力上。如 ToolEmu 的评估所示，智能体必须能优雅地响应工具故障或意外输出。鲁棒性测试可包括故意注入故障——如 API 错误或空响应——观察智能体是恢复了（重试、切换工具、向用户解释问题）还是崩溃了。一个关键指标是被注入的故障中得到妥善处理的比例，反映智能体在不确定或不完美条件下的可靠程度。

### 3.4 安全与对齐

安全涵盖智能体对伦理准则的遵循、对有害行为的避免，以及对法律或政策约束的遵守。随着 LLM 智能体更强大、更自主，意外不良后果（如生成虚假信息、仇恨言论或不安全指令）的风险上升，使安全评估不可或缺。在金融服务、网络安全和自主决策等领域，智能体漏洞可能导致严重后果，这些评估尤为关键。

**3.4.1 公平性**

AI 智能体缺乏公平与透明，可能导致有偏见的结果、用户信任下降以及意外的社会后果。例如在金融应用中，贷款审批或投资策略中的偏见决策会强化系统性不平等（FinCon、AutoGuide）。多智能体交互中也出现伦理关切：决策框架必须确保符合标准与社会规范。

可解释性对增强用户信任至关重要，尤其在 AI 智能体提供推荐或自动化辅助的交互式系统中。指南驱动的决策（AutoGuide）与结构化透明机制（MATSA、FinCon）等方法为用户提供清晰的推理路径。R-Judge 则分析智能体在自主决策时如何感知风险，强调 AI 交互中的透明与可信。评估这些维度，确保 AI 智能体在运行环境中符合伦理标准并保持公平。

**3.4.2 伤害、毒性与偏见**

安全的一个方面是确保智能体输出不含仇恨言论、骚扰或极端偏见言论等有害内容。毒性评估常使用专门的测试集与指标，如 RealToxicityPrompts 数据集——一组可能诱发毒性内容的提示——其响应用自动毒性检测器或人工标注员检查。指标包括含毒性语言的响应百分比，或（分类器给出的）平均毒性分数。HELM 将毒性与偏见指标纳入整体评估，指示模型产生冒犯性内容或表现出不良偏见的频率。对交互式智能体，可用挑衅性或伦理挑战性的输入（红队测试）评估它，再衡量其失败率（以不安全方式响应的频率）。CoSafe 等安全数据集正是针对这一点：评估对话智能体面对旨在诱骗其违反安全规则的对抗性提示（如用户隐晦地请求自残建议或非法指令）时的表现。CoSafe 揭示即使先进的智能体也存在漏洞，例如会上"共指攻击"的当（用户含糊指称某物以绕过过滤器）。评估过程包括监控智能体面对对抗性查询时的响应是否违反政策。得到一个数值分数（如"智能体在 X% 的对抗案例中产生了违规响应"）便将安全量化。

**3.4.3 合规与隐私**

除避免明显的毒性外，许多部署要求智能体遵守特定的监管或政策约束。例如金融聊天机器人不得泄露机密信息或提供特定类型的金融建议；医疗助手不得偏离既定的医学指南。合规评估可能高度领域特定，涉及精心设计以测试智能体是否守住边界的场景（如用户向医疗机器人索要处方药推荐——正确、安全的行为是拒绝并建议咨询医生）。

在企业场景中，合规评估可能需要反映实际政策的专有测试用例。一种做法是将这些关切纳入评估框架：例如面向企业的 HELM 基准被提议纳入金融、法律等领域的领域特定提示与指标（如金融术语准确率、响应合规性）。该过程包括收集有代表性的企业场景（可能含机密或定制数据），并设计反映真实世界成功标准的评估指标（如：智能体在响应中是否遵守了所有法律免责声明要求？）。TheAgentCompany 则在结构化正确性约束下评估企业 AI 智能体，要求它们在完成任务时遵循预定义的组织政策。

## 4. 评估过程

### 4.1 交互模式

对 LLM 智能体的评估可以在多种交互模式、配合不同工具下进行。一个根本区分是**离线评估**（使用预先生成的静态数据集）与**在线评估**（涉及反应式仿真、人在回路或在线系统监控）。

**4.1.1 静态与离线评估**

离线评估常作为基线进行，通常依赖数据集与静态测试用例：代表智能体可能面临的挑战的任务、提示或对话集合。模拟对话可用于帮助构建这些数据，但它们在不同运行之间是惰性的。尽管运行和维护相对便宜简单，离线评估通常缺乏细腻度，无法充分覆盖 LLM 智能体可能或期望给出的广泛响应。因此，它们更容易受错误传播影响，对系统表现的代表性通常较差。

**4.1.2 动态与在线评估**

与其他 ML 系统一样，在线评估常发生在 LLM 智能体部署之后。在线评估不依赖合成、历史或手工制作的数据，而是利用仿真或真实用户交互。这种自适应数据对于发现静态测试中未发现的痛点与问题至关重要，且通常富含合成或通用基准难以捕捉的领域上下文。动态评估可以使用代理来**模拟用户或环境**，对智能体行为作出反应式的实时响应。例如在 Web 智能体评估中，研究者构建了网页模拟器（MiniWoB、WebShop、WebArena 等），智能体的行为（点击链接、填写表单）可以被编程验证其顺序是否正确。

**评估驱动开发（Evaluation-driven Development, EDD）**的概念也被提出，主张让评估成为智能体开发周期的内在组成部分：持续评估智能体——离线（开发中）与在线（部署后）并举——以检测回归并适应新用例。其进一步给出了一种参考架构：由 AgentOps 组件监控生产中的智能体表现，并将洞察反馈给开发者。这虽仍是新兴理念，但它强调评估不是一次性任务，而是一个持续的过程——对会学习或演化的智能体尤其如此。

### 4.2 评估数据

对 LLM 智能体评估日益增长的兴趣，催生了专门针对第 3 节所述智能体能力的多样化数据集、基准与排行榜。许多资源旨在反映真实世界的复杂性，混合使用人工标注、合成与交互生成的数据构建。例如，AAAR-1.0、ScienceAgentBench 和 TaskBench 等数据集为研究推理、科学工作流和多工具规划提供结构化的专家标注基准；FlowBench、ToolBench 和 API-Bank 等则聚焦大规模 API 库上的工具使用与函数调用。这些基准通常不仅包含黄金工具序列，还包含期望的参数结构，从而支持细粒度评估。

与此同时，AssistantBench、AppWorld 和 WebArena 等数据集在网页与应用环境中模拟更开放式、交互式的智能体行为，强调动态决策、长时程规划以及用户-智能体交互。若干基准还支持安全与鲁棒性测试——如 AgentHarm 评估潜在有害行为，AgentDojo 评估对提示注入攻击的韧性。伯克利函数调用排行榜（BFCL）与 Holistic Agent Leaderboard 等排行榜则通过提供标准化测试用例、自动化指标（如 AST 正确性、胜率）和排名机制，将这些评估整合起来以比较各系统。

### 4.3 指标计算方法

**基于代码的方法**是最确定、最客观的途径。它依赖显式规则、测试用例或断言来验证智能体响应是否满足预定义标准，特别适用于输出定义良好的任务，如数值计算、结构化查询生成或编程任务的语法正确性。其主要优势是一致性与可复现性，对基准测试高度可靠。但基于代码的方法通常不够灵活，难以评估开放式或定性响应（如自然语言生成、创造性问题求解）——这类场景的正确性是主观的。尽管如此，对于正确性定义良好的结构化任务，它仍是基础技术。

**LLM-as-a-Judge（LLM 作为裁判）**方法利用 LLM 的推理能力，按指令给定的定性标准评估智能体响应。该方法因能处理主观、细腻的任务（如摘要、推理、对话交互）而流行起来。其近期扩展是 **Agent-as-a-Judge**：评估过程由多个 AI 智能体交互来精炼评定，可能提高评估可靠性。该方法高度可扩展、能适应复杂任务，因此受到越来越多关注。

**人在回路评估**仍是主观方面（如自然度、用户满意度）和安全攸关判断的黄金标准。人工评估可以采取用户研究、专家审计（领域专家评审智能体输出）或众包标注（按相关性、正确性、语气等维度给输出打分）等形式。该方法在开放式任务（如内容生成、战略决策、对话连贯性）中提供最高可靠性，但昂贵、耗时、难以扩展，对需要频繁评估的大规模自动化系统并不实际。

### 4.4 评估工具

过程维度中一个值得注意的方面，是支持自动化、可扩展、持续性智能体评估工作流的软件框架与平台的出现。这些工具使评估直接集成进开发生命周期，反映了智能体构建中评估驱动开发（EDD）的兴起。OpenAI Evals 是一个开源框架，允许开发者为模型指定评估任务与指标，自动执行并报告结果（虽未见于学术文献，但反映了实际需求）。DeepEval、InspectAI、Phoenix、GALILEO 等其他开源或商业工具提供丰富的分析、评估编排与调试能力。此外，Azure AI Foundry、Google Vortex AI、LangGraph、Amazon Bedrock 等智能体开发平台也越来越多地集成评估功能，帮助开发者监控性能、检测回归、使智能体适应不断变化的用户需求。Xia 等人进一步提出 AgentOps 架构，持续监控已部署的智能体，通过实时反馈与质量控制闭合开发与部署之间的环路。

### 4.5 评估环境

评估环境指评估执行所处的环境。与软件工程类似，这里存在一个权衡：更真实（但往往更昂贵、可能更不安全）的环境，与更简单、更可控（但通常对最终性能代表性较差）的环境。系统评估所处的环境通常取决于系统的预期用途：没有编辑权限的简单 LLM 智能体可直接在其工作环境中测试；而要与众多的相互交织的系统协作并作出修改的 LLM 智能体，则更可能在 mock API 或沙箱环境中评估。对不那么受控的系统，评估环境可采用网页模拟器形式，如 MiniWoB、WebShop 或 WebArena。随着智能体开发的推进，评估环境也常随之演进——从较小的 mock API 环境到实时部署——智能体的性能与可信性在这一过程中被逐步确定。

## 5. 企业级特有挑战

随着基于 LLM 的智能体从研究演示走向企业部署，新的挑战正在浮现。企业通常要求高性能的同时具备可预测的可靠性、法规合规、数据安全与可维护性，而这些在评估中常被忽视。为弥补这些缺口，我们讨论以下关切并概述未来方向。

### 5.1 基于角色访问带来的复杂性

在企业环境中评估 LLM 智能体的一个关键挑战，是需要考虑基于角色的访问控制（RBAC）——它管理用户访问数据与服务的权限。在这类环境中，用户依角色拥有不同级别的访问权限，代表用户行动的智能体必须遵守同样的约束。这给智能体评估带来复杂性：智能体检索信息或对其采取行动的能力不是均一的，而是上下文地绑定于用户权限。

为应对这一点，一些评估框架已开始将访问控制约束纳入设计。例如 IntellAgent 包含要求验证用户身份的评估任务，并执行拒绝访问其他用户信息的策略。通过将角色特定的限制嵌入任务生成，这些方法更准确地建模了智能体在权限敏感的企业上下文中的行为。

### 5.2 可靠性保障

可靠性保障在企业环境中尤为重要——智能体被期望在合规与审计框架内运行，这些框架要求确定性或可重复的、可解释的行为。在此类场景中，偶尔的成功是不够的：智能体必须跨时间与使用场景可靠地执行，才谈得上生产就绪。

评估可靠性并非易事。由于 LLM 智能体本质上是随机的，衡量一致性需要多次执行同一任务并观察结果的变化。这带来显著的评估开销：每个输入运行多个试次在计算上很昂贵，测试涉及工具、记忆或多智能体协调的复杂任务时尤其如此。此外，要得出有意义的结论，基准必须包含能反映智能体可能遇到的任务类型与条件的代表性数据集。

一些工作已开始应对该挑战。例如 τ-benchmark 明确纳入 pass^k 指标来评估智能体一致性；将其应用于零售与机票预订领域后，作者表明当前智能体在一致性上表现挣扎。

### 5.3 动态与长时程交互

评估 LLM 智能体的一个主要挑战，是评估它们在动态演变环境中的长时程任务上的表现。与大多数聚焦短片段或单次交互的现有基准不同，真实世界的企业智能体常常在与用户、系统和数据交互的同时连续运行很长时间。

应对这一挑战，对于理解智能体随时间的行为至关重要——在企业环境中，可靠性、适应性与目标对齐在智能体整个生命周期中都至关重要。标准的短期评估无法捕捉性能漂移、上下文保持或决策对业务结果的累积效应等现象。

为着手解决该问题，一些研究引入长时仿真与扩展对话作为评估工具。例如 Park 等人在持续运行的小镇的模拟环境中观察生成式智能体，研究跨多日交互的涌现行为；Maharana 等人则通过 600 轮对话评估长期对话记忆，聚焦智能体在长对话中维持连贯与上下文的能力。

### 5.4 对领域特定政策与合规要求的遵循

评估企业智能体的另一重大挑战，是确保它们能在领域特定政策与合规约束内运行。企业常执行严格的运营规则——如审批工作流、数据保留政策、使用配额，以及 GDPR、HIPAA 等法律法规——智能体在任务执行全过程中都必须遵守。在这类上下文中评估智能体，仅衡量任务成功是不够的，还需验证智能体行为是否符合正式的政策约束与法律合规标准。例如，生成财务报告的智能体必须避免未经授权访问机密预测，并确保生成内容符合监管报告标准。如果在评估中不显式建模这些约束，在传统基准中被判为"正确"的智能体，仍可能因违反政策或合规风险而在生产中失败。

## 6. 未来研究方向

随着基于 LLM 的智能体在复杂性与应用范围上持续增长，未来研究必须走向更稳健、更实用、更可扩展的评估方法论。我们强调四个能显著推动该领域的方向：

- **整体化评估框架**：当前评估工作常聚焦孤立维度，如任务成功、规划质量或工具使用。但真实应用中的智能体必须同时平衡多种胜任力。未来工作应开发能跨多个相互依赖的维度评估智能体表现的整体化评估框架。
- **更真实的评估环境**：为弥合实验室环境与生产环境之间的鸿沟，智能体评估必须走向更真实的条件，包括构建纳入企业特定要素的评估环境，如动态多用户交互、基于角色的访问控制和领域特定知识。这些环境可通过真实世界部署试验，或通过模仿企业工作流的仿真环境来实现。
- **自动化与可扩展的评估技术**：手动评估智能体行为——尤其在多轮或长时程场景中——成本高昂且难以规模化。未来研究应探索自动化评估方法，以减少人力并提高可复现性，包括用合成数据生成可控测试用例、利用仿真环境模拟任务上下文，以及推进 LLM-as-a-judge、Agent-as-a-judge 等基于 LLM 的评估技术。
- **时间与成本受限的评估协议**：评估必须高效，能支持智能体的迭代开发。今天的方法——尤其需要重复试次或人在回路评估的——可能非常耗时耗资源。未来研究应致力于开发时间与成本受限的评估协议，在深度与效率之间取得平衡。

总之，未来研究应聚焦开发整体化、真实、可扩展且高效的评估方法。这些方向对于规模化构建可靠、可信的 LLM 智能体至关重要。
