## Why

`docs/prototype.html` 的 14 屏原型已定稿并合入 main，但当前前端实现与它存在结构性偏差：菜单的一级/二级包含关系对不上、接入中心的口径整个换了一套（LoongSuite 三通道 vs 旧的 AgentScope/OpenCode/HTTP）、多张表缺列、系统管理多了一个本应独立的页签。这些偏差不是细节打磨的问题——**菜单结构和接入口径决定了用户怎么理解这个平台**，越晚对齐，返工面越大。

一期以原型为准把基础模块拉齐，建立一条可验收的基线：此后任何界面改动都先改原型、再改代码。

## What Changes

范围为 11 个二级菜单。**成本与配额、通知中心不在一期**（成本与配额的后端 `services/budget.py` 已实现，仅缺前端出口，推后不阻塞）。

### 菜单结构（一级 / 二级包含关系）

一期目标结构，与原型一致：

| 一级 | 二级 |
|---|---|
| 总览 | 仪表盘 |
| 观测与审计 | 接入中心 · AI Agent 可观测 |
| 评估与实验 | 指标库 · 评估器 · 评估任务 · Bad Case 管理 |
| 数据中心 | 轨迹库 / 数据集 |
| 持续优化 | 实验与回归 |
| 系统管理 | 成员与权限 · 操作审计 |

对当前实现的三处改动：

- **数据中心从两个二级菜单合并为一个**。现在是「轨迹库」「数据集」两项指向 `/datacenter?tab=` 的不同 tab，改为单项「轨迹库 / 数据集」，页内 tab 切换。
- **操作审计从「系统管理」的第三个页签提为独立二级菜单**，路由 `/audit`。API `/api/system/audits` 已存在，只需建页面并改导航。
- **总览下的「通知中心」一期不动**，保持现状。

> 记录一处假设：原型把操作审计放在「成本与治理」分组下，与「成本与配额」并列。由于成本与配额不在一期，一个只含审计的「成本与治理」分组会让人误解，故一期把操作审计挂在「系统管理」下。待成本与配额落地时再评估是否单立分组。

### 各屏与原型的差异（以原型为准）

- **接入中心**：接入指引页签从「AgentScope / OpenCode / HTTP API 直推」改为 LoongSuite 三通道——① Python Agent（AgentScope 等应用内）② Pilot（OpenCode / Hermes 等本地 Coding CLI）③ OTLP 直推（CodeBuddy 及兜底）。应用列表新增「智能体类型」「接入通道」两列。
- **评估任务**：页签顺序改为「离线任务」在前、「在线任务」在后；离线任务表新增「数据集」列。
- **Bad Case 管理**：列表新增「触发评估器」「Root Cause」两列。
- **数据中心**：数据集页签的表新增「类型」「版本」「条目数」「已配金标准」列；轨迹库行提供「转为评测任务」入口。
- **系统管理**：移除「审计日志」页签（提为独立菜单）；成员表新增「来源」「可做什么」「加入时间」列；工作空间表新增「日额度」「我的角色」列。
- **实验与回归**：对比报告表新增「主要退化原因」列。
- **操作审计**（新页面）：操作人 / 操作 / 对象 / 结果 / 时间五列，改评分器 rubric、改金标准、重跑任务三类标记为高风险，支持按操作人筛选与「仅高风险」开关。
- **仪表盘 / AI Agent 可观测 / 指标库 / 评估器**：结构已与原型一致，本期只做交互与字段口径核对，不做结构性改动。

### 全局交互基线

原型已确立的交互约定，一期在真实页面上落地：所有主操作按钮有响应（弹窗或反馈）、表格行可下钻详情、筛选控件真实过滤并联动命中计数与空态、关键列可排序、写操作对只读角色置灰。

**不改动**：后端数据模型与既有 API 契约。一期是前端对齐 + 补一个已有 API 的页面出口。

## Capabilities

### New Capabilities

- `navigation`: 一级/二级菜单的包含关系、路由映射、当前项高亮与下钻页的归属高亮、按角色的写操作置灰
- `dashboard`: 核心质量指标卡、趋势与排行、告警区，以及数据范围切换
- `agent-access`: 三条 LoongSuite 接入通道的指引与应用接入管理（注册、Key、连通性、状态）
- `agent-observability`: Trace / Session 列表查询与轨迹详情下钻（轨迹树、评估结果、打分公式还原）
- `metric-dictionary`: 92 项指标的只读字典、「层 × 柱」覆盖度视图与评估器挂靠关系
- `evaluators`: 评估器的类型体系、版本与发布状态、质量门禁（L-01 / L-02）呈现
- `eval-tasks`: 离线批量评估任务的创建、状态机与结果查看，在线任务作为次要页签保留
- `bad-case-review`: 低分 Case 的人工复核、Root Cause 标注、失败模式聚类与批量操作
- `data-center`: 轨迹库与数据集的统一入口、数据集版本与金标准完成度、轨迹转评测任务
- `regression-gate`: 版本对比实验、退化清单与 CI 门禁结论
- `system-management`: 工作空间隔离、三级角色 RBAC 与成员管理
- `operation-audit`: 平台自身关键操作的只追加留痕、高风险操作标记与判定依据的长期保留

### Modified Capabilities

无。`openspec/specs/` 当前为空，本次是首批能力定义。

## Impact

**前端**（主要工作面）
- `frontend/src/layout/MainLayout.vue`：导航分组与二级菜单调整
- `frontend/src/router.js`：新增 `/audit` 路由；`/datacenter` 保留单入口
- 新增 `frontend/src/pages/Audit.vue`
- 修改 `Access.vue`、`Tasks.vue`、`BadCases.vue`、`Datacenter.vue`、`System.vue`、`Regression.vue`
- 核对 `Dashboard.vue`、`Traces.vue`、`TraceDetail.vue`、`Metrics.vue`、`Evaluators.vue`

**后端**（改动很小）
- `/api/system/audits` 已存在，需确认是否支持按操作人筛选与高风险标记；缺则补查询参数
- 应用列表需返回「智能体类型」「接入通道」字段，`models.App.type` 已有，接入通道需新增字段或由 type 推导
- 其余接口现状足够，不改契约

**不受影响**：数据模型（除 App 可能加一个字段）、OTLP 摄入链路、评估执行引擎、Kafka / ClickHouse 相关代码。

**验收依据**：`docs/prototype.html` 为界面事实来源；`docs/prototype.smoke.js` 的交互约定作为真实页面的交互验收参考。
