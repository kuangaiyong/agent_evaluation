## Context

见 `proposal.md - Why`。这里只记与实现路径相关的现状与约束。

现有工程是 FastAPI + Vue3（Element Plus）+ Kafka + ClickHouse，16 个前端页面、14 个后端 router 均已可运行，后端测试 42 项通过。也就是说，这不是从零搭建，而是**在一个跑得起来的系统上做结构对齐**——绝大多数后端 API 已具备，缺口集中在前端。

三条约束决定了实现方式：

1. **`docs/prototype.html` 是界面事实来源。** 它已合入 main，14 屏可点，交互由 `docs/prototype.smoke.js` 的 28 项断言约束。字段名、表格列、页签口径以它为准。
2. **一期不动数据契约。** 除应用可能新增一个字段外，不改数据模型与既有 API 的请求/响应形状。这是为了让前端对齐可以独立推进、独立回滚。
3. **只有一个人开发。** 因此优先复用已有 API，避免同时改前后端；能靠前端解决的不动后端。

## Goals / Non-Goals

**Goals**

- 前端菜单结构、页签口径、表格列与原型一致，且这种一致性可被自动校验，而不是靠人对着截图比
- 为 11 项能力建立首批 spec，此后界面改动先改原型与 spec、再改代码
- 每个模块的写操作对只读角色一致地置灰

**Non-Goals**

- 不做视觉重绘。现有 Element Plus 观感保留，只调结构与字段
- 不引入前端状态管理库或组件库替换
- 不做响应式适配的深度优化（现有断点保持）
- 不在本期建立前端自动化测试体系。原型的 smoke 测试作为交互验收参考，但不要求为每个 Vue 页面补等价测试——这是二期的事

## Decisions

### D1：以原型为验收基线，并把「一致性」变成可执行的检查

**决定**：写一个对比脚本，从 `docs/prototype.html` 与 `frontend/src/` 两侧各自抽取导航结构、页签清单、表格列名，逐项比对并输出差异；差异清零即视为对齐。

**为什么**：人工对照截图不可重复，而且这次差异（页签顺序反了、少两列）恰恰是肉眼最容易放过的类型。把它变成脚本，返工时能立刻知道有没有改全。

**取舍**：脚本靠正则从 `.vue` 抽 `el-table-column` 的 `label` 与 `el-tab-pane` 的 `label`，对动态生成的列会漏。可接受——本期涉及的列都是静态声明的；漏检时以原型为准人工补。

**备选**：为每个页面写 Vitest 组件测试断言列名。更准，但要引入测试框架与配置，对一个人的投入产出比不划算，推到二期。

### D2：接入通道改为按形态划分，通道信息存在后端

**决定**：应用实体新增 `channel` 字段，取值为三条通道之一；`models.App.type` 保留为智能体类型（AgentScope / OpenCode / Hermes Agent / CodeBuddy / 其他）。前端列表新增「智能体类型」「接入通道」两列。

**为什么**：旧划分按产品名（AgentScope / OpenCode / HTTP API），新工具进来无处归类——CodeBuddy 就是例子。按形态划分后，任何新工具都能归到三条之一。

**取舍**：新增字段意味着要动数据模型，与「一期不动数据契约」有张力。折中：`channel` 可空，存量数据按 `type` 推导出默认值，读接口保证总能返回该字段。这样迁移不阻塞，前端也不必处理缺失。

**备选**：完全由 `type` 前端推导，不加字段。但推导规则会散在前端，且新增工具时要改前端代码——把规则留在数据里更合适。

### D3：操作审计复用既有 API，只建页面

**决定**：新建 `Audit.vue`，调用已有的 `/api/system/audits`；从 `System.vue` 移除审计日志页签。若该接口不支持按操作人筛选与高风险标记，则补查询参数与一个派生字段，不改响应结构。

**为什么**：这是本期投入产出比最高的一项——能力已经在后端跑着，只是没有出口。

**高风险的判定放在哪**：放服务端。三类高风险操作（改评分器 rubric、改金标准、重跑任务）由 `action` 字段判定，规则写在服务端并随响应返回布尔标记。放前端会导致规则散落，且换个客户端就失效。

### D4：数据中心合并菜单，路由收敛为单入口

**决定**：导航只保留 `/datacenter` 一项，页内 tab 切换；移除 `?tab=traj` / `?tab=ds` 两个菜单入口。页内 tab 状态可继续用 query 参数以支持刷新保持与分享链接。

**为什么**：两个菜单指向同一路由的不同 query，在导航高亮逻辑里需要特判（现有代码里就有一处 `if (p.includes('datacenter'))` 的特判）。合并后高亮规则统一。

### D5：一期把操作审计挂在「系统管理」下

**决定**：不新建「成本与治理」一级分组，操作审计作为「系统管理」的第二个二级菜单。

**为什么**：原型把它与「成本与配额」并列在「成本与治理」下，但成本与配额不在一期。一个只含审计的「成本与治理」分组会让用户以为这里有成本功能。

**取舍**：与原型的分组归属不一致，属于本期已知且刻意的偏差，记录在案。待成本与配额落地时再评估是否单立分组并迁移——迁移成本是改一行导航配置。

### D6：写操作置灰统一由一处判定

**决定**：各页面统一以「当前用户在本空间的角色」计算一个 `canWrite`，写操作控件绑定它。管理员专属操作（成员管理、配额调整）另用 `canAdmin`。

**为什么**：现有页面里 `canWrite` 的计算已在多处重复出现。本期涉及 6 个页面改动，若继续各写各的，角色规则一旦调整就要改 6 处。

**范围克制**：只做取值来源的统一，不引入权限指令或高阶组件——那是超出本期需要的抽象。

## Risks / Trade-offs

- **对比脚本给出假阴性**（动态生成的列抽不到，误报为「已对齐」）→ 脚本只作辅助，每个模块改完仍需对照原型该屏人工过一遍；把已知的抽取局限写进脚本注释。
- **App 新增 `channel` 字段触及数据模型**，与「不动数据契约」的承诺有张力 → 字段可空且读接口保证有默认值；变更集中在一次迁移里完成，不分散到各任务。
- **移除「审计日志」页签会让习惯旧位置的用户找不到** → 一期用户量小，通过发布说明告知；若确有需要，可在系统管理页保留一个跳转链接。
- **原型与真实页面会二次漂移**：原型是静态 HTML，真实页面接真数据，两者不可能永远一致 → 明确边界：原型定「结构与字段口径」，真实页面定「数据与状态」。对比脚本只校验前者。
- **一期不补前端测试**，界面回归只能靠人工 → 已知负债，记录在二期。后端 42 项测试仍是硬门槛，不因前端改动而放松。

## Migration Plan

1. **后端先行**：App 增 `channel` 字段（可空 + 由 `type` 推导默认值），审计接口补筛选参数与高风险标记。后端测试保持全绿。
2. **导航结构调整**：改 `MainLayout.vue` 与 `router.js`，新增 `/audit` 路由。此步独立可验证——菜单结构对了，各页内容尚未改也不影响可用性。
3. **逐页对齐**：按 `tasks.md` 的顺序改页面。每页改完跑一次对比脚本，确认该页差异清零。
4. **整体验收**：对比脚本全绿 + 后端测试全绿 + 逐页对照原型人工过一遍。

**回滚**：前端改动按页面粒度提交，任一页出问题可单独回退。后端的 `channel` 字段可空，回滚前端不影响后端。

## 已核实的前提

写任务清单前核过代码，两处原本待定的地方已有确定答案：

- **审计接口需要补参数。** `/api/system/audits` 当前只接受 `limit`，既没有按操作人筛选，也没有高风险标记；`AuditLog` 模型有 `actor` / `action` / `obj` / `result` / `ip` / `created_at` 六个字段，够用。因此需要补 `actor` 查询参数与一个由 `action` 派生的 `high_risk` 布尔字段，不改现有响应中的既有键。
- **接入通道的推导规则是确定的。** 存量 `App.type` 只有 `AgentScope` 与 `OpenCode` 两种取值，映射为 `AgentScope → 通道①`、`OpenCode → 通道②`、其余 → 通道③，覆盖完整，无歧义。
