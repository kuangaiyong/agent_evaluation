# TAgentEval 实施排期

> 约束：**一个人 + AI 辅助开发**、面向团队内部 **1000 人**、**本地部署**。
> 范围：原型 20 个导航屏 + 1 个下钻屏，**全部要做，只分先后**。
> 配套：[技术栈选型.md](技术栈选型.md) · [整体技术方案.md](整体技术方案.md) · 界面口径以 [prototype.html](prototype.html) 为准。

## 0. 排期依据

不按工作量排，按**「缺了它平台就不成立」的程度**排，再用现有代码复用度做二次排序。

现有资产盘点【实测】：后端 **14 个 router / 54 个接口**，前端 **16 个页面 / 1805 行**。

| | 屏数 | 说明 |
|---|---|---|
| 有基础可改造 | **14** | 后端接口或前端页面已存在，本次是补齐与对齐原型 |
| 完全全新 | **7** | quickstart · boards · insight · pipeline · assets · memory · risk |

## 1. 排期总览

| 期 | 主题 | 屏数 | 估算 | 做完能干什么 |
|---|---|---|---|---|
| **一期** | 评测闭环跑通 | 7 | ~32 人日 | 接入一个真实 Agent，跑完一次评估，拿到三口径结果 |
| **二期** | 数据飞轮与约束力 | 5 | ~20 人日 | 低分样本沉淀为回归集，版本对比出门禁结论并阻断 CI |
| **三期** | 1000 人规模治理 | 5 | ~17 人日 | 多团队隔离、成本可控、关键操作留痕 |
| **四期** | 持续优化延伸 | 4 | ~42 人日 | 资产版本化、经验自进化、自定义大盘、安全审计 |
| | | **21** | **~111 人日** | |

**估算前提**：全职投入、AI 辅助编码、含自测但不含大规模用户验收。按每周 5 个工作日折算约 **22 周**。若为兼职（每周 2 天），需 ×2.5。

> ⚠️ **这类估算天然偏乐观**。四期的四个模块都是全新且不确定性高（尤其 `memory` 与 `risk`），实际可能显著超出。建议一期二期跑完后用真实速度重新校准三四期。

## 2. 一期：评测闭环跑通（~32 人日）

**目标**：平台能被真实使用一次 —— 接入 Agent → 看到轨迹 → 定义评判标准 → 跑评估 → 看到结果。

**这七屏缺任何一个，闭环就断了。**

| 屏 | 现有基础 | 本期要做 | 估算 |
|---|---|---|---|
| `access` 接入中心 | `apps`(5 接口) + `services/access.py` | 三通道扩为**四通道**（加 eBPF），端点改自建网关 | 2 |
| `traces` 链路观测 | `traces`(3 接口)，前端仅 52 行 | 补表格列、筛选、三视角页签 | 3 |
| `trace` 链路详情 | `TraceDetail.vue`(112 行) | 补 span 树与逐步耗时 | 2 |
| `evaluators` 评估器 | `evaluators`(5 接口) + svc | **接入 DeepEval**：16 预置 + GEval + DAGMetric，阈值改 τ=0.75 | **5** |
| `tasks` 评估任务 | `tasks`(6 接口) | 补分步表单、四种数据来源、试次 k | 3 |
| `insight` 分析洞察 | **无** | 全新：三口径卡片、评分分布、三列分数、低分下钻 | 4 |
| `dashboard` 工作台 | `dashboard`(1 接口) | 改造为 KPI + 待办入口 | 2 |
| — | — | **数据层全表加 `workspace_id`**（界面留三期，见 §6.1） | 3 |
| — | — | 前端视觉体系对齐原型（token、组件、明暗主题） | 5 |
| — | — | 联调与自测 | 3 |

**验收标准**：

1. 一个真实 Agent（建议先用 Claude Code 走 Pilot 通道）接入成功，链路可查
2. 用 `TaskCompletionMetric` 跑完一个 50 样本的评估任务
3. 结果页**同时显示 Average / pass@k / pass^k**，且 τ=0.75 而非 DeepEval 默认的 0.5
4. 低分样本能从分析洞察下钻到链路详情

**关键风险**：DeepEval 集成是本期唯一的技术不确定项。建议**第一周就做技术验证**（跑通一个最小样本），不要放到期末。

## 3. 二期：数据飞轮与约束力（~20 人日）

**目标**：让评测结果沉淀成资产，并对版本发布产生实际约束 —— 这是评测体系与「跑个分看看」的分水岭。

| 屏 | 现有基础 | 本期要做 | 估算 |
|---|---|---|---|
| `trajectory` 轨迹库 | `datacenter` 的 `/trajectories` | 从 Datacenter 拆为独立屏，标明 Trace/eBPF 双源 | 2 |
| `datasets` 数据集 | `datacenter`(6 接口，含 `from-traces`) | 拆为独立屏，补字段管理与四种创建来源 | 3 |
| `pipeline` 数据加工 | **无**（但 `from-traces` 可复用） | 算子链 + 单次/周期调度 + 内置模版 | 5 |
| `badcases` Bad Case 库 | `badcases`(4 接口) | 补「触发评估器」「Root Cause」列与复盘状态流 | 2 |
| `regression` 实验与回归 | `regression`(5 接口) | **门禁判定 + bullet 阈值图 + CI webhook 接线** | 5 |
| — | — | 自测 | 3 |

**验收标准**：

1. 评估产生的低分样本**自动写入** Bad Case 库
2. 从轨迹库勾选一批 → 一键沉淀为回归集
3. 跑一次版本对比，**门禁给出「阻断」结论并写明依据**（哪个指标、实测多少、较基线降多少）
4. CI 通过 `gate_webhook_url` 收到回调，退出码非 0 能阻断合并

**依赖**：必须在一期之后 —— 没有评估结果就没有 Bad Case，没有数据集就没有回归。

## 4. 三期：1000 人规模治理（~17 人日）

**目标**：从「一个团队试点」变成「1000 人能同时用而不互相干扰」。

| 屏 | 现有基础 | 本期要做 | 估算 |
|---|---|---|---|
| `space` 空间与成员 | `system`(6 接口) | 空间切换界面 + 四类角色权限（数据层一期已铺好） | 5 |
| `budget` 成本与配额 | `services/budget.py`（**无 router**） | 补 router + 前端；把 `judge_daily_limit_yuan` 接到执行路径做熔断 | 4 |
| `audit` 操作审计 | `services/audit.py` + `Audit.vue`(124 行) | 补「改阈值/改金标准/重跑任务」三类高风险标记与筛选 | 2 |
| `notify` 通知中心 | `notifications`(3 接口) | 补未读徽标与「全部已读」 | 1 |
| `quickstart` 快速启动 | **无** | 三条主线引导 + CLI/CI 入口说明 | 2 |
| — | — | 自测 | 3 |

**验收标准**：

1. 三个工作空间的数据互不可见，切换即时生效
2. 只读角色看不到任何写操作入口
3. 单空间超出 Token 配额后**新任务被阻断，在跑任务不受影响**
4. 修改评估器阈值这一操作在审计里被标为高风险并可筛选

**为什么不更早**：这些都是「人多了才需要」的。一期二期单团队试点时可以不做 —— 但**数据层的 `workspace_id` 必须一期就铺**，见 §6.1。

## 5. 四期：持续优化延伸（~42 人日）

**目标**：补齐 AgentLoop 的「持续优化」能力。**这一期是锦上添花，不是平台成立的必要条件。**

| 屏 | 本期要做 | 新增表 | 估算 |
|---|---|---|---|
| `assets` Agent 资产 | Prompt/Skill 版本化，Latest/Production 双通道，安全扫描 | 4 | 8 |
| `memory` 经验与记忆 | 经验库挖掘 + 召回、记忆库四策略、**pgvector 语义检索** | 3 | 10 |
| `boards` 仪表盘 | 自定义大盘：图表配置引擎 + 布局 | 1 | 8 |
| `risk` 风险审计 | 提示注入 / 敏感信息 / 越权工具调用检测 | 1 | 10 |
| — | 自测 | | 6 |

**这四个的不确定性最高，理由各不相同**：

- `memory` —— 「从轨迹挖掘经验并召回注入」业界都还在探索，没有成熟范式可抄。**建议先做一个只读的经验展示，把自动挖掘往后放。**
- `risk` —— 唯一有**外部知识依赖**的模块：需要提示注入规则库、敏感信息正则库。纯开发解决不了，要么找开源规则集，要么与安全团队合作。
- `boards` —— 图表配置引擎是典型的「看着简单做着深」，一个人做容易陷进去。**可考虑先提供几张固定报表，把自定义能力延后。**
- `assets` —— 相对确定，但 4 张表 + 版本流转 + 灰度切换，量在那里。

## 6. 三个排期陷阱

### 6.1 空间隔离：数据层必须一期做，界面可以三期做

**这是本排期里最容易踩的坑。**

`workspace_id` 要加到**所有业务表**并在查询层强制过滤。一期做时只有 6 张表受影响；如果拖到三期，二期新增的 `pipelines`、`experiment_plans` 等表也要一起改，**改造面翻倍，且要重跑全部回归**。

**结论**：一期就把 `workspace_id` 字段、查询过滤、`owner` 字段铺好（约 3 人日），界面（空间切换器、成员管理）留到三期。**数据层早做便宜，晚做昂贵。**

### 6.2 DeepEval 集成要在一期第一周验证，不能压到期末

评估器是所有后续期的依赖：二期的门禁要它、三期的配额要统计它的调用、四期的经验挖掘要它的评分。

它也是一期唯一的**技术不确定项**（外部库集成、异步并发、阈值口径）。压到期末发现不通，整个排期都要重排。

**结论**：第一周先跑通「一个样本 + 一个 `TaskCompletionMetric`」的最小闭环，再展开其余工作。

### 6.3 三个已知缺口要在一期二期顺手补掉，别攒到最后

技术方案 §8 列的四条风险里，有三条是现有代码的真实缺口：

| 缺口 | 建议补的时机 | 理由 |
|---|---|---|
| 长任务中断（无断点续跑） | **一期**，随评估执行一起做 | 一期就要跑真实评估任务，进程一重启任务就丢，会直接影响验收 |
| PG 侧无 TTL 与归档 | **二期** | 二期开始有持续数据写入，再不做就要清历史 |
| 预算熔断未接线 | **三期**，随 budget 屏一起 | `judge_daily_limit_yuan` 与 `JudgeDailyStat` 已是半成品，接线成本低 |

## 7. 如果时间不够：可以往后挪而不影响平台成立的部分

用户要求不砍功能，本排期也确实覆盖全部 21 屏。但若实际进度落后，**以下顺序往后挪的代价最小**（仅供参考，不是建议砍掉）：

1. `boards` 自定义仪表盘 —— `insight` 已提供固定视角的分析，短期可替代
2. `memory` 的**自动挖掘**部分 —— 保留只读展示，挖掘逻辑延后
3. `risk` —— 依赖外部规则库，可先接一个最小规则集
4. `quickstart` —— 可用 README 临时替代
5. `pipeline` 的**通用算子链** —— `from-traces` 已能覆盖最常用的「从轨迹建集」

**不可挪的**：一期七屏、二期的 `regression` 门禁、三期的 `space` 与 `budget`。前者是闭环，后两者是 1000 人规模的前提。
