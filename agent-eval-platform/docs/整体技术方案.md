# TAgentEval 整体技术方案

> 配套文档：[技术栈选型.md](技术栈选型.md)（回答「用什么」），本文回答「怎么搭」。
> 界面口径以 [prototype.html](prototype.html)（20 屏）为准，行为契约以 `openspec/specs/prototype-*` 五份规格为准。
> 证据口径同选型文档：【实测】可追溯到代码行，【文档】附官方链接，【推断】未经证实。

## 1. 分层架构

```
┌─ 被测侧（不属于平台，装在用户的 Agent 上）─────────────────────┐
│  LoongSuite Python Agent │ Pilot │ OTLP SDK │ eBPF 探针        │
└───────────────────────────────┬───────────────────────────────┘
                                │ OTLP over HTTP（内网自建网关）
┌─ ① 接入层 ────────────────────▼───────────────────────────────┐
│  OTLP 网关：Token 鉴权 → 降噪（跳过 format/embed）→ 属性截断    │
│  routers/otlp.py · services/otlp_gateway.py                    │
└───────────────────────────────┬───────────────────────────────┘
                                │ 直连（轻量期）/ Kafka（放大后）
┌─ ② 归一化层 ──────────────────▼───────────────────────────────┐
│  唯一的归一化入口：Span 树 → Trajectory（Trace 与 eBPF 双源汇聚）│
│  services/assembler.py                                         │
└───────────────────────────────┬───────────────────────────────┘
┌─ ③ 存储层 ────────────────────▼───────────────────────────────┐
│  PostgreSQL（控制面 + 事件）  ⟷  ClickHouse（可选，分析加速）    │
│  pgvector（经验/记忆的语义检索）                                │
└───────────────────────────────┬───────────────────────────────┘
┌─ ④ 评估层 ────────────────────▼───────────────────────────────┐
│  DeepEval 执行器 · asyncio 并发池 · 归一化 · 三口径聚合 · 门禁   │
│  services/worker.py · services/evaluators.py                   │
└───────────────────────────────┬───────────────────────────────┘
┌─ ⑤ 应用层 ────────────────────▼───────────────────────────────┐
│  FastAPI 20 屏 API  ⟷  Vue3 + Element Plus 前端                │
└───────────────────────────────────────────────────────────────┘
```

**一条要守住的原则**：**摄入有三条写路径（直连 / Kafka / 回填），但归一化只有一处**（`services/assembler.py`）【实测，见项目 CLAUDE.md 架构主线】。任何新增数据源都必须汇到这里，否则轨迹口径会分叉。

## 2. 接入层：LoongSuite 四通道

按**被接入对象的形态**分通道，不按产品名——按产品名切分的老口径遇到新工具就无处归类【实测 `services/access.py:1-7`】。

| 通道 | 技术 | 适用对象 | 侵入性 | 能拿到什么 |
|---|---|---|---|---|
| ① Python Agent | LoongSuite Python 探针，改启动命令 | LangChain / LangGraph / AgentScope / OpenAI SDK | 不改代码 | 框架内完整上下文：规划、工具入参、中间态 |
| ② Pilot | LoongSuite Pilot 本地客户端，一机装一次 | Claude Code / Codex / OpenCode / Cursor | 不改代码 | 对话、工具调用、Token 事件 |
| ③ OTLP 直推 | OpenTelemetry SDK | 自研 Agent、无探针覆盖的框架 | 需少量埋点 | 取决于埋点质量 |
| ④ eBPF 无侵入 | 主机/容器级内核态采集 | 改不了启动方式的存量服务 | 零改动 | **仅进程外可见的请求与响应**，拿不到框架内部决策 |

**统一上报到自建 OTLP 网关**（`https://otlp.<内网域名>/v1/traces`），鉴权用**接入 Token**，不经任何云厂商端点。

**网关侧的两个降噪参数**【实测 `config.py`】：`otlp_skip_span_ops`（默认跳过 `format,embed` 类 span）、`otlp_max_attr_chars`（属性截断 8000 字符）。这两个直接决定存储成本，需按实际数据回调。

> ④ 与 ①② 是**互补不是替代**。需要完整轨迹时必须叠加探针，这一点要在接入指引里写明，避免用户以为 eBPF 能覆盖一切。

## 3. 存储层

### 3.1 现有 16 张表【实测 `models.py`】

`users` `workspaces` `memberships` `apps` `traces` `metrics` `evaluators` `eval_tasks` `score_records` `bad_cases` `datasets` `dataset_samples` `regression_runs` `judge_daily_stats` `audit_logs` `notifications`

其中 **`metrics` 表随指标字典一同废弃**（评估能力来源已改为 DeepEval）。

### 3.2 新原型带来的表缺口

20 屏逐一核对后，需新增以下表：

| 屏 | 新增表 | 关键字段要点 |
|---|---|---|
| 仪表盘 `boards` | `dashboards` | 空间隔离、布局 JSON、图表定义 |
| 实验与回归 `regression` | `experiment_plans` | 基线版本、候选版本、数据集、评估器集合、调度 |
| 轨迹库 `trajectory` | `trajectories` | 由 Span 树清洗组装；含 `steps` / `tool_calls` / `model_calls` / `source`(trace\|ebpf) |
| 数据加工 `pipeline` | `pipelines` `pipeline_runs` | 算子链 JSON、调度模式（单次/周期）、输出数据集、产出条数 |
| Agent 资产 `assets` | `prompts` `prompt_versions` `skills` `skill_versions` | **Latest / Production 双通道指针**、安全扫描结果 |
| 经验与记忆 `memory` | `experiences` `memory_stores` `memory_items` | `experiences` 带 **vector 列（pgvector）** 供召回；命中次数与命中后通过率 |
| 风险审计 `risk` | `risk_events` | 风险类型、等级、关联会话、处置状态 |
| 成本与配额 `budget` | `quotas` `quota_usage` | 空间级配额（评测次数 / Token），超额阻断标记 |

**其余 12 屏复用现有表**，无孤立屏。

### 3.3 PG 与 ClickHouse 的分工

【实测 `services/clickhouse_store.py:1-8`】既有设计已写明，本方案沿用：

- **PG** 承担控制面与在线查询（用户/应用/评估器/任务/数据集/复核流）
- **ClickHouse** 承担事件与分析（仪表盘聚合、趋势、根因），热数据 30 天 TTL，评分与 Bad Case 保留 365 天
- **未启用时自动退化为纯 PG**，这是轻量期的默认形态

### 3.4 PG 侧的保留策略（现有缺口）

ClickHouse 层已有 TTL，**PG 侧没有**【实测】。需补：

| 表 | 策略 |
|---|---|
| `traces` / `trajectories` | 热数据 90 天，之后归档到冷表或对象存储 |
| `score_records` | 保留 365 天（长周期趋势需要） |
| `audit_logs` / `risk_events` | 保留 ≥ 2 年（合规） |

实现方式：定时任务 + 分区表，或 `pg_partman`。**不要靠人工清理。**

## 4. 评估层

### 4.1 执行模型

```
评估任务
  → 拆样本（数据来源：链路 / Agent 轨迹 / 日志 / 数据集）
  → asyncio 并发池（信号量限流，默认 10 路）
  → 逐样本调 DeepEval（metric.a_measure，其 async_mode 默认开启【文档】）
  → 各评估器按自身制式打分（5 分制 / Pass-Fail / 0-1 连续）
  → 归一化到 [0,1]
  → 按公式聚合
  → 同时输出 Average / pass@k / pass^k 三个口径
```

**并发度不是越高越好**：上游 LLM 服务有限流，且 `judge_daily_limit_yuan` 是硬预算【实测】。并发池要与预算熔断联动 —— 预算打满时**停止派发新样本而不是失败重试**。

### 4.2 打分与聚合

```
task_score = s_safety × ( α · s_completion + β · s_robustness )
α = 0.8   β = 0.2   τ = 0.75   k = 3（关键链路 5）
```

`s_safety` 是 **0/1 乘法门控**——安全违规不能被高完成度抵消。

**三分量 → DeepEval 评估器的映射【推断，待方法论确认】**：

| 分量 | 建议来源 | 说明 |
|---|---|---|
| `s_safety` | `ToxicityMetric` / `BiasMetric` | 任一超阈即判 0 |
| `s_completion` | `TaskCompletionMetric`（多轮改用 `ConversationCompletenessMetric`） | 主完成度 |
| `s_robustness` | `ToolCorrectnessMetric` + `ArgumentCorrectnessMetric` | 加权后叠加 k 次试次的一致性 |

> 该映射由平台侧提出，**尚未经方法论确认**。原型界面上已挂「待确认」徽标，落地前需与评测体系负责人对齐后再固化。

**三口径必须同时报**，只报 Average 会掩盖稳定性问题——Average 0.83 而 pass^k 0.67，意味着重复跑三次有三分之一掉出阈值，那是稳定性问题不是能力问题。

**但 pass^k 不能对全量评测集开**【文档，外层 `01-指标体系与指标字典.md:208`】：它的算力是单试次的 **k 倍**，方法论明确要求只对 **L4 关键子集**开（通常是回归集中标记为「关键链路」的 20–30%）。

这条对实现有三个直接约束：

1. 数据集样本需要带 **`is_critical` 标记**，评估任务据此决定该样本跑 k 次还是 1 次
2. 任务配置里的 `k` 是**关键子集的试次**，不是全量试次；界面上要写清楚，否则用户会以为全量都跑 k 次
3. 另一条方法论陷阱一并落地：**k 从 3 提到 5 时 pass^k 必然下降，这是数学必然不是质量退步**，跨 k 比较前必须对齐 —— 报告里要显示 k 值，禁止不同 k 的结果直接并列对比

### 4.3 阈值口径

DeepEval 的 `threshold` 默认 **0.5**，平台统一取 **τ=0.75**。这个差异必须在配置与界面上显式标注，否则评出来的通过率会与方法论对不上。

### 4.4 长任务的可靠性（现有缺口）

现有 worker 是**进程内 asyncio**【实测 `services/worker.py:1-5`】，进程重启会丢任务。需补：

1. 任务状态与**已完成样本游标**持久化到 PG
2. 启动时扫描 `running` 状态任务并**从游标续跑**
3. 任务超时看门狗，避免僵尸任务永久占用配额

## 5. 多租户与权限

| 层 | 机制 |
|---|---|
| 资源隔离 | 所有业务表带 `workspace_id`，查询层强制注入过滤 |
| 角色 | 管理员 / 测试开发 / 测试工程师 / 只读（四类） |
| 权限点 | 建改评估任务与数据集（tester+）、建改评估器与 Pipeline 与资产（devops+）、空间设置与成员与配额（admin） |
| 配额 | 空间级，评测次数 + Token 两类，超额**阻断新任务但不影响在跑任务** |

**权限是两层**【实测，项目 CLAUDE.md 架构主线】：接口层校验 + 数据层 `workspace_id` 过滤。两层都要有，只做接口层会被越权查询绕过。

**登录**：1000 人规模建议接公司 SSO / LDAP，不自建用户体系。现有 `users` 表保留，作为 SSO 身份的本地映射。

## 6. 门禁与 CI 集成

- **判定线** τ=0.75，**任一核心指标低于 τ 即阻断**
- 门禁结论必须写明依据（哪个指标、实测多少、较基线变化多少），不能只给一个「阻断」徽标
- **CI 回调**：`gate_webhook_url` + `gate_webhook_secret` 已预留【实测 `config.py`】
- **CLI**：`tae eval run --dataset <name> --k 3`，退出码非 0 即阻断合并

## 7. 部署编排

```yaml
# 轻量期形态（单机 8C16G + 500GB SSD）
services:
  postgres:   # PG 16 + pgvector 扩展
  backend:    # FastAPI，4 个 uvicorn worker
  frontend:   # Vue 构建产物 + Nginx
  # 以下按需启用，非默认
  # clickhouse:  CLICKHOUSE_ENABLED=true 时
  # kafka:       KAFKA_BROKERS 非空时
  # minio:       出现超大 payload 时
```

**四条运维约定**：

1. **备份**：PG 每日全量 + WAL 归档，恢复演练至少做一次（没演练过的备份不算备份）
2. **升级**：Compose 编排入库，可一键重建
3. **监控**：平台自身接 OpenTelemetry，避免「评测平台自己是黑盒」
4. **Python 版本锁 3.12** —— 3.14 下 SQLAlchemy 2.0.36 解析 `str | None` 注解会崩【实测】

## 8. 风险与对策

| 风险 | 后果 | 对策 | 状态 |
|---|---|---|---|
| 单点故障 | 全平台不可用 | 快照 + 一键重建；关键期双机冷备 | 待建 |
| 长任务中断 | 评估任务丢失 | 状态与游标落 PG + 启动续跑 | **缺口，见 §4.4** |
| 磁盘增长 | 数月后打满 | PG 侧 TTL 与归档 | **缺口，见 §3.4** |
| LLM 限流与成本 | 打爆上游 / 账单超支 | 并发信号量 + 退避 + 预算熔断 | 半成品：`judge_daily_limit_yuan` 与 `JudgeDailyStat` 已在，**需接到执行路径** |
| 判官不可复现 | 评测结论失去仲裁力 | 判官版本与 Prompt 全部版本化；同一任务复评须可回放 | 待建 |
| eBPF 通道被误用 | 用户以为它能替代探针 | 接入指引显式写明能力边界 | 已在原型文案中 |
