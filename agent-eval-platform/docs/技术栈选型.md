# TAgentEval 技术栈选型

> 决策日期 2026-09-07。本文回答三个问题：**后端用 Python 还是 Java**、**最终技术栈是什么**、**单机能不能撑 1000 人**。
>
> **证据口径**：【实测】来自本仓库现有代码或本文的容量测算，可追溯到文件行；【文档】来自官方文档，附链接；【推断】是由前两者反推、未经证实的判断，**不可当结论引用**。

## 0. 结论速览

| 项 | 结论 |
|---|---|
| 后端语言 | **Python 3.12 + FastAPI** |
| 决定性理由 | 评估器生态在 Python：DeepEval 无 Java 对等物。选 Java 就得同时维护两套语言栈 |
| 部署形态 | **单机 Docker Compose 起步**，8C16G + 500GB SSD |
| 单机能否撑 1000 人 | **能**。峰值 < 10 QPS，余量两到三个数量级。风险在可用性不在性能 |
| 刻意不引入 | Kafka、ClickHouse、Redis、Celery、独立向量库 —— 均给出引入触发条件 |

## 1. 这不是从零选型

现有 `backend/` 已有 **3373 行 FastAPI 实现**【实测】，且架构与 Langfuse v3 同构。因此本次是「把已验证的架构正式化」，不是推倒重来。

已经落地的部分【实测】：

| 能力 | 位置 | 说明 |
|---|---|---|
| PG 管控制面 + ClickHouse 管事件分析 | `backend/app/services/clickhouse_store.py:1-8` | 文件头注释即写明该分工，与 Langfuse v3 一致 |
| ClickHouse 表结构 | 同上 `DDL` | `traces_ch` / `score_records_ch` / `bad_cases_ch`，`ReplacingMergeTree` + 按日分区 + TTL（热数据 30 天、评分 365 天） |
| fail-open 降级 | `backend/app/config.py:26` | `clickhouse_enabled: bool = False`，未启用时自动退化为纯 PG |
| Kafka 摄入通道 | `backend/app/kafkaio.py` | 兼容 Collector 直发 proto 与网关 JSON 信封；`kafka_brokers` 为空即直连模式 |
| LLM 成本保护 | `config.py` `judge_daily_limit_yuan: 50.0` + `models.py:192 JudgeDailyStat` | 判官日预算与用量统计表已在 |
| 门禁 CI 回调 | `config.py` `gate_webhook_url` / `gate_webhook_secret` | 回归门禁的 Webhook 出口已预留 |
| OTLP 网关降噪 | `config.py` `otlp_skip_span_ops` / `otlp_max_attr_chars` | 默认跳过 `format,embed` 类 span，属性截断 8000 字符 |
| 接入通道按形态划分 | `backend/app/services/access.py:1-7` | 注释写明「按产品名切分的老口径遇到新工具无处归类」，故按形态分通道 |

**这批既有资产直接决定了选型**：换 Java 等于把这 3373 行连同上述设计一起重写。

## 2. 语言选型：Python + FastAPI vs Java + Spring Boot

### 2.1 五维对比

| 维度 | Python + FastAPI | Java + Spring Boot | 判定 |
|---|---|---|---|
| **① 评估器生态** | DeepEval 原生 Python，60+ 指标，含 `GEval` / `DAGMetric` / 多轮会话 4 指标 / Agentic 3 指标【文档】；RAGAS、promptfoo、Phoenix、TruLens 均为 Python 一等公民 | LangChain4j、Spring AI 成熟，但**评估侧只有第三方「受 RAGAS 启发」的移植品**（`ai-qa-solutions/spring-ai-ragas`），无 DeepEval 对等物 | **Python 压倒性** |
| **② 团队现状** | 测试部以 Python 为主（用户裁定）；现有 3373 行后端即出自该背景 | 需依赖部门内少数人的技能，长期维护有人力单点 | **Python** |
| **③ 并发模型贴合度** | 负载形态是「大量并发等待 LLM 响应」的 IO 密集型，asyncio 天然契合；DeepEval 自带 `async_mode`【文档】 | 线程池可行，虚拟线程（JDK 21+）后更优 | **Python 略优** |
| **④ 性能** | 峰值需求 < 10 QPS（见 §4），余量两到三个数量级 | 同左 | **不构成区分度** |
| **⑤ 企业中间件与治理** | 生态弱于 Java | 连接池、事务、监控、发布规范成熟 | **Java 占优，但本项目用不到重型中间件** |

### 2.2 性能维度为什么不构成区分度

这是最容易被误用的维度，所以单独说清楚。

本平台的负载有三段，**没有一段的瓶颈在 Web 框架**：

1. **OTLP 摄入** —— 峰值约 5 Span/s（见 §4）。两种框架都是数量级的余量。
2. **查询聚合** —— 瓶颈在数据库的扫描与聚合，不在应用层序列化。
3. **评估执行** —— 单次 LLM 判官调用**秒级**（约 3s），比框架处理耗时高 3~4 个数量级。这段的优化方向是并发度与限流，不是语言。

**结论**：拿 FastAPI 与 Spring Boot 的框架跑分来做本项目的选型依据是错配的。真正该关心的是「能不能方便地并发等待 LLM、能不能直接用评估库」。

### 2.3 选 Java 的代价

若选 Java，DeepEval 不能直接用，只有两条路：

| 路径 | 代价 |
|---|---|
| 放弃 DeepEval，改用 `spring-ai-ragas` | 指标覆盖面大幅缩水：无 `GEval`（自然语言 criteria）、无 `DAGMetric`（确定性决策树）、无多轮会话四指标。而我们原型里这些都是核心 |
| Java 主服务 + Python 评估 worker（gRPC/HTTP） | **同时维护两套语言栈** —— 把选 Java 想省下的一致性又赔了进去，还多一层跨进程调用的故障面 |

### 2.4 这条结论的前提

**依赖「测试部以 Python 为主」这一前提。** 若公司层面强制新服务必须 Java，结论需重算，届时推荐 §2.3 的第二条路径（Java 主服务 + Python 评估 worker），并接受多一套语言栈的运维成本。

## 3. 最终技术栈

| 层 | 选型 | 版本 | 理由 |
|---|---|---|---|
| **前端框架** | Vue 3 + Vite + Pinia + Vue Router | Vue 3.4+ | 用户裁定 |
| **UI 组件** | Element Plus | 2.x | 用户裁定 |
| **图表** | ECharts | 5.x | 原型需要 bullet（阈值对比）、多系列折线、分数分布直方图；ECharts 覆盖且支持无障碍配置 |
| **后端框架** | **Python + FastAPI** | **Python 3.12**、FastAPI 0.115 | 见 §2。**必须锁 3.12**：3.14 下 SQLAlchemy 2.0.36 解析 `str \| None` 注解会崩【实测，见项目 CLAUDE.md】 |
| **数据校验** | Pydantic v2 | 2.10 | 已在用 |
| **ORM** | SQLAlchemy 2.0 | 2.0.36 | 已在用 |
| **主数据库** | **PostgreSQL** | 16 | 控制面 + 轻量期事件层。用户已确认从 MySQL 改为 PG，与现有实现一致 |
| **向量检索** | **pgvector** 扩展 | 0.7+ | 经验库召回与记忆库语义检索。经验条目量级在千条内，不值得为此引独立向量库 |
| **采集探针** | **LoongSuite** 四通道 | — | Python Agent / Pilot / OTLP 直推 / eBPF。**探针装在被测应用上，与平台后端语言无关** |
| **传输协议** | OpenTelemetry / OTLP | proto 1.27 | 已在用（`opentelemetry-proto` + `protobuf`） |
| **评估执行** | **DeepEval** | 最新稳定版 | 16 个预置指标 + `GEval` + `DAGMetric`。见 §5 |
| **CI 门禁**（可选） | promptfoo | — | 声明式配置、适合放流水线做发布门禁【文档】 |
| **平台自监控** | OpenTelemetry SDK | — | 平台自己也要可观测，避免「评测平台自身是黑盒」 |
| **对象存储**（可选） | MinIO | — | 仅当出现超大 payload（长上下文、多模态附件）时启用，对齐 Langfuse 的 S3 角色【文档】 |
| **部署** | Docker Compose | — | 起步形态，编排预留 K8s 迁移路径 |

### 3.1 刻意不引入的组件

**堆组件会让单机运维成本失控，而当前量级用不到它们。** 每一项都给出引入触发条件，不是一刀切地否定：

| 组件 | 为什么现在不用 | 什么时候引入 |
|---|---|---|
| **Kafka** | 万级 Span/天下 PG 直写足够；代码已保留通道（`kafka_brokers` 为空即直连）【实测】 | 摄入峰值 > 200 Span/s，或需要跨进程削峰 |
| **ClickHouse** | 同上；开关 `clickhouse_enabled` 已就位，切换不需改代码【实测】 | Span > 10 万/天，或单表 > 5000 万行，或仪表盘聚合查询 > 1s |
| **Redis** | 10 QPS 下 PG 足够；配额计数用 PG 行锁即可，无并发热点 | 用户 > 3000，或出现明确的查询热点，或需要跨实例共享会话 |
| **Celery / RQ** | 进程内 asyncio 已能跑离线批次【实测，`services/worker.py:64 offline_batch`】；引入等于多一套 broker 与 worker 运维 | 需要跨机器分布式执行评估任务 |
| **独立向量库**（Milvus/Qdrant） | 经验条目千条量级，pgvector 甚至暴力扫描都够 | 向量数据 > 100 万条，或需要复杂过滤 + 向量的混合检索 |

## 4. 单机能否承载 1000 人：能，性能不是风险

### 4.1 输入参数（便于日后按实际值重算）

| 参数 | 取值 | 来源 |
|---|---|---|
| 注册用户 | 1000 | 用户给定 |
| 日活率 | 30% → 300 人 | 【推断】内部工具典型值 |
| 人均日查询 | 10 次 | 【推断】 |
| Span 量 | 日均万级，上限按 3 万/天算 | 用户给定 |
| 单 Span 大小 | 5KB（含输入输出文本） | 【推断】 |
| 评估任务 | 20 个/天 × 200 样本 × k=3 | 【推断】 |

### 4.2 测算

| 项 | 计算 | 结果 |
|---|---|---|
| Span 摄入均值 | 30000 ÷ 86400 | **0.35/s** |
| Span 摄入峰值 | 工作时段 8h 集中 + 峰值系数 5 | **约 5/s** |
| 查询峰值 | 3000 次/天，8h 集中，峰值系数 10 | **约 3 QPS** |
| **合计峰值** | 5 + 3 | **< 10 QPS** |
| FastAPI 承载力 | 4 个 uvicorn worker，简单 JSON 端点在千级 RPS 量级【推断，业界常识量级】 | **余量两到三个数量级** |
| 存储增长 | 30000 × 5KB = 150MB/天；PG 索引与 WAL 放大约 2× | **300MB/天 → 110GB/年** |
| 存储稳态 | 配 90 天热数据保留 + 冷归档 | **约 27GB** |
| LLM 判官调用 | 20 × 200 × 3 = 12000 次/天；3s/次、并发 10 路 | **约 1 小时/天**，且这是**外部 LLM 服务**的负载 |

> **这个 12000 次是上界，实际会低约一半。** 方法论要求 pass^k **只对 L4 关键子集开**（回归集中标记为「关键链路」的 20–30%），其余样本单试次即可【文档，外层 `01-指标体系与指标字典.md:208`】。按 25% 关键子集算：`200×0.25×3 + 200×0.75×1 = 300` 次/任务，全天约 **6000 次**。上表按全量 k=3 估算是刻意留的保守余量。

**推荐配置**：8C16G + 500GB SSD 单机。

### 4.3 真正的风险在这四条

性能余量充足，但**单机形态有可用性代价**，必须配对策：

| 风险 | 后果 | 对策 |
|---|---|---|
| **单点故障** | 宕机即全平台不可用 | 定期快照 + 可一键重建的 Compose 编排；关键期可上双机冷备 |
| **长任务中断** | 评估任务跑几十分钟，进程重启即丢 | **任务状态持久化到 PG + 启动时恢复未完成任务**。现有 worker 是进程内 asyncio【实测 `services/worker.py:1-5`】，**此项是缺口，需补** |
| **磁盘无节制增长** | 数月后打满 | PG 侧补 TTL 与归档。ClickHouse 层已有 TTL 设计，**PG 侧目前没有，是缺口** |
| **LLM 限流与成本失控** | 判官打爆上游、账单超支 | 并发信号量 + 指数退避 + 配额熔断。`judge_daily_limit_yuan` 与 `JudgeDailyStat` 已在【实测】，需接到评估执行路径上 |

### 4.4 演进触发点

现有 fail-open 开关让这些切换**不需要重构**：

```
Span > 10 万/天 或 单表 > 5000 万行  →  CLICKHOUSE_ENABLED=true（代码已支持双写）
摄入峰值 > 200/s 或 需要削峰        →  配置 KAFKA_BROKERS（代码已支持）
用户 > 3000 或 需要 SLA            →  迁 K8s，Web 与 Worker 拆容器（对齐 Langfuse v3）
向量数据 > 100 万条                →  pgvector 换独立向量库
```

## 5. 评估框架：为什么是 DeepEval

【文档】业界的实践共识是**需要两层**：一个轻量框架做 CI/CD 门禁（DeepEval / RAGAS / promptfoo），一个平台做人工标注、回归追踪与看板（Braintrust / LangSmith / Arize）。

**TAgentEval 本身就是「平台」那一层，因此需要嵌入「框架」那一层。**

| 候选 | 定位 | 是否选用 |
|---|---|---|
| **DeepEval** | Python + pytest 风格，60+ 指标，覆盖 RAG / Agentic / 多轮会话 / 安全 | **✅ 主选**。指标覆盖面最全，且有 `GEval`（自然语言 criteria）与 `DAGMetric`（确定性决策树）两种自定义方式 |
| RAGAS | 检索专项，reference-free 指标 | ❌ 覆盖面窄于 DeepEval，其 RAG 指标 DeepEval 已有对等物 |
| promptfoo | 声明式对比、红队、发布门禁 | **⭕ 可选补充**，放 CI 流水线做门禁，与平台内评估互补 |
| Phoenix / TruLens | 以 OpenTelemetry 为中心，step 级评分 | ❌ 与我们自建的观测层职能重叠 |
| Opik / LangSmith / Braintrust | 平台型 | ❌ 与 TAgentEval 定位冲突 |

**阈值口径**：DeepEval 的 `threshold` 默认 0.5，**我们统一取 τ=0.75**（平台口径，源自外层方法论文档）。这个差异必须在代码与界面上显式标注，否则评出来的通过率会与方法论对不上。

## 6. 与 Langfuse 的对照

用户要求参考 Langfuse。【文档】其 v3 自托管架构为：

| Langfuse v3 组件 | 角色 | TAgentEval 对应 |
|---|---|---|
| PostgreSQL | 事务数据 | ✅ 相同 |
| ClickHouse | traces/observations 的 OLAP 存储 | ⭕ 可选，开关已就位（轻量期不启用） |
| Redis / Valkey | 缓存 + 队列 | ❌ 轻量期不引，改用 PG + 进程内 asyncio |
| S3 兼容对象存储 | 原始事件 + 多模态附件 | ⭕ 可选（MinIO） |
| Web / Worker 双容器 | 读写分离 | ⭕ 单机期同进程，迁 K8s 时拆分 |

**判断**：Langfuse 的组件划分是对的，但它面向的是 SaaS 多租户与高吞吐场景。我们在**日均万级 Span** 的量级下，把四个组件砍成一个 PG 是合理的简化 —— 且演进路径与它一致，将来放大不需要改架构，只需要打开开关。
