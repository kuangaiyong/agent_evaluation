# TAgentEval 代码组织方案对比

> 场景：Python + FastAPI **单体**应用，21 个功能屏，**分四期**开发，**一个人 + AI 辅助**。
> 配套：[实施排期.md](实施排期.md) · [整体技术方案.md](整体技术方案.md)

## 0. 结论速览

**推荐方案 C（域垂直 + 管道横向 + 内核共享），并在一期开工前一次性迁移。**

理由一句话：**AI 辅助编码时，「改一个功能只需读一个目录」比「跨四个文件跳转」的收益，比团队协作场景下更大。** 而现在 3373 行是迁移成本最低的时刻。

---

## 1. 现状实测

```
backend/app/
  main.py  config.py  db.py  deps.py  security.py  seed.py
  models.py     222 行 / 16 张表
  schemas.py     76 行 / 12 个类
  routers/      14 个文件 / 54 个接口
  services/     11 个文件
```

**两个实测发现，直接决定了方案选择：**

**① router 与 service 大部分是一对一的**，说明现有「横向分层」实际上已经在按业务域切，只是被硬拆到了两个目录：

```
routers/evaluators.py  ↔  services/evaluators.py
routers/apps.py        ↔  services/access.py
routers/metrics.py     ↔  services/metric_dict.py
```

改一个功能要跳四个地方：`routers/x.py` → `services/y.py` → `models.py` 找表 → `schemas.py` 找 DTO。

**② 但摄入链路天然是横向的**，跨多个域：

```
routers/otlp.py    → services/{otlp_gateway, worker, clickhouse_store}   （引 3 个）
routers/ingest.py  → services/{assembler, worker, clickhouse_store}      （引 3 个）
```

**这条决定了纯垂直切分不成立** —— 摄入管道硬塞进某个业务域会很别扭。

**③ 四期后的膨胀预估**：新增 14 张表 → `models.py` 约 **30 张表 / 420 行**；`schemas.py` 约 **40+ 个类**。单文件还不算灾难，但 AI 每次改动都要在大文件里定位，改错位置的概率随行数上升。

## 2. 四个方案

### 方案 A：维持现状（技术分层 / Package by Layer）

```
app/
  routers/     21 个文件
  services/    ~20 个文件
  models.py    30 张表
  schemas.py   40+ 个类
```

| | |
|---|---|
| **优** | 零迁移成本；FastAPI 教程默认形态，上手无门槛 |
| **劣** | 改一个功能跨 4 个文件；`models.py`/`schemas.py` 成为所有域的争用点；**四期每次新增模块都要在这两个大文件里插代码**，冲突面持续扩大 |
| **AI 友好度** | ✗ 低。AI 要读大文件才能找到目标表/DTO，且容易改到隔壁域 |
| **四期演进** | ✗ 每期在 4 个地方各加一块，边界靠自觉 |

### 方案 B：纯功能域垂直切分（Package by Feature）

```
app/
  features/
    evaluators/   router.py service.py models.py schemas.py
    tasks/        ...
    datasets/     ...
  core/           config.py db.py security.py deps.py
```

| | |
|---|---|
| **优** | 改一个功能只读一个目录；新增模块 = 新增一个目录，不碰老代码 |
| **劣** | **摄入管道无处安放** —— `otlp → assembler → worker → clickhouse` 跨 4 个域，塞进任一个都别扭；公共实体（如 `Trace` 被观测、评估、数据集三个域共用）会产生跨域 import 或重复定义 |
| **AI 友好度** | ✓ 高 |
| **四期演进** | ✓ 好，但管道类需求会不断挑战边界 |

### 方案 C：混合式 —— 域垂直 + 管道横向 + 内核共享 ← **推荐**

```
app/
  core/          配置 · DB 会话 · 鉴权 · 依赖注入 · 统一异常
  shared/        跨域小工具（分页、时间、ID）与共享实体
  pipeline/      横向管道：ingest（OTLP 网关 / Kafka / 归一化）· eval_runner（评估执行）
  domains/       按业务能力垂直切，每域自带 router / service / models / schemas
    identity/    认证 · 用户 · 空间 · 成员 · 角色
    access/      接入中心 · 应用管理
    observability/ 链路观测 · 链路详情 · 轨迹库
    evaluation/  评估器 · 评估任务 · 分析洞察
    dataset/     数据集 · 数据加工
    quality/     Bad Case · 实验与回归
    assets/      Prompt / Skill 资产
    context/     经验库 · 记忆库
    governance/  风险审计 · 操作审计 · 配额 · 通知
    console/     工作台 · 快速启动 · 仪表盘
  main.py        只做装配：注册各域 router
```

| | |
|---|---|
| **优** | 兼顾两者：业务改动落在单个域目录内；管道与内核有正当归属，不必硬塞 |
| **劣** | 需要事先想清楚「什么是域、什么是管道」；`shared/` 有变成垃圾桶的风险 |
| **AI 友好度** | ✓ 高。且目录名本身就是给 AI 的作用域提示 |
| **四期演进** | ✓ 每期新增的是目录，不是在老文件里插代码 |

### 方案 D：方案 C + 显式契约（Modular Monolith）

在 C 的基础上加一条硬约束：**域之间只能通过对方的 `api.py` 调用，禁止 import 对方的 `service.py` / `models.py` 内部**。

| | |
|---|---|
| **优** | 边界不会随时间腐坏；将来真要拆服务时，`api.py` 就是现成的接口清单 |
| **劣** | 一个人开发时，约束的收益不如团队场景明显；跨域读数据要多写一层转发 |
| **AI 友好度** | ✓✓ **反而更高** —— AI 最容易犯的错就是随手 import 到别的域，有机器可检查的约束挡着，比写在文档里管用 |

## 3. 为什么推荐 C（并建议吸收 D 的一条）

### 3.1 决定性因素是「AI 辅助」而非「一个人」

传统上「一个人的项目用分层就够了，不必上垂直切分」——因为一个人脑子里装得下全局。

**但 AI 辅助改变了这个前提**：

| | 人工编码 | AI 辅助编码 |
|---|---|---|
| 上下文 | 人脑记得住全局，跨文件跳转靠记忆 | AI 每次只看被喂进去的片段，**跨文件跳转要显式给路径** |
| 改错位置的风险 | 低（有肌肉记忆） | **高**（大文件里定位靠文本匹配，隔壁域的同名函数会误伤） |
| 目录结构的作用 | 主要是给人看的组织 | **同时是给 AI 的作用域提示** —— 「改评估器」→ 只读 `domains/evaluation/` |

所以：**垂直切分在 AI 辅助场景下的收益，比传统团队场景更大**，这条足以压过「一个人不需要复杂结构」的直觉。

### 3.2 建议吸收方案 D 的一条：机器可检查的边界

不必引入 `import-linter` 这类专用工具（多一个依赖、多一份配置）。**用一条 pytest 架构测试就够**，零新依赖：

```
测试思路（不是实现）：
  遍历 domains/ 下每个 .py，解析其 import 语句
  断言：domains/A 不得 import domains/B 的内部模块
        允许：import domains/B/api.py、import core/、import shared/、import pipeline/
```

这条测试会在 AI 随手写出跨域 import 时立刻变红 —— 比写在 CLAUDE.md 里靠自觉管用得多。

### 3.3 `shared/` 防腐

`shared/` 最容易变成垃圾桶。定一条规矩：**只有被 ≥3 个域使用的东西才能进 `shared/`**，两个域共用就先复制。复制两份的成本，远低于一个被 10 个域依赖的万能工具类。

## 4. 域划分与四期的对应

21 屏归入 10 个域，**每期新增的是完整目录**：

| 期 | 新增/改造的域 | 覆盖屏 |
|---|---|---|
| **一期** | `access` · `observability` · `evaluation` · `console`(部分) · `identity`(仅数据层) | access · traces · trace · evaluators · tasks · insight · dashboard |
| **二期** | `dataset` · `quality` | trajectory · datasets · pipeline · badcases · regression |
| **三期** | `identity`(完整) · `governance`(部分) · `console`(quickstart) | space · budget · audit · notify · quickstart |
| **四期** | `assets` · `context` · `governance`(risk) · `console`(boards) | assets · memory · risk · boards |

**注意 `identity` 跨了一期和三期**：一期只做数据层（`workspace_id` 字段与查询过滤），三期补界面。这与 [实施排期.md](实施排期.md) §6.1 的「数据层早做便宜」一致 —— 域目录一期就建好，三期往里填界面，不用挪结构。

## 5. 迁移时机与路径

### 5.1 时机：一期开工前一次性迁移

| 选项 | 代价 |
|---|---|
| **现在一次性迁移**（推荐） | 3373 行、75 项测试。预估 **2-3 人日**。是**最便宜的时刻** |
| 新模块用新结构，老模块逐步迁 | 长期两套结构并存，AI 会困惑「这个功能该放哪」，且迁移永远做不完 |
| 四期后再迁 | 届时约 15000+ 行，迁移成本 5 倍以上，且要重跑全部回归 |

**与「空间隔离数据层早做便宜」是同一个道理**：结构性改动的成本随代码量超线性增长。

### 5.2 迁移路径（保证每步可回退）

1. **先建骨架**：创建 `core/` `shared/` `pipeline/` `domains/` 空目录与 `__init__.py`
2. **搬内核**：`config.py` `db.py` `deps.py` `security.py` → `core/`。跑测试，应全绿
3. **搬管道**：`otlp_gateway` `assembler` `worker` `kafkaio` `clickhouse_store` → `pipeline/`。跑测试
4. **按域搬**：一次搬一个域（router + service + 从 `models.py` 拆出该域的表 + 从 `schemas.py` 拆出该域的 DTO），**每搬完一个域跑一次测试**
5. **拆表最后做**：`models.py` 的拆分放在最后，因为它牵连最广；拆完后 `models.py` 只保留 `Base` 与跨域共享实体
6. **加架构测试**：最后补 §3.2 那条跨域 import 检查

**每步都跑 `pytest tests/ -q`，基线 75 项通过**。任何一步掉项就停下来查，不要连着搬。

### 5.3 迁移期间的风险

- **`ensure_schema()` 迁移机制**：本项目没有 Alembic，靠 `db.py` 的 `ensure_schema()` 做表结构演进【实测，见项目 CLAUDE.md】。拆 `models.py` 时要确保所有模型仍被 `Base.metadata` 收集到，否则建表会漏
- **`seed.py` 引用面广**：它 import 了几乎所有模型，是搬迁时最容易断的地方，建议放在最后调整
- **循环 import**：域之间若有双向依赖，垂直切分会立刻暴露成 `ImportError`。**这是好事** —— 它逼你在早期就理清依赖方向，而不是等到四期

## 6. 与现有约定的衔接

| 现有约定 | 迁移后 |
|---|---|
| 「摄入三条写路径但归一化只有一处」 | 归一化统一落在 `pipeline/ingest/assembler.py`，边界更清楚 |
| 「处处 fail-open」 | 降级开关集中在 `core/config.py`，各域读配置不自行判断 |
| 「`ensure_schema()` 而非 Alembic」 | 不变，但要保证拆表后模型仍全部注册到 `Base.metadata` |
| 「权限是两层」 | 接口层校验放 `core/deps.py`，数据层 `workspace_id` 过滤放各域 service |
| 「`docs/prototype.html` 是界面事实来源」 | 不变。域划分按业务能力，与屏是多对多，**不要求一屏一域** |
