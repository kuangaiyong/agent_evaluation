## 引言

良好的评估能帮助团队更有信心地发布 AI 智能体。没有评估，团队很容易陷入"反应式循环"——只能在生产环境中发现问题，而修复一个故障又往往引发新的故障。评估（evals）能让问题和行为变化在影响用户之前就被看见，并且其价值会在智能体的整个生命周期中不断复利增长。

正如我们在《Building effective agents》（构建高效智能体）一文中所述，智能体跨越多轮运行：调用工具、修改状态、根据中间结果自适应调整。这些让 AI 智能体变得有用的能力——自主性、智能性和灵活性——同样也让它们更难评估。

通过我们的内部工作，以及与处于智能体开发前沿的客户的合作，我们学会了如何为智能体设计更严谨、更有用的评估。以下是在一系列智能体架构和真实部署场景中被验证有效的做法。

## 评估的结构

**评估（evaluation，简称 "eval"）**是对 AI 系统的一种测试：给 AI 一个输入，然后对其输出应用评分逻辑来衡量成功与否。本文重点讨论**自动化评估**——即在开发过程中无需真实用户即可运行的评估。

**单轮评估**很直接：一个提示词、一个响应、一套评分逻辑。对于早期的 LLM，单轮、非智能体的评估是主要的评估方式。随着 AI 能力的进步，**多轮评估**变得越来越普遍。

在一个简单的评估中，智能体处理一个提示词，评分器检查输出是否符合预期。而在更复杂的多轮评估中，一个编码智能体会获得工具、一项任务（例如本例中的构建一个 MCP 服务器）和一个环境，执行"智能体循环"（工具调用与推理），并用实现结果更新环境。随后通过单元测试来验证 MCP 服务器是否能正常工作，以此完成评分。

**智能体评估**则更为复杂。智能体跨越多轮使用工具，不断修改环境中的状态并随时自适应——这意味着错误会传播和累积。前沿模型还可能找到超越静态评估限制的创造性解法。例如，Opus 4.5 在解决 τ2-bench 中一个订机票的任务时，发现了政策中的一个漏洞并借此完成了任务。按评估原本的写法，它"失败"了，但它实际上为用户找到了一个更好的解决方案。

在构建智能体评估时，我们使用以下定义：

- **任务（task）**（也称问题或测试用例）：一个具有明确输入和成功标准的单一测试。
- **试次（trial）**：对任务的一次尝试。由于模型输出在多次运行间存在差异，我们会运行多个试次以获得更一致的结果。
- **评分器（grader）**：对智能体表现的某一方面进行评分的逻辑。一个任务可以有多个评分器，每个评分器包含多条断言（有时称为**检查项**）。
- **转录本（transcript）**（也称轨迹 trace 或 trajectory）：一个试次的完整记录，包括输出、工具调用、推理过程、中间结果以及所有其他交互。对于 Anthropic API 而言，这就是评估运行结束时的完整消息数组——包含评估期间对 API 的所有调用和所有返回的响应。
- **结果（outcome）**：试次结束时环境的最终状态。一个订机票智能体可能在转录本末尾说"您的航班已预订"，但结果要看环境的 SQL 数据库中是否真的存在一条预订记录。
- **评估基座（evaluation harness）**：端到端运行评估的基础设施。它提供指令和工具、并发运行任务、记录所有步骤、对输出评分并聚合结果。
- **智能体基座（agent harness，或称脚手架 scaffold）**：让模型得以作为智能体行动的系统：它处理输入、编排工具调用并返回结果。当我们评估"一个智能体"时，评估的是基座**和**模型协同工作的整体。例如，Claude Code 就是一个灵活的智能体基座，我们还通过 Agent SDK 使用其核心原语构建了长时运行智能体基座。
- **评估套件（evaluation suite）**：为衡量特定能力或行为而设计的任务集合。套件中的任务通常共享一个宏观目标。例如，一个客户支持评估套件可能测试退款、取消和升级转人工等场景。

## 为什么要构建评估？

团队刚开始构建智能体时，靠手动测试、内部试用（dogfooding）和直觉就能走得相当远。更严格的评估甚至可能被视作拖慢发布速度的额外开销。但在早期原型阶段之后，一旦智能体进入生产环境并开始规模化，没有评估的开发方式就会开始崩溃。

崩溃点往往出现在这样的时刻：用户反馈智能体在改动后"感觉变差了"，而团队如同"盲飞"，除了靠猜和试之外没有任何验证手段。没有评估，调试就是反应式的：等投诉、手动复现、修 bug，然后祈祷没有引入别的回归。团队无法区分真实的回归与噪声，无法在发布前用数百个场景自动测试变更，也无法衡量改进。

我们多次见证过这一发展过程。以 Claude Code 为例，它最初基于 Anthropic 员工和外部用户的反馈快速迭代；随后我们加入了评估——先是针对简洁性、文件编辑等较窄的领域，然后扩展到过度工程化（over-engineering）等更复杂的行为。这些评估帮助我们发现问题、指导改进，并聚焦研究与产品团队之间的协作。结合生产环境监控、A/B 测试、用户研究等手段，评估为 Claude Code 的规模化持续改进提供了信号。

在智能体生命周期的任何阶段，编写评估都很有价值。早期，评估迫使产品团队明确"智能体怎样才算成功"；后期，评估帮助守住一致的质量门槛。

Descript 的智能体帮助用户剪辑视频，因此他们围绕成功剪辑工作流的三个维度构建了评估：不能搞坏东西、做用户要求的事、并且要做好。他们从人工评分演进到由产品团队定义标准、定期人工校准的 LLM 评分器，现在定期运行两个独立的套件分别用于质量基准测试和回归测试。Bolt AI 团队起步较晚，在智能体已被广泛使用之后才开始构建评估。他们在 3 个月内搭建了一套评估系统：运行智能体并用静态分析给输出评分，使用浏览器智能体测试应用，并用 LLM 裁判评估指令遵循等行为。

有些团队在开发之初就创建评估；另一些团队则在规模化之后、评估成为改进智能体的瓶颈时才补上。评估在智能体开发早期尤其有用，因为它能把期望行为显式地编码下来。两位工程师读同一份初始规格说明，可能对"AI 应如何处理边界情况"得出不同理解，而一套评估套件能消除这种歧义。无论何时创建，评估都有助于加速开发。

评估还决定了你能多快采用新模型。当更强大的模型发布时，没有评估的团队要面临数周的测试，而有评估的竞争对手可以快速确定新模型的强项、调优提示词，并在几天内完成升级。

一旦评估就位，你就免费获得了基线和回归测试：延迟、token 用量、单任务成本和错误率都可以在一组静态任务库上持续追踪。评估还可以成为产品团队与研究团队之间带宽最高的沟通渠道——它定义了研究者可以据以优化的指标。显然，评估的价值远不止追踪回归与改进。它的复利价值很容易被忽视，因为成本是当下可见的，而收益是日后累积的。

## 如何评估 AI 智能体

我们看到目前规模化部署的智能体有几种常见类型，包括编码智能体、研究型智能体、计算机操作智能体（computer use agents）和对话智能体。每种类型的部署行业千差万别，但都可以用类似的技术来评估。你不需要从零发明一套评估方法。下面几节介绍了几类智能体的成熟评估技术，可以以此为基础，再扩展到你的领域。

### 智能体评分器的类型

智能体评估通常组合使用三类评分器：基于代码的、基于模型的和人工评分器。每个评分器评估转录本或结果的一部分。有效评估设计的关键组成部分，就是为工作选对评分器。

**基于代码的评分器（Code-based graders）**

| 方法 | 优势 | 劣势 |
|---|---|---|
| • 字符串匹配检查（精确、正则、模糊等）<br>• 二元测试（fail-to-pass、pass-to-pass）<br>• 静态分析（lint、类型、安全）<br>• 结果验证<br>• 工具调用验证（使用了哪些工具、参数）<br>• 转录本分析（轮数、token 用量） | • 快速<br>• 廉价<br>• 客观<br>• 可复现<br>• 易于调试<br>• 可验证特定条件 | • 对不完全符合预期模式的合法变体过于脆弱<br>• 缺乏细腻度<br>• 难以评估较主观的任务 |

**基于模型的评分器（Model-based graders）**

| 方法 | 优势 | 劣势 |
|---|---|---|
| • 基于评分细则（rubric）的打分<br>• 自然语言断言<br>• 成对比较<br>• 基于参考答案的评估<br>• 多裁判共识 | • 灵活<br>• 可扩展<br>• 能捕捉细腻差异<br>• 能处理开放式任务<br>• 能处理自由形式的输出 | • 非确定性<br>• 比代码更昂贵<br>• 需要与人工评分校准以保证准确性 |

**人工评分器（Human graders）**

| 方法 | 优势 | 劣势 |
|---|---|---|
| • 领域专家评审<br>• 众包判断<br>• 抽查采样<br>• A/B 测试<br>• 标注者间一致性分析 | • 黄金标准质量<br>• 符合专家用户判断<br>• 可用于校准基于模型的评分器 | • 昂贵<br>• 缓慢<br>• 往往需要大规模获取人类专家资源 |

对于每个任务，评分可以采用加权方式（组合后的评分器得分须达到阈值）、二元方式（所有评分器必须通过）或混合方式。

### 能力评估与回归评估

**能力评估（capability/quality evals）**问的是："这个智能体擅长做什么？"它的通过率应该一开始就很低，瞄准智能体目前吃力的任务，给团队一座要攀登的山。

**回归评估（regression evals）**问的是："智能体是否仍能处理它过去能处理的所有任务？"它应该保持接近 100% 的通过率。回归评估用于防止倒退，因为分数下降就意味着有东西坏了、需要改进。当团队在能力评估上爬坡时，很重要的一点是同时运行回归评估，确保改动不会在其他地方引发问题。

当智能体上线并优化成熟后，通过率很高的能力评估可以"毕业"，转变成为持续运行的回归套件，用于捕捉任何能力漂移。那些曾经衡量"我们到底能不能做到"的任务，从此开始衡量"我们是否仍能稳定做到"。

### 评估编码智能体

编码智能体编写、测试和调试代码，像人类开发者一样在代码库中导航并运行命令。对现代编码智能体的有效评估，通常依赖于规格明确的任务、稳定的测试环境，以及对生成代码的充分测试。

确定性评分器天然适合编码智能体，因为软件通常很好评估：代码能否运行？测试能否通过？两个广泛使用的编码智能体基准——SWE-bench Verified 和 Terminal-Bench——都遵循这一思路。SWE-bench Verified 给智能体提供来自热门 Python 仓库的 GitHub issue，通过运行测试套件来评分：解决方案只有在修复了失败测试、同时不破坏现有测试的情况下才算通过。LLM 在该评估上的成绩仅用一年就从 40% 提升到 80% 以上。Terminal-Bench 则另辟蹊径：测试端到端的技术任务，例如从源码构建 Linux 内核或训练一个机器学习模型。

一旦你有了一组"通过/不通过"的测试来验证编码任务的关键**结果**，通常也很有必要对转录本评分。例如，基于启发式规则的代码质量规则可以在"通过测试"之外评估生成的代码；带有清晰评分细则的模型评分器，可以评估智能体调用工具的方式或与用户交互的方式。

**示例：一个编码智能体的理论评估**

考虑一个编码任务：智能体必须修复一个身份验证绕过漏洞。如下面的示例 YAML 文件所示，可以结合多种评分器和指标来评估该智能体：

```yaml
task:
  id: "fix-auth-bypass_1"
  desc: "修复当密码字段为空时的身份验证绕过问题，并……"
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

注意，该示例为了演示而展示了全部可用的评分器类型。实践中，编码评估通常依靠单元测试验证正确性，再配合一个 LLM 评分细则评估整体代码质量，只在确有需要时才增加其他评分器和指标。

### 评估对话智能体

**对话智能体**在客户支持、销售或教练辅导等领域与用户交互。与传统聊天机器人不同，它们维护状态、使用工具，并能在对话中途采取行动。编码和研究型智能体也可能涉及与用户的许多轮交互，但对话智能体提出了一个独特的挑战：**交互本身的质量也是你要评估的一部分**。对对话智能体的有效评估，通常依赖于可验证的最终状态结果，以及能同时捕捉任务完成度和交互质量的评分细则。与大多数其他评估不同，它们往往还需要第二个 LLM 来模拟用户。我们在自己的对齐审计智能体中就采用了这种方法，通过长时间的对抗性对话对模型进行压力测试。

对话智能体的成功可以是多维的：工单是否已解决（状态检查）？是否在 10 轮以内完成（转录本约束）？语气是否得当（LLM 评分细则）？两个体现多维度的基准是 𝜏-Bench 及其后继者 τ2-Bench。它们模拟零售支持、机票预订等领域的多轮交互：一个模型扮演用户人设，智能体则在仿真场景中完成任务。

**示例：一个对话智能体的理论评估**

考虑一个支持类任务：智能体必须为一位恼怒的客户处理退款。

```yaml
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "智能体对客户的沮丧表现了共情"
      - "解决方案被清晰地解释了"
      - "智能体的回答以 fetch_policy 工具返回的结果为依据"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

与编码智能体的示例一样，该任务为了演示而展示了多种评分器类型。实践中，对话智能体评估通常使用基于模型的评分器来同时评估沟通质量和目标完成度，因为许多任务——比如回答一个问题——可能有多个"正确"解法。

### 评估研究型智能体

**研究型智能体**收集、综合并分析信息，然后产出答案或报告等成果。编码智能体有单元测试提供二元通过/失败信号，而研究质量只能相对于任务来判断。什么算"全面"、"来源可靠"甚至"正确"，都取决于上下文：市场扫描、收购尽调、科学报告，各自需要不同的标准。

研究型评估面临独特挑战：专家之间可能对一份综合分析是否"全面"存在分歧；参考内容不断变化导致标准答案漂移；输出更长、更开放，出错空间也更大。例如 BrowseComp 这样的基准，测试的是 AI 智能体能否在开放互联网上"大海捞针"——问题被设计成验证容易、求解困难。

构建研究型智能体评估的一个策略是组合评分器类型： groundedness（有据性）检查验证论断是否有检索到的来源支撑；覆盖度检查定义好答案必须包含的关键事实；来源质量检查确认所查来源是权威的，而不仅仅是第一个被检索到的。对于有客观正确答案的任务（"X 公司第三季度营收是多少？"），精确匹配即可。LLM 既能标记缺乏依据的论断和覆盖缺口，也能验证开放式综合内容的连贯性与完整性。

鉴于研究质量的主观性，LLM 评分细则应频繁地与专家人工判断校准，才能有效地评估这类智能体。

### 评估计算机操作智能体

**计算机操作智能体**通过与人类相同的界面与软件交互——截屏、鼠标点击、键盘输入和滚动——而不是通过 API 或代码执行。它们可以使用任何带图形用户界面（GUI）的应用，从设计工具到遗留的企业软件。评估需要在真实或沙箱环境中运行智能体，让它实际操作软件应用，并检查是否达成了预期结果。例如，WebArena 测试基于浏览器的任务：用 URL 和页面状态检查来验证智能体导航是否正确，并对会修改数据的任务做后端状态验证（确认订单真的被提交，而不只是出现了确认页面）。OSWorld 则将其扩展到完整的操作系统控制：评估脚本在任务完成后检查各种产物——文件系统状态、应用配置、数据库内容和 UI 元素属性。

浏览器操作智能体需要在 token 效率和延迟之间取得平衡。基于 DOM 的交互执行快但消耗大量 token，基于截屏的交互更慢但更省 token。例如，让 Claude 总结维基百科时，从 DOM 提取文本更高效；而在亚马逊上找一款新笔记本保护壳时，截屏更高效（因为提取整个 DOM 的 token 开销太大）。在我们的 Claude for Chrome 产品中，我们专门开发了评估来检查智能体是否为每种上下文选对了工具，这让我们能够更快、更准确地完成基于浏览器的任务。

## 如何理解智能体评估中的非确定性

无论哪种智能体类型，智能体行为在不同运行之间都会有差异，这使得评估结果比表面上更难解读。每个任务都有自己的成功率——这个任务 90%，那个任务 50%——而这次评估通过的任务，下次可能就失败。有时，我们想衡量的是智能体在一个任务上**多频繁**地成功（即在多大比例的试次中成功）。

有两个指标可以捕捉这种细微差别：

- **pass@k**：衡量智能体在 **k** 次尝试中至少得到一次正确解的概率。随着 k 增大，pass@k 分数上升："射门机会"越多，至少命中一次的概率越高。pass@1 为 50% 意味着模型在一半的评估任务上首次尝试即成功。在编码场景中，我们通常最关心智能体第一次尝试就找到答案——即 pass@1。而在其他场景中，只要有一个方案可行，提出多个方案也是合理的。
- **pass^k**：衡量**全部 k** 个试次都成功的概率。随着 k 增大，pass^k 下降，因为要求在更多试次中保持一致是更高的门槛。如果你的智能体单次试次成功率为 75%，运行 3 个试次，那么三次全过的概率是 (0.75)³ ≈ 42%。这个指标对面向客户的智能体尤为重要，因为用户期望每次都行为可靠。

pass@k 和 pass^k 随试次数增加而分化。当 k=1 时两者相同（都等于单次试次成功率）；到 k=10 时，它们讲述完全相反的故事：pass@k 趋近 100%，而 pass^k 跌到 0%。

两个指标都有用，选择哪个取决于产品需求：一次成功即有价值的工具选 pass@k，一致性至关重要的智能体选 pass^k。

## 从零到一：构建优秀智能体评估的路线图

本节给出我们经过实战检验的实用建议，帮助你从"没有评估"走到"值得信任的评估"。可以把这看作评估驱动开发的路线图：尽早定义成功、清晰地衡量它、持续迭代。

### 收集初始评估数据集的任务

**第 0 步：尽早开始**

我们看到很多团队推迟构建评估，因为他们以为需要数百个任务。实际上，从真实失败中提取 20–50 个简单任务就是很好的起点。毕竟在智能体开发早期，系统的每次改动通常都有清晰、显著的影响，效应量大意味着小样本量就足够了。更成熟的智能体可能需要更大、更难的评估来检测更小的效应，但一开始最好采取 80/20 策略。等得越久，评估越难构建。早期，产品需求可以很自然地转化为测试用例；等得太久，你就得从一个在线系统里反向推导成功标准。

**第 1 步：从你已经在手动测试的内容开始**

从开发期间手动检查的内容入手——每次发布前你会验证的行为、终端用户常做的任务。如果你已经在生产环境，看看你的 bug 跟踪系统和支持工单队列。把用户报告的失败转化为测试用例，能确保你的套件反映真实使用情况；按用户影响排优先级，可以帮你把精力投到最重要的地方。

**第 2 步：编写无歧义的任务并附参考解**

把任务质量做对，比看上去更难。一个好的任务，应该让两位领域专家各自独立评审也能得出相同的通过/失败结论。他们自己能完成这个任务吗？如果不能，任务就需要打磨。任务规格中的歧义会变成指标中的噪声。模型评分器的标准同理：模糊的评分细则会产生不一致的判断。

每个任务都应该能被一个正确遵循指令的智能体完成。这一点可能很微妙。例如，对 Terminal-Bench 的审计发现：如果一个任务要求智能体写一个脚本但没有指定文件路径，而测试假设了某个特定的脚本路径，那么智能体可能"非战之罪"地失败。评分器检查的所有内容都应该能从任务描述中明确得知；智能体不应因规格含糊而失败。对于前沿模型，如果跨多个试次的通过率为 0%（即 pass@100 为 0%），这多半是任务本身坏掉的信号，而不是智能体无能，也是在提醒你要复查任务规格和评分器。为每个任务创建一个参考解——一个已知能通过所有评分器的可行输出——会很有用。这既证明任务可解，也验证评分器配置正确。

**第 3 步：构建均衡的问题集**

既要测试某行为**应该**发生的情形，也要测试它**不应该**发生的情形。单边评估导致单边优化。例如，如果你只测试"该搜索时智能体是否搜索"，最终可能得到一个几乎什么都搜的智能体。尽量避免类别不平衡的评估。我们在为 Claude.ai 的网页搜索构建评估时就深有体会：难点在于防止模型在不该搜索时搜索，同时保留它在适当时候进行深入研究的能力。团队构建的评估覆盖两个方向：模型应该搜索的查询（比如查天气），以及模型应该凭已有知识回答的查询（比如"谁创立了苹果？"）。在欠触发（该搜不搜）和过触发（不该搜乱搜）之间取得平衡很困难，对提示词和评估都进行了很多轮打磨。随着更多样例问题的出现，我们也会持续补充评估以改善覆盖度。

### 设计评估基座和评分器

**第 4 步：构建稳健的评估基座和稳定的环境**

至关重要的是，评估中的智能体与生产中使用的智能体行为大体一致，且环境本身不引入额外噪声。每个试次都应从干净的环境开始，做到"隔离"。运行之间不必要的共享状态（残留文件、缓存数据、资源耗尽）可能导致由基础设施抖动而非智能体表现引起的相关性失败。共享状态也可能人为抬高成绩。例如，在一些内部评估中，我们观察到 Claude 通过查看先前试次留下的 git 历史，在某些任务上获得了不公平的优势。如果多个不同的试次因环境的同一个限制（比如 CPU 内存有限）而失败，那么这些试次并不独立——它们受到同一因素影响——评估结果就无法可靠地衡量智能体表现。

**第 5 步：用心设计评分器**

如前所述，优秀的评估设计需要为智能体和任务选择最合适的评分器。我们建议：尽可能用确定性评分器；在确有必要或需要额外灵活性时用 LLM 评分器；审慎地使用人工评分器做额外验证。

人们常有一种直觉，想检查智能体是否遵循了非常具体的步骤，比如以正确顺序执行一串工具调用。我们发现这种做法太僵硬，会导致测试过于脆弱，因为智能体经常能找到评估设计者没想到的合法路径。为了避免不必要地惩罚创造性，通常更好的做法是**给智能体的产出评分，而不是给它走的路径评分**。

对于包含多个组成部分的任务，要设置**部分得分**。一个正确识别了问题、验证了客户身份但没能完成退款的支持智能体，明显好于一开始就失败的智能体。重要的是在结果中体现这种"成功的连续谱"。

模型评分往往需要仔细迭代来验证准确性。LLM-as-judge 评分器应与人类专家密切校准，以增强"人工评分与模型评分之间几乎没有分歧"的信心。为避免幻觉，要给 LLM 留一条退路，比如指示它在信息不足时返回"Unknown（未知）"。另一个有效做法是创建清晰、结构化的评分细则，对任务的每个维度分别评分，并且每个维度用一个独立的 LLM-as-judge，而不是用一个裁判评所有维度。一旦系统足够稳健，只需偶尔进行人工复核即可。

有些评估存在隐蔽的失败模式：即使智能体表现良好，也会因为评分 bug、智能体基座的限制或任务歧义而得分很低。再老练的团队也可能漏掉这些问题。例如，Opus 4.5 最初在 CORE-Bench 上只得到 42%，直到一位 Anthropic 研究员发现了多个问题：僵化的评分——期望答案是"96.124991…"时给"96.12"判错；任务规格含糊；以及无法精确复现的随机性任务。在修复 bug 并改用约束更少的脚手架之后，Opus 4.5 的分数跳升到 95%。类似地，METR 也发现他们的时间跨度基准中有几个任务配置有误：任务要求智能体优化到一个明确给出的分数阈值，但评分却要求超过该阈值。这惩罚了像 Claude 这样遵循指令的模型，而无视给定目标的模型反而得了更高的分。仔细复查任务和评分器可以帮助避免这些问题。

还要让评分器能抵御绕过或投机取巧。智能体不应能轻易"作弊"。任务和评分器的设计应保证：通过评估 genuinely（真正）要求解决了问题，而不是钻了意料之外的空子。

### 长期维护和使用评估

**第 6 步：检查转录本**

不读大量试次的转录本和评分，你就无法知道评分器是否工作良好。在 Anthropic，我们投资建设了查看评估转录本的工具，并定期花时间阅读它们。当任务失败时，转录本会告诉你：是智能体真的犯了错，还是评分器拒绝了一个合法解。它还常常揭示智能体行为和评估行为的关键细节。

失败应该看起来是"公平的"：能看清智能体错在哪、为什么错。当分数不再爬升时，我们需要确信那是智能体表现的问题，而不是评估的问题。阅读转录本，是你验证评估确实在衡量真正重要之事的方式，也是智能体开发的一项关键技能。

**第 7 步：监控能力评估的饱和**

一个 100% 通过的评估能追踪回归，但无法提供改进信号。**评估饱和**指的是智能体通过了所有可解任务，没有留下任何改进空间。例如，SWE-Bench Verified 的分数今年从 30% 起步，前沿模型如今已接近饱和（>80%）。随着评估趋近饱和，进步也会放缓，因为只剩最难的任务。这会让结果具有欺骗性：巨大的能力提升在分数上只表现为微小增长。例如，代码审查初创公司 Qodo 起初对 Opus 4.5 并不满意，因为他们的一次性编码评估没有捕捉到该模型在更长、更复杂任务上的收益。作为回应，他们开发了一套新的智能体评估框架，从而获得了对进步清晰得多的图景。

按我们的经验，在没有人深入挖掘评估细节、阅读过一些转录本之前，我们不会对评估分数照单全收。如果评分不公平、任务含糊、合法解被惩罚，或者基座限制了模型发挥，评估就应该修订。

**第 8 步：通过开放贡献和维护，让评估套件长期保持健康**

评估套件是一个活的工件，需要持续关注和明确的归属权才能保持有用。

在 Anthropic，我们尝试了各种评估维护方式。被证明最有效的是：设立专门的评估团队负责核心基础设施，而大多数评估任务由领域专家和产品团队贡献，并由他们自己运行评估。

对 AI 产品团队来说，拥有并迭代评估应当像维护单元测试一样日常。团队可能在一些"早期测试看着能用"的 AI 功能上浪费数周，而一个设计良好的评估本可以提前暴露那些未被言明的期望。定义评估任务，是压力测试"产品需求是否具体得足以开工"的最佳方式之一。

我们建议实践评估驱动开发（eval-driven development）：在智能体还做不到的时候，就先为规划中的能力构建评估，然后迭代直到智能体表现良好。在内部，我们经常构建一些今天"够用"的功能，赌的是几个月后模型的能力。从低通过率起步的能力评估会把这一点显现出来。当新模型发布时，跑一遍套件就能快速看出哪些赌对了。

最贴近产品需求和用户的人，最有资格定义成功。以当前的模型能力，产品经理、客户成功经理或销售人员都可以用 Claude Code 以提交 PR 的方式贡献一个评估任务——让他们来！或者更好的是，主动为他们创造条件。

## 评估如何与其他方法配合，形成对智能体的整体理解

自动化评估可以在数千个任务上运行，无需部署到生产环境，也不影响真实用户。但它只是理解智能体表现的众多方式之一。完整的图景还包括生产环境监控、用户反馈、A/B 测试、人工转录本审查和系统化人工评估。

**理解 AI 智能体表现的各种方法概览**

| 方法 | 优点 | 缺点 |
|---|---|---|
| **自动化评估**：以编程方式运行测试，无需真实用户 | 迭代更快；完全可复现；不影响用户；可在每次提交时运行；无需生产部署即可大规模测试场景 | 前期建设投入较大；需要随产品和模型演进持续维护以防漂移；若与真实使用模式不符，可能造成虚假信心 |
| **生产环境监控**：追踪在线系统的指标与错误 | 揭示大规模真实用户行为；捕捉合成评估遗漏的问题；提供智能体实际表现的真实基准 | 反应式——问题先影响用户你才知道；信号可能有噪声；需要投入埋点建设；缺少评分基准答案 |
| **A/B 测试**：用真实用户流量比较变体 | 衡量真实用户结果（留存、任务完成）；控制混杂因素；可扩展且系统化 | 慢——需要数天到数周才能达到显著性，且要求足够流量；只能测试已部署的改动；若不能充分审查转录本，对指标变化背后"为什么"的信号较弱 |
| **用户反馈**：点踩、bug 报告等显式信号 | 能暴露你没预料到的问题；附带真实用户的真实样例；反馈通常与产品目标相关 | 稀疏且自选样；偏向严重问题；用户很少解释*为什么*失败；无法自动化；主要靠用户发现问题会对用户体验造成负面影响 |
| **人工转录本审查**：人工阅读智能体对话 | 建立对失败模式的直觉；捕捉自动化检查遗漏的细微质量问题；帮助校准"好"的标准并掌握细节 | 耗时；无法扩展；覆盖不一致；评审疲劳或评审者差异会影响信号质量；通常只给定性信号而非清晰的定量评分 |
| **系统化人工研究**：由受训标注员对智能体输出做结构化评分 | 多位人工标注员给出黄金标准质量判断；能处理主观或含糊的任务；为改进模型评分器提供信号 | 相对昂贵、周期长；难以频繁运行；标注者间分歧需要调和；复杂领域（法律、金融、医疗）需要人类专家开展研究 |

这些方法对应智能体开发的不同阶段。自动化评估在发布前和 CI/CD 中尤其有用——在每次智能体变更和模型升级时运行，是抵御质量问题的第一道防线。生产环境监控在上线后接管，用于发现分布漂移和意料之外的真实世界失败。A/B 测试在流量充足后验证重大变更。用户反馈和转录本审查是填补缺口的持续性实践：持续分拣反馈、每周抽样阅读转录本、按需深挖。系统化人工研究则应保留给 LLM 评分器校准，或用于以人类共识为参照标准的主观输出评估。

正如安全工程中的**瑞士奶酪模型**，没有任何单一的评估层能抓住所有问题。多种方法组合起来，从一层漏掉的失败会被另一层接住。

最有效的团队会组合这些方法：用自动化评估支撑快速迭代，用生产监控提供真实基准，用定期人工审查进行校准。

## 结论

没有评估的团队会陷入反应式循环的泥沼——修一个失败、造出另一个，无法区分真实的回归与噪声。而早做投资的团队看到的恰恰相反：开发不断加速，因为失败变成测试用例，测试用例防住回归，指标取代猜测。评估给整个团队一座清晰可攀的山，把"感觉智能体变差了"变成可行动的事项。价值会复利增长，但前提是你把评估当作核心组件，而不是事后补票。

模式因智能体类型而异，但这里描述的基本功是共通的：尽早开始，不要等待完美套件；从你看到的失败中采集真实任务；定义无歧义、稳健的成功标准；用心设计评分器并组合多种类型；确保问题对模型足够有难度；迭代评估以提升信噪比；阅读转录本！

AI 智能体评估仍是一个新兴、快速演进的领域。随着智能体承担更长的任务、在多智能体系统中协作、处理越来越主观的工作，我们也需要不断调整技术。随着我们学到更多，我们会持续分享最佳实践。
