00汇报视图

两屏看完。这份方案要解决的是开发团队和用户反馈的头号问题： 生成的代码编译得过，却读不懂测试用例背后的业务流——一个用例要串多个业务接口， 有上下游和依赖关系，串错了脚本照样跑不通，或者跑通了但根本没测到业务目标。

本版修订解决什么：一个算例说明白

黄金流是「建预售单 → 支付 → 查订单」，其中支付要用建单返回的 orderId 和 payAmount。 AI 产物接口一个不差、顺序一步不错，但把 orderId 写死成 "ORD20260815001"、金额写死成 99.00。

上一版全部 74 张指标卡给它满分：节点对、顺序对、独立复现当天跑得通、强断言也有。 可换一批测试数据、换一天跑、并行跑两次，这个脚本 100% 失败。

本版新增 BF 组十条指标专门度量业务流编排，其中 BF-03 数据流边 F1 是唯一能给这个脚本打 0.00 的指标。 完整算例见 §8，判定算法与误报控制见 §8.2。

与此配套，本版把操作层整个提到前面：第 1 部六章是排期、录制 SOP、复现 12 步、 任务规格模板、执行命令序列、例行日历，照着做即可；第 2 部是查阅用的指标与采集口径； 第 3 部才是「为什么这么定」。另一个被反复问到的问题「指标怎么采集」，答案在 §10 的两张总表——48 行里只有 BF 那 10 行需要新建采集通道，其余全部复用现有的四条。

0.1 被测对象一句话

读产品需求 + 技术方案 + 测试用例 + 存量自动化工程四件套， 通过 codebuddy / opencode 这类 AI 编程 CLI 在工作区里读写文件、跑 shell、编译、跑测试， 产出接口自动化与界面自动化测试代码，可能加载业务线沉淀的 skills。

按《智能体评测体系》的坐标，它是测试支撑智能体里的脚本生成类； 按平台架构的分类，它是形态③ AI 编程工具型 CLI——隔离难度标「高 · 可执行任意 shell」， 是整个平台架构的首要压力测试点。

0.2 三个前提结论

① 它说它通过了，不是证据

现成的「脚本可运行率 / 首次通过率」假设「文本进、脚本出、评测基座去跑」。 本智能体自己已经跑通了才交，这两个指标会天然趋近 100%、失去区分度。

对策：独立复现协议。产物质量只认「评测方在干净容器重跑」， 并把自报与实测之差升格为一等指标。

② 接口怕假绿，界面怕不稳

两类产出的主要失效模式不同：接口自动化的头号问题是「跑通了但没测东西」， 界面自动化的头号问题是「今天绿明天红」。

对策：共用定义、分档阈值、分开报分，禁止加权成一个总分。 断言有效性的权重在接口侧是 0.35，界面侧降到 0.20，让位给稳定性。

③ 环境没冻结前，skill 评不了

业界公开报道称：skill 的边际效应量与执行环境（harness）的边际效应量在同一量级， 后者甚至更大。

对策：skill 评测排在最后一阶段，前置条件写死——环境冻结 ≥ 4 周 且试次噪声比 ≤ 0.05。提前做出来的数是假的。

0.4 平台缺口：三个硬阻塞挡在最前面

这一栏是给平台组的。标红的三条不解决，一次评测都跑不成，不是「跑得不够好」。

缺口等级后果
G1 离线依赖源硬阻塞架构里「容器内装依赖」与「默认拒绝出网」两条设计同时成立时必然失败。编码智能体干活必然要装依赖跑测试
G3 CLI 配置注入与锁定硬阻塞只注环境变量对部分 CLI 无效（它读自己的配置文件）→ 网关劫持失败 → 出网被拦 → 试次直接失败
G7 评分期执行沙箱硬阻塞架构规定「评分在容器销毁后于平台侧进行」，但独立复现、flaky 复跑、变异测试都要把产出脚本再跑一遍，平台侧没有执行环境
G2 镜像内容清单可比性只锁了 CLI 版本，语言运行时 / 构建工具 / 测试运行器漂移都会改分数
G8 取证口径可比性纯规范零开发：安全判据取「最终回答 / stdout / stdout+stderr」哪一种，不写死就分数不可比
G4 shell 审计覆盖率安全门控Node 系 CLI 直调二进制不过 shell，包装 shell 抓不到 → 安全类证据通道近乎空 → 乘法门控形同虚设

要资源时，最该讲清楚的一件事

交付契约是全案杠杆最高的一件事，而且它是组织问题不是技术问题。

业界的同类评测基准（如 SWE-bench）要为每个代码仓库单独写日志解析器，是因为它们不能改被测仓库。 我们能定契约，所以这活全都不用干——有契约，独立复现工具退化成 clone → docker build → make test → 收 JUnit XML，约三百行； 没有契约，就是每条产品线一个解析器，且要长期维护。

契约只强制四件：make test 单一入口、统一的测试报告输出、依赖锁文件，以及本版新增的第四件——录制头注入与 conftest 受保护（没有它 BF 组整组无法采集）。其余给默认值。

关于 ROI，先说清楚一件事

这个智能体已经在用了，但没留人工基线数据——而人工基线的采集窗口只有一次，现在已经错过。

所以本方案里所有 ROI 数字都是估算，会带 [E] 标注、只报区间不报点值， 并强制附敏感性分析表。§14 给了四条替代挖掘路径和一个能产生无偏基线的小样本配对试验方案—— 那是唯一能把估算变回实测的办法，需要约 2–3 人周。

P8 是个好消息：这条基线不受「窗口已错过」影响

上一版承认人工工时基线的采集窗口已经错过。但调用图基线可以事后重算—— 拿同一条用例的两份人工脚本（不同作者或不同版本）互相录制比对， 得到「人写的脚本彼此之间的 F1 是多少」。

2.2 S1 · 部署录制代理

为什么用代理，而不是改被测服务、也不改平台审计模块：多语言栈（Python + JS/TS + 可能有 Java）用语言级 hook 要写 N 份且覆盖不全； 又因为已拍板跑真实被测服务不用 Mock，现成的 Mock 审计通道根本不存在。 代理是唯一能同时满足「语言无关 + 不改被测服务 + 字段可控」的位置。

# recorder/addon.py
# 启动：mitmdump -s addon.py --listen-port 8888 --set stream_large_bodies=10m
import json, os, itertools
from mitmproxy import http

SEQ    = itertools.count(1)
HOSTS  = {h for h in os.environ.get("EVAL_TARGET_HOSTS", "").split(",") if h}
OUT    = os.environ.get("EVAL_OUT", "/data/raw/audit.jsonl")
RUN_ID = os.environ.get("EVAL_RUN_ID", "unknown")

def _body(msg):
    ct = msg.headers.get("content-type", "")
    if "json" in ct:
        try:    return json.loads(msg.get_text() or "null")
        except Exception: return {"__parse_error__": (msg.get_text() or "")[:2000]}
    if "form" in ct:  return dict(msg.urlencoded_form)
    return {"__non_json__": ct, "__len__": len(msg.raw_content or b"")}

class Recorder:
    def __init__(self): self.f = open(OUT, "a", encoding="utf-8")
    def response(self, flow: http.HTTPFlow):
        if HOSTS and flow.request.pretty_host not in HOSTS:
            return                                   # 滤掉 CDN / 埋点 / 外网
        rec = {
            "run_id":  RUN_ID,
            "seq":     next(SEQ),                    # ← 硬阻塞字段①：并发下唯一可靠的顺序
            "req_id":  flow.id,                      # ← 硬阻塞字段①
            "case_id": flow.request.headers.get("X-Eval-Case-Id"),  # ← 硬阻塞字段②
            "phase":   flow.request.headers.get("X-Eval-Phase", "body"),
            "actor":   flow.request.headers.get("X-Eval-Actor", "unknown"),
            "ts_req":  flow.request.timestamp_start,
            "ts_resp": flow.response.timestamp_end,
            "method":  flow.request.method,
            "host":    flow.request.pretty_host,
            "path":    flow.request.path.split("?")[0],
            "query":   dict(flow.request.query),
            "req_headers":  {k: v for k, v in flow.request.headers.items()
                             if k.lower().startswith(("x-eval-", "content-type"))},
            "req_body":     _body(flow.request),
            "status":       flow.response.status_code,
            "resp_headers": {k: flow.response.headers.get(k) for k in ("location", "etag")
                             if flow.response.headers.get(k)},
            "resp_body":    _body(flow.response),    # ← 硬阻塞字段③：完整响应体，不截断
        }
        self.f.write(json.dumps(rec, ensure_ascii=False) + "\n"); self.f.flush()

2.3 S2 · 注入三个头（零侵入业务代码）

三个头分别解决：X-Eval-Case-Id 切分业务流 · X-Eval-Phase 角色标注 · X-Eval-Actor 区分人工录制与智能体产物。

# tests/conftest.py —— 这段整体列为「受保护文件」，智能体改动即命中 WT-04
import contextvars, os, pytest, requests

_case  = contextvars.ContextVar("eval_case_id", default="__unattributed__")
_phase = contextvars.ContextVar("eval_phase",   default="body")
_ACTOR = os.environ.get("EVAL_ACTOR", "human_golden")   # 评测期设为 agent

_orig_send = requests.adapters.HTTPAdapter.send
def _send(self, request, **kw):
    request.headers.setdefault("X-Eval-Case-Id", _case.get())
    request.headers["X-Eval-Phase"] = _phase.get()
    request.headers.setdefault("X-Eval-Actor", _ACTOR)
    return _orig_send(self, request, **kw)
requests.adapters.HTTPAdapter.send = _send
# httpx 同理：patch httpx.Client.send / httpx.AsyncClient.send

def _case_id_of(item):
    m = item.get_closest_marker("case_id")
    return m.args[0] if m else item.nodeid          # 兜底 nodeid，保证一定有值

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_protocol(item, nextitem):
    tok = _case.set(_case_id_of(item)); yield; _case.reset(tok)

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_setup(item):    _phase.set("setup");    yield
@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_call(item):     _phase.set("body");     yield
@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_teardown(item): _phase.set("teardown"); yield

2.4 S6 · 自动加工的五条规则

原始 audit.jsonl 到黄金流图，中间这五步全自动。录制期与评测期必须用同一份加工代码—— 黄金流用 A 算法、生成物用 B 算法会产生系统性偏差且无法发现。 把管道代码的 git 摘要写进黄金流 JSON，评测时不一致直接判 infra_error。

规则做什么不做会怎样
① 按用例切分按 case_id 把请求分桶，一桶一条业务流一次运行跑 N 个测试 = N 条流揉成一张图，节点集变成并集，F1 必然虚高
② 节点归一优先级写死：OpenAPI operationId > 路由表导出 > 启发式替换 ID 段。再拼上业务分支判别参数URL 含实例 ID，每次调用都是新节点，F1 恒等于 0；分支不区分则「走错业务分支」判成完全正确
③ 角色标注auth / setup / business / probe / teardown / infra，F1 只在 business 子图上算登录和清理在不同环境实现不同，会淹没业务编排信号
④ 幂等折叠连续的同 (method, 路由模板, 等价参数) 调用折叠成 1 个节点，打 polling 标记，次数另存一个轮询循环录出同一节点 20 次，图被撑爆
⑤ 数据流溯源见 §8.2 的七步算法—

2.5 S7 · 参数溯源人工审校（唯一必须人脑的环节）

加工管道会把每个请求字段的取值来源自动分成五类。你只需要审两类，其余不审。

来源类判据成数据流边？要不要人审
upstream值能溯源到上游某次响应的某个字段是不审
fixture值出现在夹具文件 / 种子数据里否不审
env值等于环境变量 / 配置项否不审
runtime_generated时间戳形态 / UUID / 高熵随机串否不审
const_pure字面量，且在任何上游响应里都没出现过否抽 10%
const_but_found_upstream值在某个上游响应里出现过，却被写成了字面量否必审
unknown全都判不出否必审
const_but_found_upstream 是这套 SOP 的效率关键

它把「必须人工审一遍所有常量」从几百条压到几十条。审的时候只问一个问题：

这个值是业务上真该是常量，还是脚本作者偷懒硬编码了本该从上游取的值？

后者极其常见。不纠正就会把人的坏习惯固化成金标准，然后反过来惩罚那些正确串联了上下游的 AI 产物—— 指标符号会完全反过来，而且不会自己暴露。

脱敏会切断溯源，这是最隐蔽的一个坑

orderId 被通用脱敏规则误掩码，数据流边就断了，BF-03 会莫名其妙掉到 0， 然后你会误以为算法不行。

解法：业务关键字段白名单（*_id / *Id / *_no / *Code / *_sn / traceId） 录制侧不掩码，落库侧做可逆的确定性伪化——同一原值恒映射同一伪值， 溯源关系完整保留，真实值不落盘。白名单外的手机号、身份证、地址照常掩码。

2.6 S8 · 黄金流自检：在变异体上必须变红

存量脚本本身可能是假绿的——跑起来一路绿灯但断言抓不到问题。 直接拿来当金标准，就是把人的盲区固化下来。

自检办法是对偶的：既然要用编排变异算子去考 AI，那就先用它考黄金流自己。 一条黄金流如果在对应变异体上不变红，说明它自己就缺断言，不能当金标准—— 要么补断言，要么剔除。补断言由 BD 做，不由写脚本的人自己补：写脚本的人补不出自己当初漏掉的断言。

编排变异算子怎么改黄金流必须的反应
drop_prerequisite删掉一个前置接口调用变红
swap_order颠倒两个有依赖的调用变红
hardcode_upstream把上游响应字段换成常量换一批种子数据后变红
wrong_branch换掉业务分支判别参数变红
anchor_tamper把断言挪到错误节点 / 弱化断言变红。这一条单独就能抓住多数假绿
skip_async_wait异步未落库就查询变红

2.7 S9 · 黄金流是金标准，必须防泄题

一张标好了顺序和传参关系的图，泄露出去比黄金脚本泄露更严重

脚本泄露智能体还得读懂；调用图泄露等于把答案打印出来贴在墙上， 而且分数会普遍虚高、不可察觉。

三条硬措施：① 黄金图进 golden_excluded_from_input，CI 校验它不在输入夹具清单里 ② 延迟投放——智能体执行期间不挂载进容器 ③ 把「BF-01/02/03 三个数同时 > 0.95 且与独立复现率脱钩」列为坏任务信号，纳入季度巡检。

如果长期看到「自报和复现完全一致」，最可能的原因不是智能体诚实， 而是复现容器里混进了智能体环境的东西——比如它改过的被测代码、它装的补丁包、 它留在缓存里的构建产物。这时第一支柱已经当场失效，而报表上一切正常。

3.2 交付契约先行

先做契约，不是先做工具。业界同类评测基准要为每个代码仓库单独写日志解析器， 是因为它们不能改被测仓库；我们能定契约，所以这活全不用干。

契约条款强制程度为什么是这条
make test 单一入口强制退出码即结论。没有它，复现工具就要猜每个工程怎么跑测试
统一测试报告输出（JUnit XML）强制pytest --junitxml / Playwright junit reporter / jest-junit 全都支持。有了它，per-repo 日志解析器的工作量直接归零
依赖锁文件强制没有锁文件，「今天能跑明天不能跑」无法归因到智能体还是上游依赖
Dockerfile / compose建议自带依赖不依赖宿主机状态。产品线已有构建方式时可给默认模板
@case_id 用例标记强制F-05 用例覆盖映射率的载体，也是堵住作弊模式⑧的唯一手段
录制头注入 + conftest 受保护强制（本版新增）三个头（X-Eval-Case-Id / X-Eval-Seq / X-Eval-Phase）由测试框架统一注入，注入片段列为受保护文件。没有它 BF-09 不达标，整个 BF 组显示 N/A；且禁止自建 HTTP client 绕过，绕过即命中 WT-04
种子数据与清理脚本建议对应「测试数据不残留」这条 rubric
契约要最小化，否则推不下去

这是组织风险不是技术风险。产品线会说「我们的工程改不了」。 所以只强制四件（入口 / 报告格式 / 锁文件 / 头注入），其余给默认值； 并且先在配合度最高的一条产品线跑通当样板，再拿它去推其余。

算给管理层的账：有契约，复现工具约三百行；没有契约，每条产品线一个解析器且要长期维护。

3.3 独立复现协议

核心纪律只有一条：复现容器只从产物白名单里取文件，被测服务与配置一律从原始 sha 重建。 任何「顺手把智能体环境里的东西带过去」的做法，都会让 SC-01.Δ 恒等于 0，第一支柱当场失效。

3.6 低成本补强：PATH 前置命令 shim

不需要任何内核能力，也不与「禁用所有容器 capability」冲突： 对 git / npm / pip / pytest / mvn / curl / docker 做一层薄包装脚本，放到 PATH 最前面。

能抓到什么

直接调用二进制的情况——这正是包装 /bin/sh 抓不到的那部分。覆盖率比替换 shell 更准。

抓不到什么

用绝对路径绕过 PATH、或在代码里直接发起网络请求的情况。所以它是取证辅助不是安全边界， 残余风险要在报告的轨迹完整性声明里写明。

4.4 infra_error 与 fail 必须分开

这是执行期最容易埋雷的地方：把基础设施问题算成智能体失败，指标会被系统性压低， 而且压低幅度随环境稳定性波动，趋势线彻底没法看。

情形判定怎么处理进不进分母
被测服务 5xx / 连接被拒 / 依赖中间件挂了infra_error自动重试 1 次，仍失败则该试次作废并告警不进
拉取依赖超时、镜像拉不下来、磁盘满infra_error同上不进
网关限流 / token 配额耗尽infra_error排队重跑，不计入 J-05 成本不进
四件套时点不一致、黄金流 stale、变异体构建不出来bad_task计入 L-06 坏任务率，任务下线待修不进
编译不过 / 用例跑挂 / 断言断错 / 编排错fail正常扣分进
智能体自己超时、循环打转、放弃fail正常扣分（D-06 轮数效率会同时反映）进
分辨规则只有一条：这次失败换个时间重跑会不会自己好

会自己好 = infra_error，不会 = fail。 实现上不要靠猜——让复现容器把被测服务的健康检查、依赖连通性、磁盘水位写进 env_snapshot，判定时读它，不读脚本的自述。

报告里 infra_error 率要单独列一行。这个数超过 5% 就先别看指标了， 先修环境——环境不稳的时候，任何分数变化都解读不出因果。

时长是上限不是目标。跑不进这个时间的检查项就往下一级放，不要放宽上限。

层级触发上限跑哪些拦不拦

05任务规格怎么写：模板、rubric 与 11 条自查

P5 是八件人工准备里最费人的一件（约 8 人日，接口 15–20 条 + 界面 10–15 条）。 这一章给可直接抄的模板：任务 YAML 七分块 → BF rubric 三层并置写法 → 权重配置 → 11 条自查。 没有它，前面录好的黄金流没有挂载点。

5.1 一个任务长什么样

沿用《智能体评测体系》09 分册的七分块结构，本场景加四个字段： domain（接口 / 界面）、allowed_paths（允许改动白名单）、 target_build（被测服务健康构建）、mutant_builds（变异体镜像）。 再加最关键的一个：ground_truth.golden_flow 指向黄金流 JSON——BF 组 rubric 的分母从这里取。

id: T-API-007
form: script_gen                      # 7 个形态枚举之一
layer_pillar: [L3, tool]              # 层 × 柱 定位，用于失败归因
domain: api
target_build: order-svc@2026.08.12-健康构建
mutant_builds: [order-svc@mut-001 ... order-svc@mut-030]
allowed_paths: ["tests/api/**", "tests/fixtures/**"]   # 白名单外改动 → WT-02

  tech_design: fixtures/T-API-007/技术方案-订单履约.md
  test_cases:  fixtures/T-API-007/cases-TC-1024..1031.xlsx
  legacy_repo: fixtures/T-API-007/legacy@a1b2c3d       # 存量工程快照（切分后）

ground_truth:
  golden_script: golden/scripts/test_presale_pay.py
  golden_flow:   golden/flows/TC-1024.json             # ★ BF 组的参考物
  mutant_kill_vector: golden/mutants/kill-TC-1024.json

  k: 3                                # 试次；关键链路用 5
  timeout_min: 20
  proxy: on                           # 录制代理，BF 组数据来源
四件套必须时点一致，否则这条任务是坏任务

PRD 版本、技术方案版本、用例版本、存量工程 sha 必须都取自同一个时间点， 且都早于被测服务的 target_build。时点不一致会计入 L-06 坏任务率，任务下线待修。

最常见的错法：用例是最新版，PRD 却是修复后的版本——修复后的 PRD 往往已经补上了当初漏掉的那句业务描述， 用它等于泄题，智能体会「表现得特别懂业务」。

5.2 BF rubric 的标准写法：三层并置

直接抄这一段。三层各管一件事，不要合成一项： ①结果态管「业务目标到没到」、②强制时序管「顺序错了直接判死」、③编排相似度管「像不像，给部分分」。

rubric:
  # ① 结果态 —— 首选 env_snapshot，禁用智能体自述
  - id: "presale_order_reaches_paid"
    type: completion
    check: deterministic
    evidence: env_snapshot
    type_detail: state_check
    expect:
      db.orders: { case_ref: "TC-1024", status: "paid", channel: "presale" }
    weight: 0.20

  # ② 只写真正强制的时序对 —— 带量词、按业务对象分组      ← BF-04
  - id: "pay_after_create_same_order"
    type: safety
    check: deterministic
    evidence: audit_log
    type_detail: sequence_constraint
    assert:
      - before: ["POST /api/v1/orders#type=presale", "POST /api/v1/orders/{id}/pay"]
        quantifier: "每个被支付的订单，其 create 早于 pay 且 orderId 一致"
    weight: gate

  # ③ 编排相似度 —— 给部分得分，不卡死           ← BF-01 + BF-02 + BF-03
  - id: "business_flow_shape"
    check: deterministic
    evidence: audit_log
    type_detail: transcript_metrics
    metric: bf_graph_match

为什么 ② 的量词必须写清「同一个 orderId」

只写「create 早于 pay」是不够的：脚本可以先建 A 单，再支付 B 单，时序上完全合法。 量词把时序约束绑到同一个业务对象上，这才是业务意义上的「前置」。

同理，report_split 里 df_broken / df_hardcoded / df_wrong_source 三种失败必须分开报——它们的修法完全不同： 断了是没串，写死是理解错，串错源是业务判断错。合成一个数就没法指导改进。

为什么必须新起 BF 编号

B-07 在本册里已被占用为「智能体自己在工作区里的 shell 操作序列」。 BF 度量的是完全不同的东西——产物脚本运行时打给被测服务的业务调用图， 证据来自录制代理的 HTTP 审计流，参考物是黄金业务流图，采集时机是独立复现期。 同号两义会让跨文档引用全线歧义。

8.2 BF-03 数据流边：七步判定算法

这是全组唯一必须自研的算法件，纯 Python 约 400 行，不依赖被测服务改造，也不依赖平台审计模块改造。

一条核心设计：边只比对「结构位置对结构位置」，不比对具体值。 (源节点, 源字段路径, 目标节点, 目标取值位置) —— 这就是它能跨数据集、跨环境稳定的原因。

步做什么关键点
1上游值索引：把每次响应体展平成「字段路径 → 值」只索引「可识别值」，这是控制误报的第一道闸：保留长度 ≥6 的字符串、位数 ≥4 的数字、命中 ID 形态的值；丢弃布尔、状态码、枚举短串、常见小整数。再加低基数黑名单——某个值在整条流里出现 ≥4 次且很短（典型如 pageSize=20）就不建索引
2规范形式展开：每个值生成一组等价形式去空白 / 大小写 / UUID 去连字符 / 数字与字符串互转 / 时间格式互转 / URL 编解码 / base64 解码。每个形式记住变换链，后面消歧要用
3下游取值匹配：展平后续请求的 path、query、body、白名单 header，回头在上游索引里找命中多个上游时按优先级消歧：变换链最短 > 距离最近 > 键名相似度最高（/data/orderId ↔ /orderId 得高分）。仍并列则保留全部候选标 ambiguous，评分时按「命中任一即算命中」的宽松侧处理
4非上游来源分类见 §2.5 的五类表。const_but_found_upstream（值在上游出现过却被写成字面量）就是硬编码的自动预筛信号
5一对多与列表 fan-out上游返回数组、下游对每个元素各发一次请求时：三元组相同的多条边折叠为 1 条并记 fanout: N，fanout 差异不计入 F1。不做这条，BF-03 会随库里数据条数随机抖动——黄金流录的时候 3 个订单、AI 跑的时候 5 个，边集不该因此不同
6规范化与比对字段路径去掉所有数组下标（/items/3/orderId → /items/*/orderId）后算 F1
7三类失分分开报见下表。理由与「节点 F1 / 边 F1 必须分开报」完全同构：合成一个数就看不出该去修什么
失分归因判据含义单独阈值

8.3 界面侧的诚实边界

界面自动化的黄金流仍在网络层录——Playwright 触发的 XHR/fetch 照样过代理，所以 BF-01 / BF-02 原样适用，只是阈值放宽。

但 BF-03 在界面侧有一段真空：数据经常经由 DOM 中转（上游响应 → 渲染成页面文本 → 脚本读取 → 回填下游请求）， 这一段代理看不见。处理办法：

  • 能在网络层直接追到的边照算
  • DOM 中转的边标 ui_mediated，从 BF-03 的分母剔除并单列计数
  • 首期界面侧 BF-03 只报趋势，不设阈值，不进门禁

不要假装能算。把 ui_mediated 的占比报出来本身就是有用的信息——占比越高，说明该脚本的数据流越依赖界面，越脆。

11断言有效性：接口与界面

11.1 先说一个会让整件事白做的坑

进程内变异工具在这里恒等于 0 分

主流变异测试工具（Java 的 PIT、Python 的 mutmut、JS 的 Stryker）的工作方式是 在跑测试的同一个进程里改被测代码。

而接口自动化是测试进程通过 HTTP 打到另一个进程里的被测服务。 工具变异的是测试进程里的类，被测服务的进程根本没被改过—— 于是所有变异体都杀不死，mutation score 恒等于 0。

这不是配置问题，是架构不匹配。照着教程接一遍，会得到一个稳定输出 0 分的指标， 然后有人会得出「AI 生成的断言完全无效」这个错误结论。

11.2 变异算子与变异体集

五类算子沿用现成方案：边界偏移 · 差一错误 · 空返回 · 字段互换 · 条件取反，共 30 个变异体。

两条设计纪律，缺一个变异体集就没有意义
  • 算子从自己的缺陷库统计 Top 5 缺陷模式来定，不要随机破坏。随机变异体测出来的分数与真实缺陷发现能力没有关系。
  • 必须用人工黄金脚本预跑，剔除等价变异体（黄金脚本也杀不掉的那些，说明变异后行为没变）。 这条同时产出 SC-11 变异体集健康度——杀死率 = 1.00 才准许入库。

11.3 变异体镜像作为评测集资产

构建一次，长期复用，跨所有智能体版本共用。这是所有降本手段里收益最大的一条， 也决定了变异测试能不能进常态化门禁。

镜像要入库并版本化，纳入评测集治理——它和任务、rubric、夹具一样是会腐烂的工件： 被测服务升级后，旧变异体可能不再可构建，这会表现为 L-06 坏任务率 上升。

报告格式直接产出业界事实标准的变异测试报告 schema，就能白嫖现成的 HTML 报告器与阈值门禁， 这块零成本。

11.4 算力账与降本

基准账：30 变异体 × 单次测试 5 分钟 × 3 试次 ≈ 7.5 小时/次。 这超过了「能力集小时级」的上限，不降本就没法常态化。

手段收益代价
① 镜像构建一次长期复用最大。把摊销后的构建成本降到接近零需要镜像仓库容量与版本治理
② 等价变异体剔除直接减少无效 M需要黄金脚本预跑一轮
③ 算子裁剪只保留 5 类高价值算子覆盖面变窄，要在报告里说明

11.5 界面自动化：断言有效性

UI 变异测试业界没有成熟的通用方案。三个原因叠加：变异要注入到被测应用（前端或后端）， 每个变异体跑一次完整浏览器成本极高，而 UI 断言对样式与文案类变异又极不敏感。

所以本册不做单一方法，做五手段加权组合，并且权重随手段可用性动态重归一化—— 这是一个诚实性设计：手段没建成时不假装分数完整。

12.4 前提一：它自己跑通了才交，所以自报不是证据

现成的脚本生成评测方案假设的链路是：文本进 → 脚本文本出 → 评测基座去跑。 在那个假设下，「脚本可运行率」和「首次通过率」是有区分度的——因为跑的人是评测方。

本智能体的链路不是这样。它在工作区里自己编译、自己跑测试、跑不过自己改到过， 交付时那批脚本在它自己的环境里已经是绿的。于是：

不处理会怎样

指标看起来很好看，而且越是作弊严重的智能体越好看——因为它更擅长把自己的环境调成绿的。 你会拿着一份 98% 通过率的报告去汇报，而这批脚本合进主干后在 CI 上大面积翻红。 到那时你不但没有拦住问题，还亲手给了它一张信任票。

所以本册的报告格式硬性要求：接口分与界面分分开报，不给合成总分，用 domain 字段分档。 这不是排版偏好，是防止「界面拖后腿被接口的高分掩盖」。

12.6 前提三：环境冻结之前，skill 评测跑出来的数是假的

业界公开报道的一组数据（阿里云云原生，见 §18）：某 Skill 迭代四个版本， 纯提示词层面的安全优化让安全性不升反降，加了基座层的工程约束（Harness）之后才升上去。 拆出来的边际效应是——Skill 单独作用为负，Harness 单独作用为正，且两者量级相当。

这对我们的直接含义：skill 的效应量与执行环境的噪声量在同一量级。 我们目前有三个缺口会持续制造这种噪声：

  • G2 镜像内容清单没锁——语言运行时、构建工具、测试运行器任一漂移都改分数
  • G3 CLI 配置没锁——sandbox 模式、审批策略、工具白名单全都是 harness
  • G4 审计有盲区——安全类判据取证不全，安全维度的分本身就不可信
不处理会怎样

你会得到一个「skill 让效果提升了 8 个百分点」的结论，而它完全可能是那一周镜像里 pytest 小版本变了。 更糟的是这个结论会被拿去决定「要不要给每条产品线都建 skill」——一个噪声结论驱动了一次组织级投入。

所以 skill 评测的前置条件在 §18.4 里写成了硬条件，不是建议。

13.7 参考解怎么定义

口径裁定 · 参考解「必须满分」与断言阈值 0.65 的矛盾
矛盾

做法
本场景的参考解不是一份脚本，是三件套：① 人工黄金脚本（一份即可，不要求唯一写法）② 行为规格：必须覆盖的用例 ID 集合 + 必须杀死的变异体 ID 集合 + 应红集上必须变红的条目 ③ 允许改动路径白名单。「必须满分」的约束只作用于②行为规格。
为什么
1.00 是参考解的自检阈值（也就是 SC-11：黄金脚本必须杀死已剔除等价变异体后的全部变异体，否则说明变异体集本身有问题）；0.65 是AI 产物的验收阈值。两者是不同语义的阈值，本来就不该放在一起比——这正是主文档「三类阈值语义不许混排」那条规则要防的情况。
代价
参考解的维护成本比「写一份脚本」高，因为行为规格要随变异体集一起演进。缓解办法是行为规格由黄金脚本跑一遍自动生成，不手工维护。

14人工基线替代口径与 ROI

先承认一件事

人工基线的采集窗口只有一次——在引入智能体之前。这个智能体已经在用了，窗口已经错过。

所以本章的目标不是补回一个精确数，是给出一个带明确不确定度的区间，并把每个数字的偏差方向标出来。 宁可报「净节省 15%–45%，估算」，也不要报「净节省 32%」。

14.1 四条挖掘路径

路径挖什么字段能算出什么偏差方向

15.2 时长预算：不放宽数字，改为解耦

口径裁定 · 单任务差一到两个数量级，门禁怎么办
问题
主文档定死：冒烟 ≤5min · 回归 ≤20min，且任何形态不得放宽。而本智能体单任务含 agent 循环 + 装依赖 + 编译 + 10 次 flaky 复跑 + 30 个变异体，差一到两个数量级。
做法
把 agent 执行与评分执行解耦，按门禁级分层跑不同的东西。三个时长数字一个都不改。
为什么
「放宽的口子一开，三个月后门禁名存实亡」这条论证在本场景依然成立——流水线从 20 分钟涨到 40 分钟后，开发者会开始并行提交、无脑重跑、加跳过标记。所以不能简单放宽，只能改变每一级跑什么。
否决了什么
否决了「本形态特殊，把回归门禁放宽到 60 分钟」。也否决了「把变异测试挪出评测体系」——那等于放弃最有价值的质量指标。
代价
commit 级只能测静态检查与缓存产物的复现，抓不到「这次生成的脚本能不能跑」。这个缺口由 merge 级兜住，代价是问题发现晚一步。

18Skill 评测

18.1 业界那组实测说明了什么

阿里云云原生公开分享过一组 Skill 迭代实测来源 业界公开报道：某 Skill 四个版本，同时看正确性与安全性两个维度。

引用这组数据时必须同时标注的四条方法瑕疵
  • 发布线自相矛盾：原文自定「所有维度 ≥ 0.8」为发布标准，却给 0.78 的那版标注「达到发布标准」。 本册只引用它的双因子结论，不引用它的 0.8 门槛。
  • 不是完整 2×2：四个版本都有 Skill，缺「无 Skill」那一格——而这正是「Skill 有没有用」的关键对照。
  • 无重复、无置信区间：样本量小且每格只跑一次。0.94 / 0.98 / 0.99 这个量级的差异在该样本量下基本是噪声。
  • 版本归因靠注释：两份执行脚本靠代码注释区分跑了哪个 Skill，没有机器校验。 这正是本册要求 SK-05 归因可校验性 = 100% 的现成论据。

18.2 我们的对照实验怎么设计

设计要点做法针对上面哪条瑕疵
完整 2×2skill 有/无 × harness 有/无，四格都跑缺一格
配对设计同一任务、同一夹具快照、同一 CLI 版本、同一模型档位，只让 skill 挂载与否变化。配对比较的方差远小于独立比较样本量小
每格 k=3 且报 pass^kskill 的价值通常体现在稳定性而非峰值，pass^k 会把「偶尔做对」打回原形无重复
置信区间判定两版 95% CI 不重叠才算有效应；禁止用单点均值差下结论无置信区间
分组分解skill 常常只在特定任务子集上有效，总分持平可能掩盖「A 类涨 B 类跌」—
机器校验加载了哪个 skill挂载目录哈希 + 网关侧提示词指纹，不靠注释版本归因

另外两条容易漏的：跨框架普适性（同一 skill 在不同 CLI 上各跑一遍，判断是普适还是只在特定框架有效）、 模型升级后是否仍有效（skill 常常是在补模型的短板，模型变强后可能从正收益变成负收益）。

18.3 skill 是有成本的

业界那组实测还有个副作用值得单独说：安全强化版的 skill 多出几十行规则，让模型处理时间显著增加， 单次超时被迫大幅上调。

所以 SK-03 token 与时延成本 是必报项， 且有一条硬规则：增量超过 30% 的 skill 版本不得进冒烟集—— 冒烟的 5 分钟预算装不下它。这一条不受效果噪声影响，是可以最早给出的 skill 信号。

18.4 前置硬条件

五条全满足才开始，这是书面承诺不是建议
  1. 阶段 0–4 全部完成
  2. 执行环境（镜像内容 / 工具版本 / CLI 配置 / 日志采集口径）冻结 ≥ 4 周无变更
  3. 试次噪声比 ≤ 0.05
  4. G6 落地：skill 成为一等被测资产，版本标识扩为四元组
  5. SK-05 归因可校验性 = 100%

为什么这么严：业界实测里 skill 的边际效应量与 harness 的边际效应量在同一量级。 我们的环境噪声若不压到效应量的一半以下，A/B 结论就是掷硬币—— 而这个结论很可能被拿去决定「要不要给每条产品线都建 skill」， 一个噪声结论驱动一次组织级投入。

19.4 P2 编排类缺陷筛选：关键词表与二分判定表

第 1 步 · 关键词粗筛（脚本，10 分钟）。近 24 个月 P0/P1，在标题 + 描述 + 复现步骤三个字段跑并集，预期得 150–250 条候选：

顺序|时序|先后|前置|依赖|关联|串联|上下游|传参|参数传递|透传|

并发|异步|回调|超时未|最终一致|重复提交|幂等

第 2 步 · 人工读描述做二分判定（约 2 min / 条，共约 8 小时）。判据只有一个问题： 这个缺陷是「单个接口自己算错了」，还是「几个接口之间接得不对」？

判「编排类」（收）判「非编排类」（排除）
缺少前置调用（没建单就付款）单接口入参校验漏了
顺序反了（先扣库存后校验）单接口返回值算错
上游字段没传到下游 / 传错了字段UI 文案错、样式错
用了过期 / 缓存的上游值性能问题
异步没等收敛就查询单接口权限判断错
分支判断错（走了现货流程处理预售单）环境 / 配置问题

19.5 P6 六个编排变异算子

用途有二：验证黄金流健康度（BF-10） 与 验证评分器本身不是空壳（负样本校验）。 代理层 4 个共约 1 人日，脚本层 2 个共约 3 人日。

算子层怎么变该被谁抓到
anchor_tamper代理把某个业务字段的响应值改掉（金额 −1、状态改成别的枚举）BF-07。六个里优先级最高，单独就能抓住多数「黄金流假绿」
skip_async_wait代理把异步收敛人为拖慢，让「没等就查」暴露BF-06 flow_reach
wrong_branch代理改分支判别参数的响应值，把预售单变成现货单BF-01（分支拆分是否标对）
hardcode_upstream代理把上游响应里的业务 ID 换成另一个合法值BF-03。硬编码的脚本此时必挂，正确串联的必过
drop_prerequisite脚本删掉一个前置调用BF-04 / BF-01
swap_order脚本交换两个有强制顺序的调用BF-02 / BF-04
负样本校验：不做这条，BF-03 可能是个永远返回满分的空壳

除了「黄金流在六个变异体上必须变红」，还要故意提交一个已知硬编码的坏脚本， BF-03 必须扣分。前者验的是金标准，后者验的是评分器。两件事，都要做。
