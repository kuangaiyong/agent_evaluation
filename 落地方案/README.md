## 这份方案在解决什么

被测智能体读产品需求、技术方案、测试用例、存量自动化工程四件套，通过 codebuddy / opencode 这类 **AI 编程 CLI** 在工作区里干活——读写文件、跑 shell、**自己编译、自己跑测试、跑不过自己改到过**，产出接口自动化与界面自动化测试代码。

**头号真实问题（开发团队与用户反馈）**：生成的代码编译得过，却**读不懂测试用例背后的业务流**——一个用例要串多个业务接口，有上下游和依赖关系；串错了脚本跑不通，或者跑通了但根本没测到业务目标。

一个算例说明为什么现有指标抓不住它：黄金流「建预售单 → 支付 → 查订单」，AI 产物**接口一个不差、顺序一步不错**，但 `orderId` / `amount` 写死。节点 F1 满分、时序边 F1 满分、独立复现当天跑得通、强断言也有——**上一版 74 张卡全给满分**，而换一批数据、换一天跑，这脚本 100% 失败。

所以本版新增 **BF 组（业务流编排正确性）十条指标**，其中 **BF-03 数据流边 F1** 是唯一能给它打 0.00 的一条。

## 四件已拍板的事

1. **业务流编排是第一支柱**，独立复现协议退居第二。黄金业务流**从存量人工脚本自动录制**（透明 HTTP 代理），不手工画图。
2. **接口与界面同等深度**。界面侧也做断言有效性度量，但 UI 变异测试业界无成熟方案，改用五手段加权组合 + 动态重归一化。
3. **人工工时基线窗口已错过**（智能体已在用但没留数据），所有 ROI 数字标估算、只报区间。**但调用图基线不受影响**——两份人工脚本互比可事后重算，这是本版新增的一条实测路径。
4. **多语言栈**（Python + JS/TS + Java，部分产品线未统一），所以录制代理做在**网络层**而非语言层，变异体镜像流水线语言无关。

## 与主文档的关系

**凡主文档已裁定的，本册只引用不复述。** 指标卡与通用指标总表的「原定义 ↗ / 原文」直达主文档对应锚点，共 **50 条跨文档引用（42 个唯一锚点）**。

指标构成：**50 张卡 = 通用重定义 8 + 特有 42**（BF 业务流编排 10 / SC 脚本产物 15 / WT 工作区可信 8 / RU 存量复用 4 / SK Skill 5）。另有**通用指标总表 42 行**（只写本场景含义，不复述原定义）。**核心指标 6 个。**

> BF 组**必须新起编号，不能复用 B-07**：B-07 在本册已被占用为「智能体自己的 shell 操作序列」，而 BF 度量的是**产物脚本运行时打给被测服务的业务调用图**，证据通道也不同（命令审计 vs 录制代理 HTTP 流）。

## 改动后必跑的校验

与主文档同一套，另加**本册特有的三项**：

- 明暗双主题对比度 computed styles 实算 · 375/768/1280/1440 四宽度无横向滚动 · 离线 0 外部请求 · 站内锚点 0 悬空 · id 唯一 · SVG 无硬编码色且每个 `<text>` 带 `on-*` 类 · 图号按章连续 · 密钥扫描 · 交互逐个点过
- ⚠️ **跨文档锚点有效性**：所有指向 `../智能体评测体系/智能体评测体系.html#...` 的锚点必须在那份 HTML 里真实存在。主文档改动章节结构时，这里会断
- ⚠️ **第 1 部篇幅占比**：第 1 部占正文（剔除指标字典这一纯查阅章）应 ≥ 30%。这是「操作层前置」是否真做到的量化自查
- ⚠️ **代码块 ≥ 12 段**且覆盖五段骨架（mitmproxy addon · pytest conftest · Playwright · Java OkHttp · 黄金流 JSON Schema）。可复制代码块是「拿到就能照着做」的实体，占比过低就会退回理论化

> 章号、小节号、图号、`§X.Y` 交叉引用标签**全部由装配脚本按最终顺序自动重算**，不要在分片文件里手写死——重排章节时手写的号一定会错位。

## 第 1 周就能开始，不依赖平台

**W1 只有三件事**：部署录制代理（PE）· 存量脚本注三个头并跑前置检查（TA）· 契约补两条（EO）。都不依赖评测平台。

**W4 是全案唯一的关键路径节点**——S7 参数溯源人工审校那 2 人日堵住，后面全停。那一周要把业务侧的其他事排开。

**G1（离线依赖源）、G3（CLI 配置注入）、G7（评分期执行沙箱）三个平台缺口要同期开工**——它们不解决，第一次完整评测跑不成。新增的 **G11（录制代理与加工管道）可自建、不必等平台**，但它依赖 G7。
