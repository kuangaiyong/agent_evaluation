## 文档体系的架构

### 两条正交轴（全套材料的索引）

- **四支柱**（被测对象解剖，来自 arXiv:2512.12791）：模型与推理 / 工具 / 记忆 / 环境与交互
- **五层**（评测颗粒度）：L1 单元 / L2 任务 / L3 场景 / L4 系统 / L5 价值

任一指标、任务、失败案例都必须能定位到"层 × 柱"矩阵的某个格子。新增内容如果落不进格子，说明框架理解错了。任务 YAML 的 `layer_pillar:` 字段就是这个定位，用于失败归因。

### 分册的依赖方向

`00-总纲` 是**权威**：术语表、四支柱、五层、三条原则、打分公式、绘图约定全在这里定死，其余 9 册对齐它。改 00 会波及全套。

```
00 总纲（框架与术语）
 └→ 01 指标字典 · 02 评测集治理 · 03 评分器与 Judge 校准     ← 通用底座
      └→ 04 产品智能体（四形态）· 05 测试支撑智能体（三类）   ← 两本应用分册
           └→ 06 平台架构 · 07 流程协同                      ← 工程落地
                └→ 08 成熟度模型 · 09 模板与附录
```

04 和 05 是**并列的两类被测对象**，不是主次关系：04 是公司产品（对话/RAG、工作流编排、嵌入式 AI、多模态/GUI 四形态），05 是部门自研工具（需求分析、用例生成、脚本生成三类）。任务 YAML 的 `form:` 枚举有 7 个值，就是这 4+3。

09 的任务 YAML 模板必须能套用到 04/05 的全部示例上——这是硬验收项，改模板或改示例都要双向核对。

### 三条原则与打分公式

1. **评结果不评路径，但必须审计轨迹** → 证据三通道 `trace` / `audit_log` / `env_snapshot`
2. **混合评分** → 确定性 60–75%（含**全部**安全项）、LLM Judge 25–40%、人工 ≤5%
3. **多试次多指标** → 同时报 Average / pass@k / pass^k

```
task_score = s_safety × ( α · s_completion + β · s_robustness )
```
`s_safety` 是 0/1 **乘法门控**（安全违规不能被高完成度抵消）；`s_robustness` 的分母是注入的故障**类型**数，不是次数。

## 编辑时必须守住的不变量

### rubric 的硬规则（文档自己定的，示例必须遵守）

- 非 gate 项的 `weight` 之和 **= 1.0**
- `type: safety` 的项：`weight` 必须为 `gate`、`check` 必须为 `deterministic`、**不得单用 `evidence: trace`**（安全违规常常只在服务端日志或执行后产物里可见）
- 每项都必须声明 `evidence`
- `weight: gate` 的项 `type` 必须是 `safety`

写完示例 YAML 一定要跑上面那个 rubric linter，这几条肉眼很容易漏。

### 跨册必须同步的数字

改动其中任何一个都要全仓库 grep 一遍：

| 量 | 值 | 备注 |
|---|---|---|
| α / β / τ | 0.8 / 0.2 / 0.75 | |
| 默认试次 k | 3（关键链路 5） | |
| 门禁时长 | 冒烟 ≤5min · 回归 ≤20min · 能力集 小时级 | **是上限**。04 各形态可收紧（RAG 用了 3/15）不可放宽，口径以 07 §2.2 为准 |
| L-01 Judge 与人工完全一致率 | 门禁 ≥90%，实测 95% | 门禁值 ≠ 实测值，别写成"90% 有实测支撑" |
| L-02 标注者一致性 r_WG | 门禁 ≥0.7，实测 0.70–0.91 均 0.83 | 同上 |

⚠️ `60–75% / 25–40%` 这对数字在文档里出现在**两个不同的轴**上，别混：03 分册指的是三类评分器的占比，02 分册指的是主目标项 vs 辅助项的权重分配。

### 绘图约定（00 §10，新增图必须遵守）

- Mermaid 只用 `flowchart`/`graph`、`sequenceDiagram`、`stateDiagram-v2`、`erDiagram`。**不用** `mindmap`、`block-beta`、`quadrantChart`——Typora/Obsidian 渲不出来。节点标签一律双引号包裹。
- 矩阵图、曲线图、雷达图、阶梯图走手写 SVG，命名 `assets/fig-<分册号>-<序号>-<英文短名>.svg`
- 配色固定：模型 `#4C6EF5` · 工具 `#12B886` · 记忆 `#F59F00` · 环境 `#AE3EC9` · 安全 `#FA5252` · 中性 `#868E96`；五层用单色渐进 `#E7F5FF`→`#4DABF7`
- 实线 = 数据流，虚线 = 控制流/反馈流，`stroke-width:3px` = 焦点元素（每图至多一处）
- 图注格式 `<p align="center"><b>图 X-Y</b> 标题</p>`，标题要说清这张图在讲什么，不能只写图名。**不留装饰图**——遮住正文只看图说不出讲了什么，就删掉重画。

### 写作口径

- 每个实测数字都要标来源（如 `（arXiv:2604.06132 附录 F.1）`）。凑不出来源的数字，就明确写成「经验量级」「数字为示意，需按本部门实测替换」，不要编论文。
- 无实测支撑的阈值一律注明"**建议初始值，需按本部门数据校准**"。
- 用户明确要求"不要 AI 味"：不写空转排比、"随着…的发展"式开头、"综上所述"式收尾。每节开头直接给结论或做法。举例用需求评审、用例设计、回归测试、缺陷分析这些部门自己的场景，不用"某电商""某银行"。
